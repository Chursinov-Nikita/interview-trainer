@@@ react-01 | reconciliation, key
Как работает reconciliation и зачем нужен `key`?
???
**Reconciliation (согласование)** — процесс, в котором React после ререндера сравнивает новое дерево элементов со старым и вычисляет минимальные изменения для DOM. Полное сравнение двух деревьев слишком дорогое, поэтому React использует два упрощающих правила:

- **другой тип элемента** на том же месте (`<div>` → `<section>`, `<Login>` → `<Profile>`) — старое поддерево целиком удаляется вместе с состоянием, новое создаётся с нуля;
- **тот же тип** — элемент переиспользуется, обновляются только изменившиеся пропсы и атрибуты.

**Зачем `key`.** В списке React по умолчанию сопоставляет элементы **по позиции**: первый с первым, второй со вторым. Если вставить элемент в начало, все позиции сдвинутся, и React решит, что изменились все элементы. `key` даёт каждому элементу «паспорт», и React узнаёт его, куда бы тот ни переместился.

```tsx
{todos.map((todo) => <TodoItem key={todo.id} todo={todo} />)}
```

**Почему индекс — плохой key.** При вставке, удалении или сортировке индекс достаётся другому элементу. Состояние (текст в инпуте, отметка чекбокса, фокус) привязано к key, поэтому оно «переезжает» на чужую строку: удалил первую задачу — галочка оказалась у второй.

Индекс допустим, только если список никогда не меняет порядок и не фильтруется.

Требования к key: стабильный (не `Math.random()` — иначе каждый рендер всё пересоздаётся), уникальный среди соседей. Лучший вариант — id из данных.

@@@ react-02 | key, state
Как сбросить состояние компонента при смене пропса?
???
Сменить `key` — React размонтирует старый экземпляр и создаст новый с чистым состоянием:

```tsx
<ProfileForm key={userId} userId={userId} />
```

Почему работает: `key` — часть «личности» компонента. Новый key для React означает другой компонент, поэтому старый удаляется со всем его state, а новый монтируется с начальными значениями.

Это лучше, чем `useEffect(() => setForm(initial), [userId])`: эффект сначала отрисует форму со старыми данными, а потом перерисует её — лишний рендер и мигание. К тому же эффект надо не забыть обновить, когда в форме появится новое поле.

Если сбросить нужно только часть состояния, можно сравнивать пропс прямо во время рендера, но чаще всего `key` — самое простое и надёжное решение. Минус: сбрасываются и все дочерние компоненты, а DOM пересоздаётся.

Типичные случаи: форма редактирования при переключении между записями, чат при смене собеседника, плеер при смене трека.

@@@ react-03 | рендер
Из каких фаз состоит обновление в React? Что вызывает ререндер?
???
Обновление проходит две фазы:

**1. Render** — React вызывает функции компонентов и получает новое дерево элементов (JSX), затем сравнивает его со старым. DOM при этом **не трогается**. Фаза должна быть чистой: React может вызвать компонент несколько раз или прервать работу ради более срочного обновления и начать заново.

**2. Commit** — React применяет вычисленные изменения к DOM. Затем синхронно запускает `useLayoutEffect` (до того, как браузер нарисует кадр), а после отрисовки — `useEffect`.

Важно: «ререндер» — это вызов функции компонента, а не обязательно изменение DOM. Если результат не изменился, DOM останется прежним.

**Что вызывает ререндер компонента:**

- изменение его **state** (`setState` с новым значением);
- **ререндер родителя** — дети перерисовываются, даже если их пропсы не изменились;
- изменение **контекста**, который компонент читает через `useContext` или `use`.

Изменение пропсов само по себе не причина: пропсы меняются только потому, что перерисовался родитель.

```tsx
function Parent() {
  const [n, setN] = useState(0);
  return <><button onClick={() => setN(n + 1)}>+</button><Child /></>;
}
// каждый клик ререндерит и Child, хотя у него нет пропсов
```

Остановить это можно через `memo`, перенос state вниз или передачу `Child` через `children`. React Compiler делает это автоматически.

@@@ react-04 | хуки, эффекты
`useEffect` против `useLayoutEffect`?
???
Оба запускаются после того, как React изменил DOM. Разница — **до или после** того, как браузер нарисовал изменения на экране:

- **`useEffect`** — после отрисовки, асинхронно. Пользователь уже видит новый кадр. Не блокирует браузер. Для запросов, подписок, таймеров, аналитики — то есть почти всегда.
- **`useLayoutEffect`** — синхронно сразу после изменения DOM, но **до** отрисовки. Браузер ждёт, пока эффект закончится.

Когда нужен `useLayoutEffect`: нужно **измерить** DOM и сразу что-то поменять, чтобы пользователь не увидел промежуточное состояние.

```tsx
function Tooltip({ anchor }: { anchor: DOMRect }) {
  const ref = useRef<HTMLDivElement>(null);
  const [top, setTop] = useState(0);

  useLayoutEffect(() => {
    const height = ref.current!.getBoundingClientRect().height;
    setTop(anchor.top - height); // разместить над элементом
  }, [anchor]);

  return <div ref={ref} style={{ top }}>…</div>;
}
```

С `useEffect` тултип сначала мелькнул бы в позиции `top: 0`, а через кадр прыгнул бы на место.

Минусы `useLayoutEffect`: тяжёлый код внутри задерживает отрисовку и делает интерфейс дёрганым. На сервере он не выполняется (там нет DOM).

Правило: начинай с `useEffect`, переходи на `useLayoutEffect`, только если видишь мигание.

@@@ react-05 | хуки, замыкания
Что такое устаревшее замыкание (stale closure) в хуках?
???
Каждый рендер компонента — это отдельный вызов функции со **своими** значениями пропсов и state. Функция, созданная в этом рендере (колбэк, эффект), через замыкание запоминает именно их. Если она живёт дольше рендера, то продолжает видеть старые значения.

```tsx
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000); // count всегда 0
  return () => clearInterval(id);
}, []);
```

Что происходит: эффект запустился один раз (пустой массив зависимостей), в первом рендере, где `count = 0`. Интервал каждую секунду вызывает `setCount(0 + 1)`. Счётчик застревает на 1.

Решения:

- **функциональное обновление** — `setCount((c) => c + 1)`: React передаёт актуальное значение, замыкание на `count` не нужно;
- **честные зависимости** — `[count]`: эффект перезапустится с новым значением (но интервал будет пересоздаваться);
- **`useRef` с последним значением** — ref один на все рендеры, `ref.current` всегда свежий;
- **`useEffectEvent`** (React 19.2) — функция, которая всегда видит свежие значения, но не является зависимостью.

Линтер `react-hooks/exhaustive-deps` предупреждает о таких местах — его предупреждения стоит исправлять, а не отключать.

@@@ react-06 | производительность, memo
Когда нужны `useMemo`, `useCallback` и `React.memo`?
???
Три инструмента мемоизации — «запомнить и не пересчитывать»:

- **`React.memo(Component)`** — компонент пропускает ререндер, если его пропсы **поверхностно равны** прошлым (каждый проп сравнивается через `Object.is`).
- **`useMemo(() => value, deps)`** — запоминает **результат вычисления** и пересчитывает, только когда изменились зависимости.
- **`useCallback(fn, deps)`** — запоминает **саму функцию**. Это то же, что `useMemo(() => fn, deps)`.

Зачем сохранять ссылки: функция и объект, созданные в рендере, — каждый раз новые. Из-за этого:

```tsx
const Row = memo(function Row({ onSelect }: { onSelect: () => void }) { … });

function List() {
  const select = () => {};               // новая функция на каждом рендере
  return <Row onSelect={select} />;      // memo бесполезен: проп всегда «новый»

  const stable = useCallback(() => {}, []); // та же ссылка между рендерами
  return <Row onSelect={stable} />;         // теперь memo работает
}
```

Когда это реально нужно:

1. проп передаётся в `memo`-компонент;
2. значение — зависимость `useEffect` (иначе эффект перезапускается каждый рендер);
3. вычисление действительно дорогое (фильтрация тысяч элементов).

Мемоизация не бесплатна: память, сравнение зависимостей, усложнение кода. Без замеров часто бесполезна. React Compiler делает её автоматически — этот проект собран с ним.

@@@ react-07 | производительность, compiler
Что делает React Compiler?
???
Это плагин сборки (Babel), который анализирует код компонентов и **автоматически вставляет мемоизацию** — то, что раньше писали вручную через `useMemo`, `useCallback` и `memo`.

```tsx
function TodoList({ todos, filter }: Props) {
  const visible = todos.filter((t) => t.status === filter); // компилятор запомнит
  const onToggle = (id: string) => toggle(id);              // и это
  return visible.map((t) => <Todo key={t.id} todo={t} onToggle={onToggle} />);
}
```

После компиляции `visible` пересчитается только при смене `todos` или `filter`, а `onToggle` сохранит ссылку между рендерами. Писать это руками не нужно.

Чем он лучше ручной мемоизации:

- мемоизирует **точнее** — даже отдельные куски JSX, а не только целые компоненты;
- не бывает забытых или неправильных зависимостей;
- код остаётся простым.

Условие: код должен **соблюдать правила React** — чистые компоненты, никаких мутаций пропсов и state, хуки только на верхнем уровне. Если компонент нарушает правила, компилятор не ломает его, а просто **пропускает** без оптимизации. Найти такие места помогает плагин ESLint `react-compiler` (входит в `eslint-plugin-react-hooks`).

Включается в Next.js одной опцией `reactCompiler: true`. Этот проект собран с компилятором, поэтому в нём почти нет ручных `useMemo`.

@@@ react-08 | хуки
Правила хуков. Почему они такие?
???
Правила:

1. Вызывать хуки только **на верхнем уровне** компонента или своего хука — не внутри `if`, циклов, вложенных функций и не после раннего `return`.
2. Вызывать хуки только **из React-компонентов и других хуков** — не из обычных функций.

**Почему.** React не знает имён твоих переменных состояния. Он хранит состояние хуков в **списке по порядку вызова**: первый `useState` — ячейка 1, второй — ячейка 2. При следующем рендере он отдаёт значения в том же порядке.

```tsx
function Form({ showAge }: { showAge: boolean }) {
  const [name, setName] = useState("");        // ячейка 1
  if (showAge) {
    const [age, setAge] = useState(0);         // ✗ ячейка 2 — только иногда
  }
  const [email, setEmail] = useState("");      // ячейка 2 или 3?
}
```

Если `showAge` сменится с `true` на `false`, хук `email` получит ячейку 2, где лежит возраст. Состояния перепутаются — отсюда ошибка «Rendered fewer hooks than expected».

Как быть с условием: вызывать хук всегда, а условие ставить **внутри** него или в использовании результата:

```tsx
useEffect(() => {
  if (!enabled) return;
  // …
}, [enabled]);
```

Исключение — `use()` из React 19: его можно вызывать в условиях и циклах, потому что он не хранит своё состояние в этом списке.

Проверяет правила плагин `eslint-plugin-react-hooks`.

@@@ react-09 | хуки, ref
Для чего нужен `useRef`, кроме доступа к DOM?
???
`useRef` — это «коробка» `{ current: … }`, которая живёт всё время жизни компонента. У неё два свойства, отличающие её от state:

- изменение `ref.current` **не вызывает ререндер**;
- значение доступно **сразу** после записи (а `setState` применится только на следующем рендере).

Поэтому ref подходит для данных, которые нужны для логики, но не для отображения:

```tsx
function Stopwatch() {
  const [time, setTime] = useState(0);
  const intervalRef = useRef<number | null>(null);  // id таймера

  const start = () => {
    intervalRef.current = window.setInterval(() => setTime((t) => t + 1), 1000);
  };
  const stop = () => {
    if (intervalRef.current) clearInterval(intervalRef.current);
  };
  return <p>{time}</p>;
}
```

Что ещё хранят в ref:

- id таймеров и подписок;
- предыдущее значение пропа (для сравнения);
- флаги вроде «компонент уже инициализирован»;
- последнюю версию колбэка, чтобы не перезапускать эффект;
- экземпляры сторонних библиотек (карта, график, редактор).

Ограничения: не храни в ref то, что показываешь на экране, — интерфейс не обновится. И не читай и не пиши `ref.current` **во время рендера** (кроме ленивой инициализации): результат станет непредсказуемым. Работают с ref в обработчиках и эффектах.

@@@ react-10 | формы
Контролируемые и неконтролируемые компоненты?
???
**Контролируемый** компонент: значение поля хранится в state React, и React — единственный источник правды. Поле показывает `value` из state, а каждое изменение проходит через `onChange`:

```tsx
const [email, setEmail] = useState("");
<input value={email} onChange={(e) => setEmail(e.target.value.trim())} />
```

Плюсы: значение всегда под рукой, можно валидировать и преобразовывать на лету (маски, обрезка пробелов), блокировать кнопку, пока форма неверна. Минус: каждый символ — ререндер.

**Неконтролируемый**: значение хранит сам DOM, как в обычном HTML. React задаёт только начальное значение через `defaultValue`, а прочитать его можно при отправке:

```tsx
function Form() {
  const onSubmit = (e: React.FormEvent<HTMLFormElement>) => {
    e.preventDefault();
    const data = new FormData(e.currentTarget);
    save(data.get("email"));
  };
  return <form onSubmit={onSubmit}><input name="email" defaultValue="" /></form>;
}
```

Плюсы: меньше кода и ререндеров. Минус: сложнее реагировать на ввод в реальном времени.

React 19 с `<form action={fn}>` снова сделал неконтролируемые формы удобными: функция получает `FormData` сама. На неконтролируемых полях работает и react-hook-form.

Частая ошибка — `value` меняется с `undefined` на строку (например, `value={user?.name}`), и React предупреждает о переключении режима. Решение: `value={user?.name ?? ""}`.

@@@ react-11 | state, антипаттерн
Почему не стоит копировать пропсы в state и синхронизировать их через `useEffect`?
???
Если значение можно **вычислить** из пропсов или другого state, хранить его отдельно не нужно. Копия — это второй источник правды, который может разойтись с первым.

```tsx
// ✗ лишний state и эффект
const [full, setFull] = useState("");
useEffect(() => setFull(`${first} ${last}`), [first, last]);

// ✓ просто вычисление в рендере
const full = `${first} ${last}`;
```

Что не так с первым вариантом:

1. **Лишний рендер.** Сначала компонент рисуется со старым `full`, потом эффект вызывает `setFull`, и происходит второй рендер. Пользователь может на мгновение увидеть устаревшее значение.
2. **Рассинхронизация.** Легко забыть зависимость или обновить одно, но не другое.
3. **Больше кода** и больше мест для ошибок.

Правило: state — только для данных, которые **нельзя** вычислить и которые меняются со временем. Всё производное (отфильтрованный список, сумма корзины, «форма валидна») — вычисляется в рендере.

Варианты, когда нужно больше:

- вычисление дорогое → `useMemo(() => heavy(items), [items])`;
- нужно сбросить state при смене пропса → `key`;
- проп — только начальное значение (`initialColor`) → копировать в state можно, но называть его явно как начальное.

@@@ react-12 | context, производительность
Какая проблема производительности у Context и как её решить?
???
Когда меняется `value` провайдера, React перерисовывает **всех** потребителей этого контекста — даже если конкретному компоненту нужно поле, которое не менялось. Выбрать «кусочек» контекста нельзя.

Вторая ловушка — объект создаётся заново при каждом рендере провайдера:

```tsx
function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  return (
    <AuthContext value={{ user, setUser }}> {/* новый объект на каждый рендер */}
      {children}
    </AuthContext>
  );
}
```

Даже если `user` не менялся, `{ user, setUser }` — новый объект, и все потребители перерисуются при любом ререндере `AuthProvider`.

Решения:

- **мемоизировать `value`**: `useMemo(() => ({ user, setUser }), [user])` (React Compiler делает это сам);
- **разделить контексты**: данные отдельно от функций (`setUser` никогда не меняется), часто меняющееся отдельно от редкого;
- **опускать провайдер ниже** — ближе к компонентам, которым он нужен;
- для часто меняющегося глобального состояния взять **стор с селекторами** (Zustand, Redux): там компонент подписывается на конкретное поле и перерисуется, только когда изменилось оно.

Контекст отлично подходит для редко меняющихся данных: тема, язык, текущий пользователь. Для состояния, которое меняется на каждый ввод, — не очень.

@@@ react-13 | хуки, state
Когда `useReducer` лучше `useState`?
???
`useReducer` выносит **логику изменения состояния** в отдельную чистую функцию — reducer. Компонент только сообщает, *что* произошло (`dispatch({ type: "add" })`), а reducer решает, *как* поменять state.

```ts
type Action = { type: "inc" } | { type: "set"; value: number };

function reducer(state: number, action: Action) {
  switch (action.type) {
    case "inc": return state + 1;
    case "set": return action.value;
  }
}

const [count, dispatch] = useReducer(reducer, 0);
dispatch({ type: "inc" });
```

Когда он удобнее `useState`:

- **много связанных полей**, которые меняются вместе (форма, корзина, загрузка `{ status, data, error }`);
- **следующее состояние сложно зависит от предыдущего** — с условиями и проверками;
- **много разных действий** над одними данными: добавить, удалить, переместить, очистить;
- **конечный автомат**: мастер из шагов, статусы заказа.

Плюсы:

- вся логика переходов в одном месте, её легко прочитать и **протестировать** без React — это обычная функция;
- `dispatch` **стабилен**: его можно передавать вниз без `useCallback`;
- компоненты описывают события, а не детали обновления.

Для одного-двух независимых значений `useState` проще и понятнее. Если reducer разрастается и нужен глобально — это повод посмотреть на Zustand или Redux Toolkit, которые построены на той же идее.

@@@ react-14 | state, batching
Почему state не обновляется сразу после `setState`? Что такое batching?
???
`setState` **не меняет** переменную сразу. Он ставит обновление в очередь и планирует новый рендер. Переменная `count` в текущем рендере — это константа, снимок значения на момент рендера:

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  const onClick = () => {
    setCount(count + 1);
    console.log(count); // 0 — в этом рендере count всегда 0
  };
}
```

Новое значение появится в **следующем** вызове функции компонента.

**Batching (пакетирование)** — React собирает все `setState`, вызванные в одном обработчике, и делает **один** рендер вместо нескольких. С React 18 это работает везде: в обработчиках, промисах, таймерах (automatic batching).

Отсюда классическая задача:

```tsx
setCount(count + 1);
setCount(count + 1); // итог: +1 — оба вызова = setCount(0 + 1)

setCount((c) => c + 1);
setCount((c) => c + 1); // итог: +2
```

Функциональное обновление получает **актуальное** значение из очереди: первая функция получает 0 и возвращает 1, вторая получает 1 и возвращает 2.

Правило: если новое значение зависит от предыдущего — используй функцию `(prev) => …`.

Если нужно действие сразу после обновления DOM — `useEffect` или, в редких случаях, `flushSync`.

@@@ react-15 | concurrent
Что делают `useTransition` и `useDeferredValue`?
???
Оба нужны, чтобы тяжёлое обновление интерфейса не тормозило срочное (ввод текста, клики). Они помечают обновление как **несрочное**: React начинает его рендерить, но если пользователь в это время печатает, прерывает работу, обрабатывает ввод и возвращается позже.

**`useTransition`** — когда ты сам вызываешь обновление:

```tsx
const [isPending, startTransition] = useTransition();

const selectTab = (next: string) => {
  startTransition(() => setTab(next)); // тяжёлая вкладка рендерится «в фоне»
};

{isPending && <Spinner />}
```

Пока новая вкладка готовится, старая остаётся интерактивной, а `isPending` позволяет показать индикатор.

**`useDeferredValue`** — когда значение приходит извне (пропсом или из чужого state), и `setState` ты не контролируешь:

```tsx
function Search({ query }: { query: string }) {
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;
  return <HeavyList query={deferredQuery} style={{ opacity: isStale ? 0.5 : 1 }} />;
}
```

Инпут обновляется мгновенно, а список рендерится по «отстающей» копии значения, когда у React есть время.

Это **не замена debounce** для сетевых запросов: они ускоряют рендер, но не уменьшают число запросов. Для запросов нужен debounce или библиотека вроде TanStack Query.

@@@ react-16 | suspense
Как работает Suspense?
???
`<Suspense>` — граница загрузки. Если какой-то компонент внутри **ещё не готов** к рендеру (ждёт данные или код), React показывает `fallback` ближайшей границы, а когда всё загрузилось — рендерит настоящее содержимое.

```tsx
<Suspense fallback={<Skeleton />}>
  <Profile />   {/* если Profile ждёт данные, покажется Skeleton */}
</Suspense>
```

Как компонент сообщает, что не готов: он «приостанавливается» (suspend) — технически бросает промис, и React ловит его ближайшей границей. Сам ты так не пишешь — это делают:

- `use(promise)` в React 19;
- `React.lazy` для кода;
- фреймворки и библиотеки с поддержкой Suspense (Next.js, TanStack Query с `useSuspenseQuery`).

Связка `useEffect` + `fetch` с Suspense **не работает**: эффект запускается уже после рендера, компонент ничего не «приостанавливает».

Что даёт Suspense:

- **декларативная загрузка**: не нужен `if (loading) return <Spinner />` в каждом компоненте;
- **гибкие границы**: одна граница на страницу или отдельные на каждый блок — по задумке дизайна;
- **стриминг на сервере**: в Next.js HTML отправляется частями — сначала каркас с `fallback`, потом готовые блоки. Пользователь видит страницу раньше.

Если граница уже показала содержимое, а новое обновление снова приостанавливает компонент, обновление в `startTransition` не будет заменять экран на `fallback`, а оставит старое содержимое.

@@@ react-17 | производительность, lazy
Как разделить бандл на чанки в React?
???
По умолчанию сборщик кладёт весь код в один или несколько больших файлов, и пользователь качает всё сразу — даже то, что он может не открыть. **Code splitting** выносит редко нужные части в отдельные файлы (чанки), которые загружаются по требованию.

Основа — динамический `import()`: он возвращает промис, и сборщик автоматически делает из импортируемого модуля отдельный чанк.

```tsx
import { lazy, Suspense } from "react";

const Chart = lazy(() => import("./Chart")); // код Chart не попадёт в основной бандл

function Dashboard({ showChart }: { showChart: boolean }) {
  return (
    <Suspense fallback={<Spinner />}>
      {showChart && <Chart />}   {/* чанк скачается, только когда понадобится */}
    </Suspense>
  );
}
```

`lazy` ждёт модуль с **экспортом по умолчанию**. Для именованного: `lazy(() => import("./Chart").then((m) => ({ default: m.Chart })))`.

Что выносить:

- тяжёлые библиотеки: графики, редакторы текста, карты;
- модалки и панели, которые открываются по клику;
- целые маршруты (в Next.js это делается автоматически — каждая страница отдельный чанк).

В Next.js для компонентов используют `next/dynamic` — это обёртка над `lazy` с опцией `ssr: false` для компонентов, которые работают только в браузере.

Посмотреть, что занимает место в бандле, можно анализатором (`@next/bundle-analyzer`). Перебарщивать не стоит: сотня мелких чанков — это сотня запросов.

@@@ react-18 | ошибки
Что такое Error Boundary и что он **не** ловит?
???
Если компонент бросает ошибку во время рендера, React по умолчанию размонтирует **всё приложение** — пользователь видит белый экран. Error Boundary — компонент-«предохранитель»: ловит ошибки рендера своих потомков и показывает запасной интерфейс вместо упавшей части.

Пишется только классом — функциональной версии в React нет:

```tsx
class ErrorBoundary extends React.Component<{ children: React.ReactNode }, { error: Error | null }> {
  state = { error: null };
  static getDerivedStateFromError(error: Error) {
    return { error };              // переключиться на запасной UI
  }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    logToSentry(error, info);      // отправить в мониторинг
  }
  render() {
    return this.state.error ? <p>Что-то сломалось</p> : this.props.children;
  }
}
```

На практике берут готовую библиотеку `react-error-boundary`, а в Next.js — файл `error.tsx` в папке маршрута.

**Не ловит:**

- ошибки в **обработчиках событий** (`onClick`) — это не рендер, лови `try/catch`;
- **асинхронный код**: таймеры, промисы, `fetch` вне рендера;
- ошибки при **рендере на сервере**;
- ошибки **в самом себе** — только в потомках.

Чтобы ошибку из обработчика показать через границу, её кладут в state и бросают при рендере: `if (error) throw error`.

Границы ставят на разных уровнях: одна на всё приложение и отдельные вокруг виджетов, чтобы падение одного блока не роняло страницу.

@@@ react-19 | dom, portals
Зачем нужны порталы?
???
`createPortal(children, domNode)` рендерит элементы в другой DOM-узел (обычно `document.body`), но в **дереве React** они остаются на своём месте:

- работает контекст родителя;
- события **всплывают по React-дереву**, а не по DOM: клик в модалке дойдёт до `onClick` компонента, который её отрендерил.

```tsx
function Modal({ children }: { children: React.ReactNode }) {
  return createPortal(<div className="modal">{children}</div>, document.body);
}
```

Нужны модалкам, тултипам, выпадающим меню и тостам — чтобы вырваться из `overflow: hidden` и контекста наложения (`z-index`) родителя. В SSR портал можно рендерить только на клиенте: на сервере нет `document`.

Пример проблемы без портала: модалка внутри карточки с `overflow: hidden` обрежется по краям карточки, а `z-index: 9999` не поможет, если у родителя свой контекст наложения (например, `transform`). Портал физически переносит разметку в `body`, и эти ограничения исчезают.

Альтернатива для модалок — нативный `<dialog>` с `showModal()`: он попадает в верхний слой (top layer) поверх всего без порталов.

@@@ react-20 | strict mode, эффекты
Почему в StrictMode эффекты срабатывают дважды?
???
Только в dev React специально проверяет компоненты:

- вызывает рендер дважды — чтобы поймать нечистые компоненты (мутации, случайные значения);
- монтирует → размонтирует → снова монтирует — чтобы проверить, что у эффектов есть правильная очистка.

Если двойной вызов что-то ломает — значит, нет cleanup:

```tsx
useEffect(() => {
  const ws = new WebSocket(url);
  return () => ws.close(); // без этого будет два соединения
}, [url]);
```

Для запросов — флаг `ignore` или `AbortController` в cleanup. В продакшене двойных вызовов нет, но та же ситуация возникает при быстрой смене пропсов, поэтому чинить нужно эффект, а не отключать StrictMode.

Зачем React это делает: в будущем он будет скрывать и показывать части интерфейса с сохранением состояния (как `<Activity>`), а значит, монтировать эффекты повторно. Компонент с правильной очисткой это переживёт, а без неё — начнёт течь памятью и дублировать подписки.

@@@ react-21 | эффекты, данные
Как правильно загружать данные в `useEffect`? Что такое race condition?
???
**Race condition (состояние гонки)** — ответы на запросы приходят **не в том порядке**, в котором запросы отправлялись.

Сценарий: пользователь открыл профиль 1, потом быстро профиль 2. Запрос за профилем 1 оказался медленнее. Сначала пришёл ответ 2 и отрисовался, потом пришёл ответ 1 — и перезаписал экран. Пользователь смотрит на страницу профиля 2 с данными профиля 1.

Решение — отменять (или игнорировать) устаревший запрос в функции очистки:

```tsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/user/${id}`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setUser)
    .catch(() => {});
  return () => controller.abort();
}, [id]);
```

При смене `id` React сначала вызовет очистку прошлого эффекта — старый запрос будет отменён, и его ответ уже не попадёт в `setUser`.

Вариант без отмены запроса — флаг:

```tsx
useEffect(() => {
  let ignore = false;
  getUser(id).then((u) => { if (!ignore) setUser(u); });
  return () => { ignore = true; };
}, [id]);
```

Чего ещё не хватает ручной загрузке: кэша (повторный переход снова грузит данные), дедупликации одинаковых запросов, повторов при ошибке, состояния загрузки и ошибки. Поэтому в продакшене обычно берут TanStack Query или SWR, а в Next.js — серверные компоненты.

@@@ react-22 | хуки, store
Для чего нужен `useSyncExternalStore`?
???
Хук для подписки на данные, которые живут **вне React**: свой стор, `matchMedia`, `navigator.onLine`, `localStorage`, размер окна. Он делает три вещи сам: подписывается на изменения, читает текущее значение и перерисовывает компонент, когда оно поменялось.

Он принимает три функции:

1. `subscribe(callback)` — подписаться на изменения и вернуть функцию отписки;
2. `getSnapshot()` — прочитать текущее значение на клиенте;
3. `getServerSnapshot()` — значение при SSR (на сервере нет `window`).

```ts
const online = useSyncExternalStore(
  (cb) => {
    addEventListener("online", cb);
    addEventListener("offline", cb);
    return () => {
      removeEventListener("online", cb);
      removeEventListener("offline", cb);
    };
  },
  () => navigator.onLine, // снимок на клиенте
  () => true,             // снимок на сервере
);
```

Почему не `useState` + `useEffect`: в concurrent-режиме React может рендерить дерево частями. Если внешний стор изменится посреди рендера, одна половина интерфейса покажет старое значение, а другая — новое. Это называется **tearing** («разрыв»). `useSyncExternalStore` гарантирует, что весь рендер увидит одно и то же значение. Плюс серверный снимок избавляет от ошибок гидратации.

Важно: `getSnapshot` должен возвращать **одно и то же** значение, пока данные не изменились. Если возвращать новый объект каждый раз, будет бесконечный ререндер.

На нём построены Zustand и react-redux.

@@@ react-23 | rsc, next
Что такое React Server Components? Чем они отличаются от SSR?
???
**Серверные компоненты (RSC)** выполняются **только на сервере**. Это обычные компоненты, но с особенностями:

- могут быть `async` и прямо внутри ходить в базу данных, читать файлы, использовать секретные ключи;
- их код **не попадает в браузер** — бандл меньше, зависимости вроде парсера Markdown остаются на сервере;
- нет состояния, эффектов и обработчиков событий — они не интерактивны.

```tsx
async function PostPage({ id }: { id: string }) {
  const post = await db.post.findUnique({ where: { id } }); // прямо в компоненте
  return <article>{post.title}<LikeButton postId={id} /></article>;
}
```

**Клиентские компоненты** (`"use client"`) — привычные: state, эффекты, обработчики. `LikeButton` выше — клиентский.

**Чем отличается от SSR.** Это разные вещи, которые работают вместе:

- **SSR** — рендер **любых** компонентов в HTML для быстрой первой загрузки. Потом весь их код всё равно скачивается в браузер, и React «оживляет» HTML (гидратация).
- **RSC** — часть дерева **никогда** не отправляется в браузер как код и не гидратируется. В браузер приходит только результат рендера.

Итого: SSR ускоряет первый показ, RSC уменьшает количество JS у клиента.

Правила композиции: серверный компонент может рендерить клиентский и передавать ему сериализуемые пропсы. Клиентский **импортировать** серверный не может — только получить его через `children` или другой проп.

@@@ react-24 | rsc, next
Что означает `"use client"` и где проводить границу?
???
`"use client"` в начале файла помечает **точку входа** в клиентский код. Этот модуль и **всё, что он импортирует**, попадает в клиентский бандл и работает в браузере. Метить каждый клиентский файл не нужно — достаточно файла на границе.

Важно: `"use client"` не означает «рендерится только на клиенте». Такие компоненты тоже проходят SSR — директива значит «нужен в браузере», то есть будет гидратирован.

**Где проводить границу** — как можно ниже, на интерактивных «листьях»:

```tsx
// page.tsx — серверный: данные, разметка, SEO
export default async function Page() {
  const product = await getProduct();
  return (
    <main>
      <h1>{product.title}</h1>
      <p>{product.description}</p>
      <AddToCart id={product.id} />   {/* клиентский — только кнопка */}
    </main>
  );
}
```

Если пометить `"use client"` всю страницу, весь её код и зависимости уедут в браузер, а прямой доступ к базе станет невозможен.

**Пропсы через границу** должны быть сериализуемыми: строки, числа, массивы, обычные объекты, `Date`, промисы, JSX. Нельзя передать функцию (кроме Server Actions) или экземпляр класса.

Приём «дырки»: клиентская обёртка (например, анимированная панель) может принять серверные компоненты через `children` — они останутся серверными.

@@@ react-25 | ssr, гидратация
Что такое гидратация и откуда берётся hydration mismatch?
???
**Гидратация** — второй шаг SSR. Сервер прислал готовый HTML, пользователь его уже видит, но кнопки ещё не работают. Затем загружается JS, и React проходит по существующему HTML, «надевая» на него компоненты: навешивает обработчики, восстанавливает связь с состоянием. DOM при этом не пересоздаётся — React ожидает, что он **совпадает** с тем, что отрендерил бы клиент.

**Hydration mismatch** — клиентский рендер дал не то, что сервер. React предупреждает в консоли и перерисовывает расходящийся кусок на клиенте (страница может мигнуть).

Частые причины:

- **разные значения**: `Date.now()`, `Math.random()`, `new Date().toLocaleString()` — на сервере и клиенте они разные;
- **браузерные API в рендере**: `window.innerWidth`, `localStorage.getItem("theme")` — на сервере их нет, там получится другое значение;
- **разная локаль или часовой пояс** при форматировании дат;
- **неверная вложенность тегов**: `<div>` внутри `<p>`, `<a>` внутри `<a>` — браузер сам «чинит» такой HTML, и DOM не совпадает с ожидаемым;
- **расширения браузера**, которые меняют разметку.

Решения:

```tsx
const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);
if (!mounted) return <Skeleton />; // одинаково на сервере и при гидратации

<time suppressHydrationWarning>{new Date().toLocaleTimeString()}</time>
```

Лучше всего — `useSyncExternalStore` с серверным снимком для браузерных значений. `suppressHydrationWarning` — точечно, для одного элемента, где расхождение ожидаемо.

@@@ react-26 | react 19, формы
Что нового в React 19 для форм (Actions)?
???
**Action** — функция (часто асинхронная), которую React вызывает при отправке формы. Раньше для формы нужны были `onSubmit`, `preventDefault`, свой `useState` для загрузки и ошибок. Теперь это встроено.

- **`<form action={fn}>`** — форма вызывает `fn` и передаёт ей `FormData` со всеми полями. Перезагрузки страницы нет.
- **`useActionState(action, initial)`** → `[state, formAction, isPending]`. Хранит результат последнего вызова (например, ошибки валидации) и флаг выполнения.
- **`useFormStatus()`** — читает статус **ближайшей родительской формы**. Удобно для кнопки «Отправить» в отдельном компоненте: не нужно прокидывать `isPending` пропсом.
- **`useOptimistic(state)`** — показывает ожидаемый результат сразу, до ответа сервера, и сам откатывает его, если action завершился ошибкой.

```tsx
function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? "Сохраняю…" : "Сохранить"}</button>;
}

function CommentForm() {
  const [state, formAction] = useActionState(addComment, { error: null });
  return (
```

@@@ react-27 | react 19, хуки
Что делает хук `use()` в React 19?
???
`use()` читает значение из **промиса** или **контекста**.

С промисом: если промис ещё не выполнен, компонент «приостанавливается», и ближайший `<Suspense>` показывает `fallback`. Когда промис выполнится, React перерисует компонент, и `use` вернёт результат. Если промис отклонён — ошибку поймает ближайший Error Boundary.

```tsx
function Comments({ promise }: { promise: Promise<Comment[]> }) {
  const comments = use(promise); // приостановит рендер до резолва
  return comments.map((c) => <p key={c.id}>{c.text}</p>);
}

<Suspense fallback={<Spinner />}>
  <Comments promise={commentsPromise} />
</Suspense>
```

В отличие от других хуков, `use` **можно вызывать в условиях и циклах**:

```tsx
function Heading({ show }: { show: boolean }) {
  if (!show) return null;
  const theme = use(ThemeContext); // после раннего return — можно
  return <h1 className={theme}>…</h1>;
}
```

Главная ловушка: промис нельзя создавать **прямо в рендере клиентского компонента** — `use(fetch(url))` создаст новый промис при каждом рендере, и компонент будет приостанавливаться бесконечно. Промис должен быть стабильным:

- создан в серверном компоненте и передан пропсом (типичный сценарий в Next.js — данные начинают грузиться на сервере, а дожидаются на клиенте);
- взят из кэша библиотеки.

@@@ react-29 | хуки
Что такое кастомный хук? Делят ли компоненты его состояние?
???
Функция с именем `use…`, которая вызывает другие хуки. Это способ переиспользовать **логику**, а не состояние: каждый вызов хука получает своё независимое состояние.

```tsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  return [on, toggle] as const;
}

const [menuOpen, toggleMenu] = useToggle();  // своё состояние
const [modalOpen, toggleModal] = useToggle(); // и здесь своё
```

Почему так: хук — это не объект и не сервис, а просто функция. Её вызов внутри компонента равносилен тому, что ты вставил её код прямо в компонент. Поэтому `useState` внутри хука — это `useState` того компонента, который хук вызвал.

Префикс `use` нужен линтеру: по нему он проверяет правила хуков. Если функция не вызывает хуки внутри, это обычная утилита, и называть её `use…` не нужно.

Чтобы делить данные между компонентами, нужно поднять state выше, использовать контекст или внешний стор.

Примеры полезных хуков: `useDebounce`, `useLocalStorage`, `useMediaQuery`, `useOnClickOutside`, `useFetch`.

Как избежать prop drilling без контекста?
???
**Prop drilling** — ситуация, когда данные передаются через несколько уровней компонентов, которым они сами не нужны, — только чтобы донести их до глубоко вложенного ребёнка:

```tsx

    <Sidebar user={user}>       {/* и Sidebar тоже */}
      <UserMenu user={user} />  {/* а нужен он только здесь */}
```

Проблемы: промежуточные компоненты знают о лишнем, при переименовании пропа приходится править всю цепочку.

```tsx
function Layout({ sidebar, children }: { sidebar: React.ReactNode; children: React.ReactNode }) {
  return <div className="grid"><aside>{sidebar}</aside><main>{children}</main></div>;
}

<Layout sidebar={<UserMenu user={user} />}>
  <Feed user={user} />
</Layout>
```

Теперь `Layout` вообще ничего не знает о пользователе — он просто раскладывает переданные блоки. `user` передаётся на один уровень, прямо туда, где нужен.

Другие способы:

- **перенести состояние ближе** к месту использования — может, оно и не должно жить наверху;
- **контекст** — для действительно глобальных данных: тема, текущий пользователь, локаль;
- **стор** (Zustand, Redux) — для общего состояния приложения.

Небольшой prop drilling на 2–3 уровня — нормально и даже хорошо: поток данных явный и легко читается.

???
Проблема: 10 000 строк — это 10 000 DOM-узлов (а с вложенными — в разы больше). Браузер тратит время на layout и paint всех строк, даже тех, что далеко за экраном, а React — на их рендер.

```tsx
  const parentRef = useRef<HTMLDivElement>(null);
  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 48, // примерная высота строки
  });

  return (
    <div ref={parentRef} style={{ height: 600, overflow: "auto" }}>
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map((row) => (
          <div key={row.key} style={{ position: "absolute", top: row.start, height: row.size }}>
            {items[row.index].name}
          </div>
        ))}
      </div>
    </div>
  );
}
```

Библиотеки: TanStack Virtual, react-window, react-virtuoso.

Дополнительно:

- стабильные `key` и `memo` для строк — чтобы при изменении одной не перерисовывались все;
- пагинация или бесконечная подгрузка — часто пользователю и не нужны все 10 000 сразу;
- CSS `content-visibility: auto` — простой вариант без JS: браузер пропускает отрисовку блоков за экраном.

Минусы виртуализации: не работает поиск браузера (Ctrl+F) по невидимым строкам, сложнее с доступностью и строками разной высоты.

@@@ react-32 | fiber, внутренности
Что такое Fiber?
???
**Fiber** — внутренняя архитектура React, переписанная в 16-й версии. Слово означает и сам движок, и единицу работы в нём.

**Что было до неё.** Старый React рендерил дерево рекурсивно, за один заход: начал — не может остановиться, пока не закончит. Большое дерево могло занять 100 мс, и всё это время браузер не реагировал на ввод.

**Что изменилось.** Каждый компонент представлен объектом-узлом fiber. В нём хранятся тип компонента, пропсы, state (список хуков), а также ссылки на родителя, первого ребёнка и следующего соседа. Получается связный список, по которому можно идти **шаг за шагом** вместо рекурсии.

Благодаря этому рендер разбит на маленькие кусочки, и React может:

- **прерывать** работу, чтобы отдать браузеру время на отрисовку и ввод;
- **приоритизировать**: ввод текста срочнее, чем фоновая перерисовка списка;
- **возобновлять** или выбрасывать незаконченную работу, если данные устарели.

На этом построены все concurrent-возможности: `useTransition`, `useDeferredValue`, Suspense, стриминг.

**Два дерева (double buffering).** React держит текущее дерево (то, что на экране) и рабочее (то, что строится). Когда рабочее готово, они просто меняются местами — поэтому пользователь никогда не видит наполовину обновлённый интерфейс.

На собесе достаточно объяснить идею: прерываемый рендер и приоритеты.

@@@ react-33 | хуки, эффекты, react 19
Что такое `useEffectEvent`?
???
(React 19.2) Хук для «событий» внутри эффекта. Функция всегда видит свежие пропсы и state, но **не является зависимостью** эффекта.

Проблема, которую он решает: в эффекте есть **реактивная** часть (от чего зависит, когда переподключаться) и **нереактивная** (что сделать, когда что-то случилось). Без `useEffectEvent` всё, что используется в эффекте, приходится добавлять в зависимости:

```tsx
useEffect(() => {
  const conn = connect(roomId);
  conn.on("connected", () => showToast(theme));
  return () => conn.disconnect();
}, [roomId, theme]); // смена темы переподключает чат — плохо
```

С `useEffectEvent`:

```tsx
const onConnected = useEffectEvent(() => showToast(theme));

useEffect(() => {
  const conn = connect(roomId);
  conn.on("connected", onConnected);
  return () => conn.disconnect();
}, [roomId]); // смена theme не переподключает чат
```

`onConnected` при вызове прочитает **текущую** тему, но эффект перезапустится только при смене `roomId`.

Правила: вызывать такую функцию можно только внутри эффектов, не передавать её другим компонентам и не вызывать в рендере. Линтер знает, что её не нужно добавлять в зависимости.

@@@ react-34 | эффекты, порядок
В каком порядке вызываются рендер и эффекты у родителя и ребёнка?
???
- **Рендер** — сверху вниз: сначала родитель, потом дети. Логично: родитель возвращает JSX, в котором и описаны дети.
- **Эффекты** — снизу вверх: сначала у детей, потом у родителя. Сначала все `useLayoutEffect` (до отрисовки), потом все `useEffect`.

```
parent render → child render →
child layout → parent layout →
child effect → parent effect
```

Почему эффекты идут снизу вверх: родитель считается «смонтированным» только тогда, когда смонтированы все его дети. Поэтому в эффекте родителя DOM детей уже готов, а ref на дочерний элемент заполнен.

```tsx
function Parent() {
  const childRef = useRef<HTMLInputElement>(null);
  useEffect(() => {
    childRef.current?.focus(); // ref уже заполнен — ребёнок смонтирован раньше
  }, []);
  return <Child ref={childRef} />;
}
```

Очистка при размонтировании идёт в том же порядке, что и эффекты.

Практический вывод: если ребёнок в своём эффекте сообщает что-то родителю (через колбэк), родительский эффект запустится уже после этого.

@@@ react-35 | рендер, ловушка
Что отрендерит `{count && <Badge />}`, если `count = 0`?
???
Отрендерит **`0`** прямо на странице. `&&` возвращает первый falsy-операнд, а React рисует числа (в отличие от `false`, `null` и `undefined`).

Как работает `&&` в JS: если левая часть falsy, результатом всего выражения будет **сама левая часть**, а не `false`. `0 && <Badge />` — это `0`. React получает число и честно выводит его как текст.

```tsx
{count && <Badge />}       // при 0 покажет «0»
{count > 0 && <Badge />}   // ✓
{!!count && <Badge />}     // ✓
{count ? <Badge /> : null} // ✓
```

То же с `NaN` и пустой строкой: `NaN` выведется как текст «NaN», а `""` ничего не покажет.

Что React не рендерит: `false`, `true`, `null`, `undefined`. Что рендерит: строки и числа, включая `0`.

В React Native это ещё и падение: текст вне `<Text>`.

Правило: слева от `&&` в JSX — всегда булево значение.

@@@ react-36 | state, производительность
Чем отличаются `useState(compute())` и `useState(() => compute())`?
???
Начальное значение нужно только при первом рендере, но выражение в скобках вычисляется **при каждом** рендере:

```tsx
useState(expensive());       // expensive вызывается на каждом рендере
useState(() => expensive()); // только при монтировании — ленивая инициализация
useState(expensive);         // то же самое: передаём саму функцию
```

Почему: `useState(expensive())` — это обычный вызов функции в JS. Прежде чем передать аргумент в `useState`, JS обязан вычислить `expensive()`. React потом выбросит результат, потому что состояние уже есть, но время уже потрачено.

Если передать **функцию**, React сам решит, когда её вызвать, — и вызовет только при первом рендере.

Это важно для тяжёлых вычислений и чтения из `localStorage`. С `useRef` ленивой формы нет — там инициализируют через `if (ref.current === null)`.

Ловушка обратного случая: если в state нужно хранить **саму функцию**, передавать её напрямую нельзя — React её вызовет. Нужно обернуть: `useState(() => myFunction)`.

@@@ react-37 | memo, ловушка
Почему `React.memo` не помогает компоненту, который принимает `children`?
???
JSX `<Box><span>hi</span></Box>` при каждом рендере родителя создаёт **новый объект** элемента в `children`. Поверхностное сравнение пропсов видит новую ссылку — memo каждый раз пропускает рендер дальше.

Напоминание: JSX — это вызов функции. `<span>hi</span>` превращается в `jsx("span", { children: "hi" })`, который каждый раз возвращает новый объект. Содержимое одинаковое, но `Object.is` сравнивает ссылки.

То же с инлайн-объектами и функциями в пропсах: `style={{…}}`, `onClick={() => …}`.

Что делать: мемоизировать передаваемые значения (`useMemo`, `useCallback`) — или вовсе не полагаться на memo, а перестроить дерево (см. «перенос состояния вниз»).

React Compiler решает это автоматически: он мемоизирует и JSX, который передаётся в `children`.

```tsx
function ScrollTracker({ children }: { children: React.ReactNode }) {

  return <div data-y={y}>{children}</div>;

```

Эти приёмы часто эффективнее `memo` и делают код понятнее.

```tsx
const options = useMemo(() => ({ roomId, serverUrl }), [roomId, serverUrl]);
```

Первый вариант самый надёжный. То же касается функций в зависимостях: функцию лучше объявить внутри эффекта.

Как сделать отложенный поиск (debounce) при вводе?
???
Кастомный хук, который возвращает значение с задержкой:

```tsx
function useDebounce<T>(value: T, ms = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), ms);
    return () => clearTimeout(id); // новое значение сбрасывает таймер
  }, [value, ms]);
  return debounced;
}

const [query, setQuery] = useState("");
const debouncedQuery = useDebounce(query);
// запрос делаем по debouncedQuery
```

Как это работает: каждый новый символ меняет `value`, эффект перезапускается, а очистка отменяет таймер прошлого символа. Таймер «доживает» до конца, только если пользователь перестал печатать на `ms` миллисекунд. Тогда `debounced` обновляется — один раз.

Инпут остаётся отзывчивым: `query` меняется мгновенно, а запрос уходит только по `debouncedQuery`.

`useDeferredValue` — про другое: он не уменьшает число запросов, а откладывает тяжёлый **рендер** ради отзывчивости ввода.

@@@ react-42 | паттерны
Что такое HOC и render props? Почему их почти вытеснили хуки?
???
Это два паттерна для **переиспользования логики** между компонентами, которые были популярны до хуков.

**HOC (Higher-Order Component)** — функция, которая принимает компонент и возвращает новый, обёрнутый дополнительной логикой:

```tsx
function withAuth<P>(Component: React.ComponentType<P>) {
  return (props: P) => {
    const user = useUser();
    return user ? <Component {...props} /> : <Login />;
  };
}
const ProtectedProfile = withAuth(Profile);
```

**Render props** — компонент вызывает функцию из пропса (часто `children`) и передаёт ей данные:

```tsx
<Mouse>{(pos) => <Cursor x={pos.x} y={pos.y} />}</Mouse>
```

**Проблемы обоих:**

- **«ад обёрток»** — в DevTools дерево из `withRouter(withTheme(withAuth(Profile)))`;
- **конфликты имён**: два HOC могут передать проп с одинаковым именем, и один перезапишет другой;
- **неявность**: глядя на компонент, непонятно, откуда взялся проп;
- вложенные render props превращаются в «пирамиду».

**Хуки** решают ту же задачу короче и явно: `const pos = useMouse()` — видно, откуда данные, нет обёрток и конфликтов.

HOC ещё встречаются в библиотеках (`connect` в старом Redux, `observer` в MobX), а render props — в компонентах вроде `<Formik>` и в паттерне «слотов». Понимать их нужно, чтобы читать старый код.

@@@ react-43 | тестирование
Как тестировать React-компоненты? Принципы Testing Library.
???
Тестировать **поведение**, а не реализацию: что видит и делает пользователь, а не state и внутренние методы.

```tsx
render(<LoginForm onSubmit={onSubmit} />);
await userEvent.type(screen.getByLabelText("Email"), "a@b.c");
await userEvent.click(screen.getByRole("button", { name: "Войти" }));
expect(onSubmit).toHaveBeenCalledWith({ email: "a@b.c" });
```

- Искать элементы как пользователь: `getByRole`, `getByLabelText`, `getByText`; `data-testid` — крайний случай.
- `userEvent` реалистичнее, чем `fireEvent`.
- Асинхронное ждать через `findBy…` и `waitFor`.
- Сеть мокать на уровне запросов (MSW), а не подменять модули.

Почему так: тест, который проверяет внутренний state, ломается при любом рефакторинге, даже если для пользователя ничего не изменилось. Тест через роли и подписи ломается только тогда, когда реально сломалось поведение. Бонус: поиск по `getByRole` и `getByLabelText` заодно проверяет доступность — если элемент не находится по роли, его не найдёт и скринридер.

Разница в запросах: `getBy` бросает ошибку, если элемента нет; `queryBy` возвращает `null` (для проверки отсутствия); `findBy` ждёт появления элемента.

@@@ react-44 | state, антипаттерн
Почему нельзя вызывать `setState` прямо в теле компонента?
???
Обновление state во время рендера запускает новый рендер, в котором снова вызывается `setState`, — бесконечный цикл (React остановит его ошибкой «Too many re-renders»).

```tsx
function Bad() {
  const [n, setN] = useState(0);
  setN(n + 1); // ✗ бесконечный цикл
  return <p>{n}</p>;
}
```

Похожая ошибка с обработчиком: `onClick={setOpen(true)}` вызывает функцию **сразу при рендере**, а не по клику. Правильно — передать функцию: `onClick={() => setOpen(true)}`.

`setState` вызывают в обработчиках событий и эффектах. Исключение — подстройка state под изменившийся проп с условием, которое перестанет выполняться, но обычно лучше вычислить значение в рендере или сменить `key`.

```tsx
const [prevItems, setPrevItems] = useState(items);
if (items !== prevItems) {   // сработает один раз после смены items
  setPrevItems(items);
  setSelection(null);
}
```

@@@ react-45 | списки, key
Должны ли ключи быть уникальны глобально? Как задать key для Fragment?
???
Ключ должен быть уникален только **среди соседей** в одном списке — в разных списках ключи могут совпадать. React сравнивает ключи только внутри одного родителя.

Если элемент списка — это несколько узлов без обёртки, используют полную форму `Fragment` (короткая `<>` ключ не принимает):

```tsx
import { Fragment } from "react";

{terms.map((t) => (
  <Fragment key={t.id}>
    <dt>{t.word}</dt>
    <dd>{t.meaning}</dd>
  </Fragment>
))}
```

Здесь обёртка `<div>` сломала бы разметку: внутри `<dl>` допустимы только `<dt>` и `<dd>`. `Fragment` группирует элементы, не добавляя узлов в DOM.

Ключ не передаётся в компонент как проп: если id нужен внутри, передай его отдельно.

```tsx
<Item key={item.id} id={item.id} />
```

Ключ ставится на **самый внешний** элемент, который возвращает `map`, — не на вложенный внутри компонента.

@@@ react-46 | refs, хуки
Для чего нужен `useImperativeHandle`?
???
Чтобы через `ref` отдать родителю не весь DOM-узел, а **ограниченный набор методов**:

```tsx
type PlayerHandle = { play(): void; pause(): void };

function VideoPlayer({ ref, src }: { ref?: React.Ref<PlayerHandle>; src: string }) {
  const videoRef = useRef<HTMLVideoElement>(null);
  useImperativeHandle(ref, () => ({
    play: () => videoRef.current?.play(),
    pause: () => videoRef.current?.pause(),
  }), []);
  return <video ref={videoRef} src={src} />;
}

// родитель
const player = useRef<PlayerHandle>(null);
<VideoPlayer ref={player} src="/intro.mp4" />
<button onClick={() => player.current?.play()}>Play</button>
```

Родитель не сможет случайно поменять стили или удалить узел — у него есть только `play` и `pause`.

Использовать редко: фокус, прокрутка, запуск анимации, управление медиа. Всё, что можно выразить пропсами (`isOpen`, `value`), лучше делать пропсами — это декларативно.

Разница подходов: декларативно — «модалка открыта, если `isOpen`», императивно — «открой модалку сейчас». React построен на первом. Императивный API нужен там, где действие нельзя описать состоянием: «поставь фокус», «проиграй с начала».

@@@ react-47 | state, архитектура
Что такое «поднятие состояния»? Как передать данные от ребёнка родителю?
???
Если двум компонентам нужно одно и то же состояние, его переносят в **ближайшего общего родителя** и передают вниз пропсами. Данные идут сверху вниз, а изменения — снизу вверх через колбэки:

```tsx
function Filters() {
  const [query, setQuery] = useState("");
  return (
    <>
      <SearchInput value={query} onChange={setQuery} />
      <Results query={query} />
    </>
  );
}

function SearchInput({ value, onChange }: { value: string; onChange: (v: string) => void }) {
  return <input value={value} onChange={(e) => onChange(e.target.value)} />;
}
```

Ребёнок не знает, где живёт состояние, — он просто вызывает `onChange`. Так у данных один источник правды, и компоненты не рассинхронизируются.

Минус: если общий родитель далеко, приходится прокидывать пропсы через много уровней. Тогда помогают композиция (`children`), контекст или стор.

Ответ на вопрос «как передать данные от ребёнка родителю»: напрямую — никак, данные в React текут только вниз. Родитель передаёт ребёнку функцию, а ребёнок вызывает её с нужными данными.

@@@ react-48 | события, dom
Что такое синтетические события в React?
???
React оборачивает нативные события в свой объект `SyntheticEvent` с одинаковым API во всех браузерах. Оригинал доступен через `e.nativeEvent`.

Особенности, о которых спрашивают:

- **Делегирование.** React не вешает обработчик на каждый элемент: с версии 17 он слушает события на корневом контейнере приложения (до этого — на `document`).
- **Пулинга больше нет.** До React 17 объект события переиспользовался, и после `await` поля были пустыми. Теперь его можно спокойно использовать асинхронно.
- **`onChange`** у инпутов срабатывает на **каждый ввод символа** (как нативный `input`), а не при потере фокуса, как нативный `change`.
- Есть версии для фазы перехвата: `onClickCapture`.
- `onScroll` не всплывает (с React 17), как и в браузере.

`e.stopPropagation()` останавливает всплытие по React-дереву, включая порталы.

Почему переход на корневой контейнер в React 17 важен: на одной странице можно запустить несколько React-приложений разных версий, и их обработчики не мешают друг другу.

@@@ react-49 | производительность, отладка
Как найти причину лишних ререндеров?
???
1. **React DevTools → Profiler.** Запиши взаимодействие и посмотри, какие компоненты рендерились и сколько это заняло. В настройках включи «Record why each component rendered» — Profiler покажет причину: изменился проп, state, контекст или ререндер родителя.
2. **Highlight updates** в настройках DevTools подсвечивает компоненты при каждом рендере — сразу видно, что «мигает» лишнее.
3. **Компонент `<Profiler>`** в коде для замеров:


@@@ react-50 | state, иммутабельность
Почему `items.push(x); setItems(items)` не вызывает ререндер?
???
React сравнивает новое состояние со старым через `Object.is`. `push` меняет **тот же** массив, ссылка не меняется — React решает, что ничего не изменилось, и пропускает рендер.

```tsx
// неправильно
items.push(newItem);
setItems(items);

// правильно — новый массив
setItems([...items, newItem]);
setItems((prev) => [...prev, newItem]); // если опираемся на прошлое значение
```

Шпаргалка без мутаций:

- добавить — `[...arr, x]`;
- удалить — `arr.filter((i) => i.id !== id)`;
- изменить — `arr.map((i) => (i.id === id ? { ...i, done: true } : i))`;
- отсортировать — `arr.toSorted(compare)` (или `[...arr].sort()`);
- объект — `{ ...obj, field: value }`.

Даже если мутация «сработала» из-за другого ререндера, она ломает `memo`, эффекты и StrictMode. Для глубоких структур удобен Immer (`useImmer`).

@@@ react-51 | формы, производительность
Почему большие формы на `useState` тормозят и что делает react-hook-form?
???
Управляемый инпут хранит значение в state: каждый введённый символ — это `setState` и ререндер всей формы. На форме из 30 полей с валидацией это заметно.

**react-hook-form** работает с **неуправляемыми** инпутами: значения живут в DOM, библиотека читает их через `ref` и ререндерит только то, что нужно (например, поле с ошибкой).

```tsx
const schema = z.object({ email: z.email(), age: z.coerce.number().min(18) });

function SignupForm() {
  const { register, handleSubmit, formState: { errors } } = useForm({
    resolver: zodResolver(schema),
  });
  return (
    <form onSubmit={handleSubmit((data) => save(data))}>
      <input {...register("email")} />
      {errors.email && <p>{errors.email.message}</p>}
      <input {...register("age")} />
      <button>Отправить</button>
    </form>
  );
}
```

`register("email")` возвращает `name`, `ref`, `onChange` и `onBlur` — спред подключает поле к библиотеке. `handleSubmit` сам вызывает `preventDefault`, валидирует данные и вызывает функцию, только если всё верно.

Плюсы: меньше ререндеров, валидация через Zod, типы данных выводятся из схемы. Для формы из двух полей хватит обычного `useState` или Actions React 19.

@@@ react-52 | react 19.2, activity
Что такое компонент `<Activity>`?
???
Появился в React 19.2. Позволяет **скрыть** часть интерфейса, не размонтируя её:

```tsx
import { Activity } from "react";

<Activity mode={tab === "chat" ? "visible" : "hidden"}>
  <Chat />
</Activity>
```

Когда `mode="hidden"`:

- компонент скрыт (`display: none`), но его **state и DOM сохраняются** — набранный текст и прокрутка не потеряются;
- эффекты очищаются, как при размонтировании (подписки и таймеры останавливаются), и запускаются снова при показе;
- обновления внутри обрабатываются с низким приоритетом и не мешают видимой части.

Раньше выбор был плохой: `{visible && <Chat />}` теряет состояние, а CSS-скрытие оставляет работать эффекты. Сценарии: вкладки, боковые панели, предварительный рендер экрана, на который пользователь скорее всего перейдёт.

Именно поэтому StrictMode проверяет, что эффекты переживают повторное монтирование: `<Activity>` будет делать это в реальной работе.

@@@ react-53 | react 19
Что ещё нового в React 19, кроме Actions и `use`?
???
- **`ref` — обычный проп** у функциональных компонентов, `forwardRef` больше не нужен.

- **Функции предзагрузки**: `preload`, `preinit`, `prefetchDNS` из `react-dom`.


@@@ react-54 | state, reconciliation, ловушка
Почему состояние не сбрасывается, если в тернарнике рендерить один и тот же компонент?
???
```tsx
{isAnna ? <Counter person="Аня" /> : <Counter person="Боб" />}
```

Переключаем `isAnna` — а счётчик Ани переходит к Бобу. React привязывает состояние к **позиции в дереве и типу компонента**, а не к пропсам. Здесь в одной позиции один и тот же тип `Counter`, значит, это «тот же» компонент — React просто обновляет пропсы.

Как сделать состояния раздельными:

```tsx
// разные ключи — разные экземпляры
{isAnna ? <Counter key="anna" person="Аня" /> : <Counter key="bob" person="Боб" />}

// или разные позиции
{isAnna && <Counter person="Аня" />}
{!isAnna && <Counter person="Боб" />}
```

Во втором варианте у React две отдельные «ячейки»: в одной `Counter` или `false`, в другой — `false` или `Counter`. При переключении один компонент размонтируется, другой монтируется заново.

Обратный случай: если обернуть компонент в другой тег (`<div>` ↔ `<section>`) на том же месте, состояние всего поддерева сбросится.

@@@ react-55 | компоненты, ловушка
Можно ли объявлять компонент внутри другого компонента?
???
Нет. На каждом рендере родителя создаётся **новая функция** — для React это новый тип компонента:

```tsx
function Form() {
  const [text, setText] = useState("");
  function Field() { // новый тип при каждом рендере
    return <input value={text} onChange={(e) => setText(e.target.value)} />;
  }
  return <Field />;
}
```

Каждый символ → ререндер `Form` → новый `Field` → React размонтирует старый инпут и создаёт новый. Итог: **фокус теряется после каждой буквы**, состояние внутри `Field` сбрасывается, лишняя работа с DOM.

Правильно — объявлять компоненты на верхнем уровне модуля и передавать данные пропсами:

```tsx
function Field({ value, onChange }: FieldProps) {
  return <input value={value} onChange={(e) => onChange(e.target.value)} />;
}
```

Вызывать функцию, которая возвращает JSX (`{renderField()}`), можно — это не компонент, а часть разметки родителя.

@@@ react-56 | безопасность, xss
Когда в React возможен XSS, если он экранирует текст?
???
React экранирует всё, что вставлено в JSX как текст, — `<b>{comment}</b>` безопасен. Опасны места, где данные становятся **кодом или разметкой**:

- `dangerouslySetInnerHTML={{ __html: html }}` — вставляет HTML как есть. Странное имя выбрано специально, чтобы такой код бросался в глаза на ревью;
- `href` и `src` из пользовательских данных: React 19 блокирует `javascript:` в атрибутах, но `data:`-ссылки и открытые редиректы на чужие сайты — нет, а старые версии React такие ссылки пропускали;
- прямая работа с DOM: `ref.current.innerHTML = …`;
- данные в `<script>` при SSR (например, `JSON.stringify` состояния без экранирования `</script>`).

```tsx
import DOMPurify from "dompurify";

<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />

const safeHref = /^https?:\/\//.test(url) ? url : "#";
```

Для Markdown используют `react-markdown` без плагина сырого HTML — он строит React-элементы, а не HTML-строку. Так устроено и это приложение.

История: React 16.9 начал предупреждать о `javascript:` в `href`, а React 19 подменяет такой адрес безопасной заглушкой, которая бросает ошибку. Проверять URL из пользовательских данных всё равно стоит самому — по белому списку протоколов.

@@@ react-57 | эффекты, cleanup
Когда вызывается функция очистки эффекта?
???
1. **Перед повторным запуском эффекта**, когда изменились зависимости. Очистка получает значения **прошлого** рендера, а потом эффект запускается с новыми.
2. **При размонтировании** компонента.
3. В dev со StrictMode — ещё один лишний цикл «эффект → очистка → эффект» при монтировании.

```tsx
useEffect(() => {
  const conn = connect(roomId);
  return () => conn.disconnect(); // отключиться от СТАРОЙ комнаты
}, [roomId]);
```

Смена `roomId` с `"a"` на `"b"`: рендер с `"b"` → очистка отключается от `"a"` → эффект подключается к `"b"`.

Что обычно чистят: подписки, `addEventListener`, таймеры, `AbortController` для запросов, сторонние виджеты. Если эффект что-то «включает», очистка должна это «выключить» — тогда компонент можно безопасно смонтировать хоть дважды.

@@@ react-58 | эффекты, async
Почему функцию эффекта нельзя сделать `async`?
???
`useEffect` ждёт, что функция вернёт **ничего или функцию очистки**. `async`-функция всегда возвращает промис — React не сможет вызвать очистку, и TypeScript выдаст ошибку.

Правильно — объявить async-функцию внутри и не забыть про отмену:

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    try {
      const res = await fetch(`/api/users/${id}`, { signal: controller.signal });
      setUser(await res.json());
    } catch (e) {
      if ((e as Error).name !== "AbortError") setError(e as Error);
    }
  }

  load();
  return () => controller.abort();
}, [id]);
```

Отмена защищает от гонки: ответ на старый `id` не перезапишет данные нового. На практике загрузку данных лучше отдать TanStack Query, SWR или серверным компонентам — там это уже решено.

@@@ react-59 | state, производительность
Что произойдёт, если вызвать `setState` с тем же значением?
???
React сравнит его с текущим через `Object.is`. Если значения равны, он **не будет** перерисовывать детей и запускать эффекты (bail out).

```tsx
const [count, setCount] = useState(0);
setCount(0); // ничего не произойдёт

const [user, setUser] = useState({ name: "Аня" });
setUser({ name: "Аня" }); // ререндер: новый объект — новая ссылка
```

Нюанс: иногда React всё же вызывает функцию компонента ещё раз, прежде чем понять, что результат не изменился, но дочерние компоненты при этом не трогает. Поэтому компоненты должны быть чистыми.

Практический вывод: для объектов и массивов не создавай новый объект, если данные не поменялись. Например, `setFilters((f) => (f.page === 1 ? f : { ...f, page: 1 }))` — вернуть тот же `f`, чтобы избежать лишнего рендера.

@@@ react-60 | react 19, формы
Как сделать форму на `useActionState` с ошибками валидации?
???
```tsx
"use client";
import { useActionState } from "react";

type State = { error?: string; email?: string; ok?: boolean };

async function subscribe(prev: State, formData: FormData): Promise<State> {
  const email = String(formData.get("email") ?? "");
  if (!email.includes("@")) return { error: "Некорректный email", email };
  await api.subscribe(email);
  return { ok: true };
}

export function SubscribeForm() {
  const [state, formAction, isPending] = useActionState(subscribe, {});
  return (
    <form action={formAction}>
      <input name="email" defaultValue={state.email} />
      <button disabled={isPending}>{isPending ? "Отправляю…" : "Подписаться"}</button>
      {state.error && <p role="alert">{state.error}</p>}
      {state.ok && <p>Готово!</p>}
    </form>
  );
}
```

- Action получает **предыдущее состояние** и `FormData`, а возвращает новое состояние.
- `isPending` — пока action выполняется; отдельный `useState` для загрузки не нужен.
- Ловушка: после action React **сбрасывает** неуправляемые поля формы. Чтобы при ошибке пользователь не терял ввод, верни значения в state и подставь их в `defaultValue`.
- В Next.js `subscribe` может быть Server Action — тогда форма работает даже до загрузки JS.

`role="alert"` заставляет скринридер сразу зачитать появившуюся ошибку.

@@@ react-61 | рендер, dom
Что делает `flushSync` и когда он нужен?
???
Обычно React группирует обновления и применяет их к DOM чуть позже. `flushSync` заставляет выполнить обновление **синхронно**, прямо сейчас:

```tsx
import { flushSync } from "react-dom";

function addMessage(text: string) {
  flushSync(() => {
    setMessages((m) => [...m, text]);
  });
  // DOM уже обновлён — новое сообщение есть в списке
  listRef.current?.lastElementChild?.scrollIntoView({ behavior: "smooth" });
}
```

Без `flushSync` в момент вызова `scrollIntoView` нового элемента ещё нет в DOM, и прокрутка уедет к предпоследнему.

Когда нужен: прокрутка или фокус на только что добавленном элементе, интеграция со сторонним кодом, которому нужен актуальный DOM, и `beforeprint`.

Это дорогой инструмент: он отключает батчинг и может ухудшить производительность. Сначала проверь, не решается ли задача эффектом или ref-колбэком.
