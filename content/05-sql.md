@@@ sql-01 | join
Какие бывают JOIN?
???
- `INNER JOIN` — только строки с совпадением в обеих таблицах.
- `LEFT JOIN` — все строки левой + совпадения справа (иначе `NULL`).
- `RIGHT JOIN` — наоборот.
- `FULL JOIN` — все строки обеих.
- `CROSS JOIN` — декартово произведение.

```sql
-- пользователи без заказов
SELECT u.*
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

@@@ sql-02 | группировка
Чем `WHERE` отличается от `HAVING`?
???
`WHERE` фильтрует **строки до** группировки. `HAVING` — **группы после** `GROUP BY`, и только в нём можно использовать агрегаты:

```sql
SELECT user_id, count(*) AS orders
FROM orders
WHERE created_at > now() - interval '30 days'  -- отбросить старые строки
GROUP BY user_id
HAVING count(*) >= 5;                          -- оставить активных
```

`WHERE count(*) > 5` — ошибка: на этапе `WHERE` групп ещё нет.

Совет для производительности: всё, что можно отфильтровать по строкам, пиши в `WHERE`. Тогда в группировку попадёт меньше данных, а условие сможет использовать индекс.

@@@ sql-03 | основы
В каком порядке логически выполняется `SELECT`?
???
`FROM / JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT / OFFSET`.

Из этого порядка следуют частые ошибки:

- алиас из `SELECT` нельзя использовать в `WHERE` — он ещё не вычислен; в `ORDER BY` можно (в PostgreSQL ещё и в `GROUP BY`);
- агрегаты нельзя писать в `WHERE`, только в `HAVING`;
- оконные функции считаются на этапе `SELECT`, поэтому фильтровать по ним можно только во внешнем запросе или CTE.

```sql
SELECT price * qty AS total FROM items
WHERE total > 100;        -- ошибка
-- нужно: WHERE price * qty > 100
```

Это **логический** порядок: планировщик физически может выполнять шаги иначе, если результат тот же.

@@@ sql-04 | индексы
Что такое индекс и как работает B-tree?
???
Отдельная структура данных, которая ускоряет поиск ценой места на диске и замедления записи.

**B-tree** (по умолчанию в PostgreSQL) — сбалансированное дерево отсортированных ключей. Поиск за O(log n); подходит для `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, `LIKE 'abc%'`.

Другие типы: Hash (только `=`), GIN (массивы, JSONB, полнотекстовый поиск), GiST (геоданные), BRIN (огромные упорядоченные таблицы).

@@@ sql-05 | индексы, производительность
Почему запрос не использует индекс?
???
- Функция над колонкой: `WHERE lower(email) = …` — нужен индекс по выражению.
- `LIKE '%abc'` — начало шаблона неизвестно.
- Несовпадение типов, неявное приведение.
- Низкая селективность: выбирается большая часть таблицы, и seq scan дешевле.
- Индекс `(a, b)`, а фильтр только по `b`.
- Устаревшая статистика — поможет `ANALYZE`.

Проверяй через `EXPLAIN ANALYZE`.

@@@ sql-06 | индексы
Как порядок колонок влияет на составной индекс?
???
Индекс `(a, b, c)` отсортирован сначала по `a`, потом по `b` — как телефонный справочник по фамилии и имени. Он работает для фильтров по `a`, `a + b`, `a + b + c` (левый префикс), но не по одному `b`.

Сначала ставят колонки с равенством, потом — с диапазоном и сортировкой:

```sql
CREATE INDEX ON orders (user_id, created_at DESC);
-- быстро: WHERE user_id = 1 ORDER BY created_at DESC LIMIT 20
```

@@@ sql-07 | производительность, explain
Как читать `EXPLAIN ANALYZE`?
???
Показывает план и **реальное** время каждого узла. На что смотреть:

- `Seq Scan` по большой таблице там, где ждёшь `Index Scan`;
- большая разница между `rows` (оценка) и `actual rows` — устаревшая статистика;
- `Nested Loop` на больших входах;
- `Sort` с записью на диск (`external merge`);
- самый дорогой узел по `actual time`.

`EXPLAIN` без `ANALYZE` запрос не выполняет.

@@@ sql-08 | ключи, основы
Что такое первичный и внешний ключ?
???
**Primary key** уникально идентифицирует строку: `UNIQUE + NOT NULL`, индексируется автоматически.

**Foreign key** ссылается на ключ другой таблицы и гарантирует целостность: нельзя сослаться на несуществующую строку. Поведение при удалении: `ON DELETE CASCADE | SET NULL | RESTRICT`.

Внешний ключ в PostgreSQL **не индексируется сам** — индекс по `user_id` обычно нужно создать вручную.

@@@ sql-09 | проектирование
Что такое нормализация? Кратко про 1НФ, 2НФ, 3НФ.
???
Устранение дублирования и аномалий обновления.

- **1НФ** — атомарные значения, без повторяющихся групп (никаких «тегов через запятую»).
- **2НФ** — 1НФ + каждый неключевой атрибут зависит от **всего** составного ключа.
- **3НФ** — 2НФ + нет транзитивных зависимостей: неключевые поля не зависят от других неключевых.

Денормализация — осознанное дублирование ради скорости чтения.

@@@ sql-10 | транзакции
Что такое транзакция и ACID?
???
Транзакция — группа операций по принципу «всё или ничего».

- **Atomicity** — применяются либо все изменения, либо ни одного.
- **Consistency** — переход между корректными состояниями, ограничения соблюдены.
- **Isolation** — параллельные транзакции не мешают друг другу (в рамках уровня изоляции).
- **Durability** — после `COMMIT` данные переживут сбой (WAL).

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

@@@ sql-11 | транзакции, изоляция
Какие уровни изоляции транзакций есть и какие аномалии они допускают?
???
Аномалии: dirty read, non-repeatable read, phantom read, serialization anomaly.

- **Read Uncommitted** — в PostgreSQL работает как Read Committed.
- **Read Committed** (по умолчанию в PG) — каждый запрос видит данные, закоммиченные на момент **его** начала.
- **Repeatable Read** — снимок на начало транзакции; в PG фантомов тоже нет.
- **Serializable** — как будто транзакции шли по очереди. Возможны ошибки сериализации, транзакцию нужно повторить.

@@@ sql-12 | postgres, mvcc
Что такое MVCC в PostgreSQL и зачем нужен `VACUUM`?
???
**Multi-Version Concurrency Control**: `UPDATE` не перезаписывает строку, а создаёт новую версию. Старая остаётся для транзакций, которые её ещё видят. Читатели не блокируют писателей, и наоборот.

Мёртвые версии копятся (bloat). `VACUUM` (обычно autovacuum) освобождает место для повторного использования, обновляет статистику и не даёт переполниться счётчику транзакций.

@@@ sql-13 | производительность, orm
Что такое проблема N+1?
???
Один запрос за списком + по запросу на каждый элемент:

```ts
const posts = await db.post.findMany(); // 1 запрос
for (const p of posts) {
  // + N запросов
  p.author = await db.user.findUnique({ where: { id: p.authorId } });
}
```

Решение: JOIN, один запрос `WHERE id IN (…)`, `include` в ORM, DataLoader (батчинг) в GraphQL.

@@@ sql-14 | оконные функции
Что такое оконные функции? Приведи пример.
???
Считают по набору строк, связанных с текущей, **не схлопывая** строки — в отличие от `GROUP BY`:

```sql
-- три последних заказа каждого пользователя
SELECT *
FROM (
  SELECT o.*,
         row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM orders o
) t
WHERE rn <= 3;
```

Ещё: `rank`, `dense_rank`, `lag` / `lead`, `sum(…) OVER (ORDER BY …)` — накопительный итог.

@@@ sql-15 | оконные функции
Чем отличаются `ROW_NUMBER`, `RANK` и `DENSE_RANK`?
???
Все три нумеруют строки внутри окна по `ORDER BY`, но по-разному ведут себя при равных значениях. Для 100, 90, 90, 80:

- `row_number` → 1, 2, 3, 4 — всегда уникальный, порядок среди равных случаен
- `rank` → 1, 2, 2, 4 — равные делят место, после них пропуск
- `dense_rank` → 1, 2, 2, 3 — без пропусков

```sql
SELECT name, salary,
       dense_rank() OVER (ORDER BY salary DESC) AS place
FROM employees;
```

Что выбрать: «ровно N строк на группу» (последний заказ, топ-3) — `row_number`; «все, кто на 2-м месте» или «вторая по величине зарплата» — `dense_rank`; места как в спорте — `rank`.

@@@ sql-16 | cte
Что такое CTE (`WITH`)? А рекурсивный CTE?
???
Именованный подзапрос для читаемости:

```sql
WITH active AS (
  SELECT * FROM users WHERE last_seen > now() - interval '7 days'
)
SELECT count(*) FROM active;
```

Рекурсивный — для деревьев (категории, комментарии, оргструктура):

```sql
WITH RECURSIVE tree AS (
  SELECT id, parent_id, name FROM categories WHERE id = 1
  UNION ALL
  SELECT c.id, c.parent_id, c.name
  FROM categories c
  JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree;
```

@@@ sql-17 | основы
`UNION` против `UNION ALL`?
???
`UNION` объединяет результаты и **убирает дубликаты** — для этого нужна сортировка или хеширование всего результата, это дороже.

`UNION ALL` просто склеивает строки. Если дублей быть не может (например, данные из разных таблиц с разными id) или они нужны — бери `UNION ALL`.

```sql
SELECT email FROM customers
UNION ALL
SELECT email FROM subscribers;
```

Правила: число колонок и их типы должны совпадать, имена колонок берутся из первого запроса, `ORDER BY` пишется один раз в конце и сортирует общий результат.

Родственники: `INTERSECT` — строки, которые есть в обоих результатах, `EXCEPT` — есть в первом, но нет во втором.

@@@ sql-18 | основы
`DELETE`, `TRUNCATE` и `DROP` — в чём разница?
???
- `DELETE` удаляет строки (можно с `WHERE`), построчно, с триггерами. Медленно на больших объёмах.
- `TRUNCATE` мгновенно очищает всю таблицу без построчной обработки, может сбросить счётчики (`RESTART IDENTITY`).
- `DROP` удаляет саму таблицу вместе со структурой.

В PostgreSQL все три транзакционны — их можно откатить.

@@@ sql-19 | null, ловушка
Какие подводные камни у `NULL`?
???
`NULL` — это «неизвестно». Любое сравнение с ним даёт `NULL`, а не true/false, а `WHERE` пропускает только true.

- `WHERE x = NULL` ничего не найдёт → нужно `IS NULL`.
- `WHERE status <> 'done'` не вернёт строки, где `status IS NULL`.
- `NOT IN (подзапрос, где есть NULL)` вернёт пустоту: `x <> NULL` — неизвестно.
- Агрегаты (`sum`, `avg`, `count(col)`) пропускают `NULL`, а `sum` по пустому набору даёт `NULL`, а не 0.
- `'a' || NULL` → `NULL`.

```sql
SELECT coalesce(sum(amount), 0) FROM payments WHERE user_id = 1;
SELECT * FROM tasks WHERE status IS DISTINCT FROM 'done';
```

Помогают `COALESCE`, `IS DISTINCT FROM` и `NOT EXISTS` вместо `NOT IN`.

@@@ sql-20 | агрегаты
`COUNT(*)`, `COUNT(column)` и `COUNT(DISTINCT column)`?
???
- `count(*)` — число строк;
- `count(col)` — число строк, где `col` **не** `NULL`;
- `count(DISTINCT col)` — число уникальных непустых значений.

Ловушка с `LEFT JOIN`: у пользователя без заказов всё равно есть одна строка (с `NULL` в колонках заказа), поэтому `count(*)` даст 1 вместо 0.

```sql
SELECT u.id, count(o.id) AS orders   -- не count(*)
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;
```

Миф: `count(1)` быстрее `count(*)`. В PostgreSQL это одно и то же, а `count(*)` даже чуть понятнее планировщику. Точный `count(*)` по большой таблице медленный (MVCC требует проверить видимость строк), поэтому для «примерно 1,2 млн» берут оценку из `pg_class.reltuples`.

@@@ sql-21 | подзапросы
`EXISTS` или `IN`? Подзапрос или `JOIN`?
???
`EXISTS` проверяет наличие хотя бы одной строки и останавливается на первой, корректно работает с `NULL`. `NOT IN` ломается, если в подзапросе есть `NULL` — используй `NOT EXISTS`.

Планировщик PostgreSQL часто превращает `IN` и `EXISTS` в одинаковый semi-join.

`JOIN` нужен, если требуются колонки второй таблицы. Если нужна только проверка наличия — `EXISTS`: `JOIN` может размножить строки.

@@@ sql-22 | пагинация, производительность
OFFSET-пагинация или keyset (курсорная)?
???
`LIMIT 20 OFFSET 10000` заставляет БД прочитать и выбросить 10 000 строк: медленно на дальних страницах, а при вставках строки «съезжают».

Keyset продолжает от последнего ключа:

```sql
SELECT * FROM posts
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

С индексом быстро на любой глубине, но перейти на произвольную страницу нельзя. Идеально для бесконечной ленты.

@@@ sql-23 | postgres, upsert
Как сделать «вставить или обновить» (upsert) в PostgreSQL?
???
```sql
INSERT INTO stats (user_id, views)
VALUES (1, 1)
ON CONFLICT (user_id)
DO UPDATE SET views = stats.views + EXCLUDED.views;
```

- Нужен уникальный индекс или ограничение на колонке конфликта — по нему PostgreSQL понимает, что строка «уже есть».
- `EXCLUDED` — строка, которую пытались вставить.
- `ON CONFLICT DO NOTHING` — просто пропустить дубликат.
- Можно добавить условие: `DO UPDATE SET … WHERE stats.updated_at < EXCLUDED.updated_at`.

Главное преимущество перед «SELECT, потом INSERT или UPDATE» — **атомарность**: два параллельных запроса не создадут дубль и не упадут на уникальном ключе. Начиная с PostgreSQL 15 есть ещё `MERGE` для сложных сценариев синхронизации.

@@@ sql-24 | postgres, jsonb
`json` или `jsonb` в PostgreSQL? Когда их использовать?
???
`json` хранит текст как есть: с пробелами, порядком ключей и дублями. `jsonb` — разобранный бинарный формат: быстрее запросы, GIN-индексы, операторы `@>`, `?`, `->>`. Почти всегда выбирают `jsonb`.

Подходит для гибких и редко запрашиваемых атрибутов. Поля, по которым часто фильтруют и джойнят, лучше держать в обычных колонках.

```sql
SELECT * FROM products WHERE attrs @> '{"color": "red"}';
```

@@@ sql-25 | транзакции, блокировки
Что такое deadlock и как его избежать?
???
Две транзакции ждут друг друга: T1 заблокировала строку A и ждёт B, а T2 заблокировала B и ждёт A. PostgreSQL обнаружит взаимоблокировку и отменит одну транзакцию с ошибкой.

Как избегать:

- блокировать ресурсы в одном порядке (например, по возрастанию id);
- держать транзакции короткими;
- повторять транзакцию при ошибке.

`SELECT … FOR UPDATE` — явная блокировка строк перед изменением.

@@@ sql-26 | безопасность
Что такое SQL-инъекция и как защититься?
???
Подстановка пользовательского ввода прямо в текст запроса: `"… WHERE name = '" + name + "'"` с `name = "' OR 1=1 --"`.

Защита — **параметризованные запросы**: значения передаются отдельно от SQL (`WHERE name = $1`). ORM делают это сами, опасны сырые запросы со строковой интерполяцией. Плюс минимальные права у пользователя БД.

@@@ sql-27 | join, ловушка
Почему `LEFT JOIN` превращается во `INNER JOIN`, если добавить условие в `WHERE`?
???
```sql
-- ✗ пользователи без оплаченных заказов пропадут
SELECT u.name, o.id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';

-- ✓ условие на правую таблицу — в ON
SELECT u.name, o.id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid';
```

У пользователей без подходящих заказов все поля `o` равны `NULL`, а `NULL = 'paid'` не даёт true — `WHERE` выбрасывает эти строки. Условие в `ON` только решает, какие заказы присоединить, и сохраняет всех пользователей.

@@@ sql-28 | join
Что такое self join? Пример.
???
Соединение таблицы **с самой собой** — для иерархий и сравнения строк одной таблицы:

```sql
-- сотрудник и его руководитель
SELECT e.name AS employee, m.name AS manager
FROM users e
LEFT JOIN users m ON m.id = e.manager_id;
```

Алиасы (`e`, `m`) обязательны, чтобы различать две копии. `LEFT` нужен, чтобы не потерять верхнего руководителя, у которого `manager_id IS NULL`.

@@@ sql-29 | postgres, distinct on
Как в PostgreSQL выбрать последний заказ каждого пользователя?
???
`DISTINCT ON` оставляет первую строку в каждой группе согласно `ORDER BY`:

```sql
SELECT DISTINCT ON (user_id) user_id, id, created_at
FROM orders
ORDER BY user_id, created_at DESC;
```

`ORDER BY` должен начинаться с тех же выражений, что в `DISTINCT ON`. Переносимый вариант для любой СУБД — `row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC)` и фильтр `rn = 1`.

@@@ sql-30 | задача, оконные функции
Как найти вторую по величине зарплату?
???
```sql
-- 1) через DISTINCT + OFFSET
SELECT DISTINCT salary
FROM salaries
ORDER BY salary DESC
OFFSET 1 LIMIT 1;

-- 2) через dense_rank — заодно видно, у кого она
SELECT emp, salary
FROM (
  SELECT emp, salary, dense_rank() OVER (ORDER BY salary DESC) AS r
  FROM salaries
) t
WHERE r = 2;
```

Ловушка: без `DISTINCT` (или с `row_number` вместо `dense_rank`) при двух одинаковых максимальных зарплатах «второй» окажется та же максимальная.

@@@ sql-31 | задача, дубликаты
Как найти и удалить дубликаты, оставив одну запись?
???
Найти:

```sql
SELECT email, count(*)
FROM emails
GROUP BY email
HAVING count(*) > 1;
```

Удалить, оставив строку с наименьшим `id` (PostgreSQL):

```sql
DELETE FROM emails a
USING emails b
WHERE a.email = b.email
  AND a.id > b.id;
```

После чистки — уникальный индекс `CREATE UNIQUE INDEX ON emails (email)`, чтобы дубли не появились снова.

@@@ sql-32 | null, выражения
Что делают `COALESCE`, `NULLIF` и `CASE`?
???
- `COALESCE(a, b, c)` — первое не-`NULL` значение: `COALESCE(nickname, name, 'Аноним')`.
- `NULLIF(a, b)` — `NULL`, если `a = b`, иначе `a`. Классика — защита от деления на ноль: `total / NULLIF(count, 0)` вернёт `NULL` вместо ошибки.
- `CASE` — условие внутри запроса:

```sql
SELECT name,
       CASE WHEN manager_id IS NULL THEN 'boss' ELSE 'staff' END AS role
FROM users;
```

@@@ sql-33 | индексы, postgres
Что такое частичный индекс, индекс по выражению и покрывающий индекс?
???
```sql
-- частичный: индексирует только нужные строки — меньше и быстрее
CREATE INDEX ON orders (user_id) WHERE status = 'new';

-- по выражению: для поиска без учёта регистра
CREATE INDEX ON users (lower(email));
-- используется запросом WHERE lower(email) = lower($1)

-- покрывающий: INCLUDE хранит доп. колонки в индексе,
-- запрос может обойтись без чтения таблицы (index-only scan)
CREATE INDEX ON orders (user_id) INCLUDE (total);
```

Частичный индекс используется, только если условие запроса совпадает с условием индекса или следует из него.

@@@ sql-34 | postgres, типы
`SERIAL` или `GENERATED AS IDENTITY`? Что выбрать для первичного ключа?
???
`GENERATED ... AS IDENTITY` — стандарт SQL, рекомендуемый в современном PostgreSQL. `SERIAL` — старый способ: это обычный `int` + отдельная последовательность, с ней проще ошибиться при правах и копировании таблиц.

```sql
CREATE TABLE users (
  id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text
);
INSERT INTO users (id, name) VALUES (5, 'x');
-- ошибка: cannot insert a non-DEFAULT value into column "id"
```

`ALWAYS` защищает от ручной вставки id, `BY DEFAULT` разрешает её. Для распределённых систем и публичных идентификаторов часто берут `uuid`.

@@@ sql-35 | postgres, представления
Чем обычное представление (VIEW) отличается от материализованного?
???
- **VIEW** — сохранённый запрос. Данные не хранит, при каждом обращении выполняет запрос заново: всегда актуально, но не быстрее исходного запроса.
- **MATERIALIZED VIEW** — результат запроса **сохранён на диск**: читается быстро, можно индексировать, но устаревает, пока его не обновят.

```sql
CREATE MATERIALIZED VIEW sales_by_user AS
SELECT user_id, sum(total) AS total FROM orders GROUP BY user_id;

REFRESH MATERIALIZED VIEW sales_by_user;
-- без блокировки чтения, но нужен уникальный индекс:
CREATE UNIQUE INDEX ON sales_by_user (user_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY sales_by_user;
```

Подходит для отчётов и дашбордов, где допустимо небольшое отставание.

@@@ sql-36 | транзакции, блокировки
Оптимистичная или пессимистичная блокировка — в чём разница?
???
**Пессимистичная** — заблокировать строку заранее, другие ждут:

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

**Оптимистичная** — не блокировать, а при записи проверить, что строку никто не изменил (колонка `version`):

```sql
UPDATE accounts
SET balance = 50, version = version + 1
WHERE id = 1 AND version = 1;
-- 0 обновлённых строк = кто-то успел раньше → перечитать и повторить
```

Пессимистичная — при частых конфликтах и коротких транзакциях. Оптимистичная — когда конфликты редки, а держать блокировку долго нельзя (например, пока пользователь редактирует форму).

@@@ sql-37 | postgres, типы
`text`, `varchar(n)` или `char(n)` в PostgreSQL?
???
В PostgreSQL между ними **нет разницы в скорости**. `text` и `varchar` без ограничения — одно и то же по сути, `varchar(n)` лишь добавляет проверку длины.

`char(n)` дополняет строку пробелами до `n` и ведёт себя неочевидно (хвостовые пробелы игнорируются в сравнениях) — его почти не используют.

Практика: `text`, а ограничение длины, если нужно, — через `CHECK (char_length(name) <= 100)` или `varchar(n)`.

@@@ sql-38 | postgres, даты
`timestamp` или `timestamptz`?
???
Почти всегда `timestamptz` (`timestamp with time zone`). Он хранит **момент времени** (внутри — UTC) и при выводе переводит в часовой пояс сессии.

`timestamp` хранит «время на стенных часах» без пояса и **молча отбрасывает** смещение:

```sql
SET TIME ZONE 'Europe/Moscow';
SELECT '2026-01-01 12:00:00+00'::timestamptz; -- 2026-01-01 15:00:00+03
SELECT '2026-01-01 12:00:00+00'::timestamp;   -- 2026-01-01 12:00:00 (пояс потерян)
```

С `timestamp` события из разных часовых поясов становится невозможно корректно сравнить.

@@@ sql-39 | группировка, основы
Почему нельзя выбрать колонку, которой нет в `GROUP BY`?
???
После группировки от каждой группы остаётся **одна строка**. Если в группе пять заказов с разными датами, неясно, какую дату показать:

```sql
SELECT user_id, created_at, count(*)  -- ошибка: created_at не сгруппирован
FROM orders
GROUP BY user_id;
```

В `SELECT` можно указывать только колонки из `GROUP BY` и агрегаты: `max(created_at)`, `count(*)`, `string_agg(...)`.

Исключение в PostgreSQL: если сгруппировать по **первичному ключу**, можно брать остальные колонки той же таблицы — они однозначно определяются ключом:

```sql
SELECT u.id, u.name, count(o.id)
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;  -- u.name можно, потому что u.id — первичный ключ
```

MySQL в старых режимах разрешал любые колонки и возвращал случайное значение из группы — источник тихих багов.

@@@ sql-40 | связи, ограничения
Что делают `ON DELETE CASCADE`, `SET NULL` и `RESTRICT`?
???
Определяют, что случится с дочерними строками, когда удаляют родительскую:

```sql
CREATE TABLE comments (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  post_id bigint NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  user_id bigint REFERENCES users(id) ON DELETE SET NULL,
  rating  int CHECK (rating BETWEEN 1 AND 5)
);
```

- `CASCADE` — удалить детей вместе с родителем (комментарии вместе с постом);
- `SET NULL` — оставить детей, обнулив ссылку (комментарий остаётся, автор «удалён»);
- `RESTRICT` / `NO ACTION` (по умолчанию) — запретить удаление, пока есть дети. `NO ACTION` можно отложить до конца транзакции, `RESTRICT` проверяется сразу.

`CHECK` — произвольное условие на значения строки.

Ловушка, о которой часто спрашивают: PostgreSQL **не создаёт индекс** на колонке внешнего ключа автоматически. Без индекса на `comments.post_id` каждое удаление поста будет сканировать всю таблицу комментариев.

@@@ sql-41 | связи, проектирование
Как в таблицах реализуются связи один-к-одному, один-ко-многим и многие-ко-многим?
???
**Один-ко-многим** — внешний ключ на стороне «многих»: у заказа есть `user_id`, у пользователя много заказов.

**Один-к-одному** — тот же внешний ключ, но с `UNIQUE`, чтобы на одного родителя была максимум одна строка:

```sql
CREATE TABLE profiles (
  user_id bigint PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  bio text
);
```

**Многие-ко-многим** — отдельная связующая таблица с двумя внешними ключами и составным первичным ключом:

```sql
CREATE TABLE user_roles (
  user_id bigint REFERENCES users(id) ON DELETE CASCADE,
  role_id bigint REFERENCES roles(id) ON DELETE CASCADE,
  granted_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, role_id)
);
```

Составной ключ не даёт выдать одну роль дважды. В связующую таблицу удобно класть данные о самой связи: дату, кто выдал, порядок.

@@@ sql-42 | индексы, производительность
Почему нельзя просто повесить индекс на каждую колонку?
???
Индекс ускоряет чтение, но у него есть цена:

- **Медленнее запись.** Каждый `INSERT`, `UPDATE` и `DELETE` обновляет все индексы таблицы. Десять индексов — десять дополнительных структур на каждую вставку.
- **Место на диске и в памяти.** Индексы конкурируют с данными за кэш, и в памяти помещается меньше полезного.
- **Нет HOT-обновлений.** Если меняется проиндексированная колонка, PostgreSQL не может обновить строку «на месте» — таблица и индексы разбухают быстрее.
- **Бесполезность при низкой селективности.** Индекс по `is_active`, где 95% строк `true`, планировщик просто проигнорирует.

Как правильно: индексы под **реальные запросы** (`WHERE`, `JOIN`, `ORDER BY`), составные — в нужном порядке колонок, проверка через `EXPLAIN ANALYZE`. Неиспользуемые индексы находят по `pg_stat_user_indexes`, где `idx_scan = 0`.

@@@ sql-43 | индексы, postgres
Какие типы индексов есть в PostgreSQL?
???
- **B-tree** (по умолчанию) — равенство, диапазоны (`<`, `BETWEEN`), сортировка, `LIKE 'abc%'`. Подходит в 90% случаев.
- **Hash** — только равенство `=`. Бывает компактнее B-tree для длинных значений, но не умеет диапазоны и сортировку.
- **GIN** — «обратный» индекс для значений, внутри которых много элементов: массивы (`@>`), `jsonb`, полнотекстовый поиск, поиск по подстроке через `pg_trgm`.
- **GiST** — геометрия и PostGIS, диапазоны (`tstzrange`), поиск ближайших соседей, exclusion constraints («бронирования не пересекаются»).
- **BRIN** — очень маленький индекс для огромных таблиц, где данные физически упорядочены: логи и события по времени вставки.

```sql
CREATE INDEX ON products USING gin (tags);           -- WHERE tags @> '{sale}'
CREATE INDEX ON events USING brin (created_at);       -- миллиарды строк логов
```

@@@ sql-44 | поиск, индексы
Как быстро искать по подстроке, если `LIKE '%текст%'` не использует индекс?
???
B-tree хранит значения отсортированными, поэтому умеет искать только по **началу** строки (`LIKE 'abc%'`). Шаблон с `%` в начале требует проверить каждую строку.

**Вариант 1 — триграммы** (`pg_trgm`). Строка разбивается на тройки символов, GIN-индекс по ним ускоряет `LIKE` и `ILIKE` с любым положением подстроки:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX products_name_trgm ON products USING gin (name gin_trgm_ops);

SELECT * FROM products WHERE name ILIKE '%телефон%';
```

Ещё умеет нечёткий поиск с опечатками: `similarity(name, 'тилефон')`.

**Вариант 2 — полнотекстовый поиск.** Слова приводятся к основе (стемминг), поэтому по запросу «кошки» найдутся «кошка», «кошку», «кошкой». Стеммер работает по правилам, а не по словарю: форму с беглой гласной «кошек» он не свяжет — для этого подключают словари (hunspell).

```sql
CREATE INDEX ON posts USING gin (to_tsvector('russian', body));

SELECT * FROM posts
WHERE to_tsvector('russian', body) @@ plainto_tsquery('russian', 'кошки');
```

Для сложного поиска с ранжированием, фасетами и подсказками берут Elasticsearch или Meilisearch.

@@@ sql-45 | оконные функции
Как посчитать нарастающий итог и разницу с предыдущей строкой?
???
Оконные функции с `ORDER BY` внутри `OVER`:

```sql
SELECT
  day,
  revenue,
  sum(revenue) OVER (ORDER BY day) AS running_total,
  revenue - lag(revenue) OVER (ORDER BY day) AS diff,
  avg(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg_7d
FROM daily_revenue;
```

- `sum(...) OVER (ORDER BY day)` — сумма от первой строки до текущей;
- `lag(col)` — значение из предыдущей строки (`lead` — из следующей); для первой строки — `NULL`;
- `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` — скользящее окно из 7 строк, например среднее за неделю.

Ловушка: рамка по умолчанию — `RANGE`, а не `ROWS`. Строки с одинаковым значением `day` получат **одинаковый** нарастающий итог — сразу с учётом их всех. Если нужен построчный итог, укажи `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` или сделай сортировку уникальной.

@@@ sql-46 | оконные функции, группировка
Чем `PARTITION BY` отличается от `GROUP BY`?
???
`GROUP BY` **схлопывает** строки: из десяти сотрудников отдела остаётся одна строка с агрегатом.

`PARTITION BY` в оконной функции считает агрегат по группе, но **оставляет все строки** — к каждой добавляется результат:

```sql
SELECT
  name,
  department,
  salary,
  avg(salary) OVER (PARTITION BY department) AS dept_avg,
  salary - avg(salary) OVER (PARTITION BY department) AS diff
FROM employees;
```

Каждый сотрудник видит среднюю зарплату своего отдела и разницу с ней. Через `GROUP BY` пришлось бы делать подзапрос и `JOIN`.

Как выбрать: нужен итог по группам (отчёт «отдел — средняя зарплата») — `GROUP BY`. Нужны строки плюс контекст группы (доля, место, отклонение от среднего) — окно.

@@@ sql-47 | агрегаты, postgres
Как посчитать несколько условных агрегатов одним запросом?
???
В PostgreSQL у любого агрегата есть `FILTER`:

```sql
SELECT
  user_id,
  count(*)                                    AS total,
  count(*) FILTER (WHERE status = 'paid')     AS paid,
  count(*) FILTER (WHERE status = 'canceled') AS canceled,
  sum(amount) FILTER (WHERE status = 'paid')  AS revenue
FROM orders
GROUP BY user_id;
```

Это один проход по таблице вместо трёх запросов. В других СУБД то же делают через `sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END)`.

Склеить значения группы в строку, массив или JSON:

```sql
SELECT
  post_id,
  string_agg(tag, ', ' ORDER BY tag) AS tags,   -- 'css, react'
  array_agg(tag)                     AS tag_list,
  json_agg(json_build_object('id', id, 'tag', tag)) AS tag_json
FROM post_tags
GROUP BY post_id;
```

`json_agg` удобен, чтобы получить вложенные данные одним запросом, без N+1.

@@@ sql-48 | проектирование, денормализация
Что такое денормализация и когда она оправдана?
???
Сознательное дублирование данных ради быстрого чтения. Примеры:

- счётчик `comments_count` в таблице постов вместо `count(*)` на каждый показ;
- `author_name` в заказе, чтобы не делать `JOIN` (и сохранить имя на момент покупки);
- готовая таблица с отчётом по дням вместо агрегации миллионов строк.

Цена — **согласованность**. При каждом новом комментарии счётчик нужно обновить в той же транзакции или триггером, иначе данные разъедутся.

```sql
BEGIN;
INSERT INTO comments (post_id, body) VALUES (1, 'Отлично!');
UPDATE posts SET comments_count = comments_count + 1 WHERE id = 1;
COMMIT;
```

Порядок действий: сначала нормализованная схема и индексы. Денормализовать — когда замеры показали, что чтение действительно узкое место. Альтернативы: материализованное представление или кэш.

Иногда дублирование нужно бизнесу, а не скорости: цена товара в заказе должна остаться прежней, даже если в каталоге её поменяли.

@@@ sql-49 | масштабирование
Чем отличаются репликация, партиционирование и шардирование?
???
- **Репликация** — полные копии одной базы на нескольких серверах. Пишут в основной (primary), читают в том числе с реплик. Даёт отказоустойчивость и масштабирование **чтения**.
- **Партиционирование** — одна большая таблица делится на части **внутри одного сервера**, например по месяцам. Запрос за октябрь читает только нужную часть, старые данные легко удалить целой партицией.
- **Шардирование** — данные делятся между **разными серверами** по ключу (например, `user_id`). Масштабирует **запись** и объём, но сложнее всего.

```sql
CREATE TABLE events (id bigint, created_at timestamptz, payload jsonb)
  PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

Подводные камни: у реплик есть **задержка** (пользователь сохранил профиль, а с реплики прочитал старый), а при шардировании трудно делать `JOIN` и транзакции между шардами.

@@@ sql-50 | блокировки, очередь
Как сделать очередь задач на PostgreSQL?
???
Несколько воркеров должны забирать задачи, не мешая друг другу и не беря одну задачу дважды. Для этого есть `FOR UPDATE SKIP LOCKED`:

```sql
UPDATE jobs
SET status = 'running', started_at = now()
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'queued'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

- `FOR UPDATE` блокирует выбранную строку до конца транзакции;
- `SKIP LOCKED` пропускает строки, которые уже заблокировал другой воркер, — без ожидания;
- `RETURNING` сразу отдаёт задачу воркеру.

Без `SKIP LOCKED` воркеры выстроились бы в очередь за одной и той же строкой.

Так устроены библиотеки вроде pg-boss и graphile-worker: отдельный брокер (Redis, RabbitMQ) для небольших и средних нагрузок не нужен, а задача создаётся в той же транзакции, что и бизнес-данные.

@@@ sql-51 | соединения, serverless
Что такое пул соединений и зачем PgBouncer?
???
Каждое соединение с PostgreSQL — отдельный процесс на сервере, который занимает память и долго устанавливается. По умолчанию `max_connections = 100`.

Проблема serverless: каждая функция на Vercel может открыть своё соединение. Сто параллельных запросов — сто соединений, и база отвечает `too many connections`.

**Пул** держит небольшое число постоянных соединений и раздаёт их запросам по очереди:

- внутри приложения — пул драйвера (`pg.Pool`) или ORM;
- снаружи — PgBouncer или встроенный пулер хостинга (у Neon и Supabase есть отдельный «pooled» URL).

Режим **transaction pooling** отдаёт соединение только на время транзакции, поэтому ломает то, что живёт на уровне сессии: `SET` без `LOCAL`, `LISTEN/NOTIFY`, сессионные advisory-блокировки.

Практика с Prisma: приложение ходит через pooled URL, а миграции — через прямое (direct) соединение.

@@@ sql-52 | первичный ключ, uuid
UUID или `bigint` для первичного ключа?
???
**`bigint` (identity)**:

- 8 байт, компактные индексы;
- последовательный — новые строки дописываются в конец индекса, вставка быстрая;
- но легко перебрать (`/orders/1001`, `/orders/1002`) и видно, сколько у вас заказов.

**UUID v4** (`gen_random_uuid()`):

- 16 байт;
- можно сгенерировать на клиенте до сохранения, удобно для офлайна и слияния баз;
- не угадывается;
- но случайный: вставки разбрасываются по всему индексу, индекс фрагментируется и хуже помещается в кэш.

**UUID v7** — компромисс: начинается с метки времени, поэтому упорядочен почти как `bigint`, но остаётся уникальным глобально. В PostgreSQL 18 есть встроенная функция `uuidv7()`.

Частая схема: `bigint` как внутренний ключ для связей и отдельный публичный идентификатор (UUID или короткий id) для URL и API.

@@@ sql-53 | postgres, returning
Что делает `RETURNING` в PostgreSQL?
???
Возвращает строки, которые затронул `INSERT`, `UPDATE` или `DELETE`, — без отдельного `SELECT`:

```sql
INSERT INTO users (email) VALUES ('ann@example.com')
RETURNING id, created_at;

UPDATE products SET stock = stock - 1
WHERE id = 42 AND stock > 0
RETURNING stock;            -- пусто, если товар закончился

DELETE FROM sessions WHERE expires_at < now()
RETURNING user_id;
```

Зачем:

- получить сгенерированный id и значения по умолчанию сразу после вставки;
- атомарно изменить и узнать результат — между `UPDATE` и `SELECT` никто не вклинится;
- меньше запросов к базе.

С CTE можно перенести данные одним запросом: `WITH moved AS (DELETE FROM queue … RETURNING *) INSERT INTO archive SELECT * FROM moved`.

Prisma использует `RETURNING` под капотом, когда возвращает созданную запись. В PostgreSQL 18 в `RETURNING` можно получить и старые значения: `RETURNING old.price, new.price`.

@@@ sql-54 | null, сортировка, unique
Как `NULL` ведёт себя в `ORDER BY` и в уникальных ограничениях?
???
**Сортировка.** В PostgreSQL `NULL` считается **больше** любого значения: при `ASC` он в конце, при `DESC` — в начале. Это часто ломает «сортировку по рейтингу»: товары без рейтинга оказываются наверху.

```sql
SELECT * FROM products ORDER BY rating DESC NULLS LAST;
```

Индекс тоже можно создать с `NULLS LAST`, чтобы он подходил под такую сортировку.

**Уникальность.** `NULL` не равен другому `NULL`, поэтому в колонке с `UNIQUE` может быть сколько угодно `NULL`:

```sql
CREATE TABLE users (email text UNIQUE);
INSERT INTO users VALUES (NULL), (NULL);  -- обе строки вставятся
```

Обычно это и нужно (email необязательный, но если указан — уникальный). Если нужно иначе, в PostgreSQL 15+ есть `UNIQUE NULLS NOT DISTINCT`.

@@@ sql-55 | даты, ловушка
Почему `created_at BETWEEN '2026-01-01' AND '2026-01-31'` теряет данные?
???
`BETWEEN` включает обе границы, а строка `'2026-01-31'` для `timestamp` означает `2026-01-31 00:00:00`. Всё, что создано 31 января после полуночи, в выборку **не попадёт**.

Правильно — полуинтервал «от включительно, до исключительно»:

```sql
SELECT * FROM orders
WHERE created_at >= '2026-01-01'
  AND created_at <  '2026-02-01';
```

Плюсы: не нужно знать, сколько дней в месяце, нет проблем с долями секунды, а соседние периоды не пересекаются и не теряют строки на стыке.

Вторая ловушка — часовой пояс. Для `timestamptz` граница `'2026-01-01'` трактуется в часовом поясе сессии. Если отчёт нужен по московскому времени, укажи пояс явно: `'2026-01-01 00:00+03'`.

Ещё один анти-паттерн: `WHERE date(created_at) = '2026-01-15'` — функция над колонкой мешает использовать обычный индекс по `created_at`.

@@@ sql-56 | задача, join
Как найти пользователей, у которых нет ни одного заказа?
???
Три способа:

```sql
-- 1. NOT EXISTS — обычно лучший вариант
SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- 2. LEFT JOIN + проверка на NULL
SELECT u.* FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

-- 3. NOT IN — с ловушкой
SELECT * FROM users
WHERE id NOT IN (SELECT user_id FROM orders);
```

Первые два PostgreSQL выполняет одинаково эффективно (anti join).

`NOT IN` опасен: если в подзапросе встретится хотя бы один `NULL` (например, заказ без пользователя), результат будет **пустым**. Сравнение `id <> NULL` даёт «неизвестно», и строка отбрасывается.

В варианте с `LEFT JOIN` проверяй на `NULL` колонку, которая в найденной строке не может быть пустой, — первичный ключ `o.id`.

@@@ sql-57 | задача, оконные функции
Как выбрать топ-3 товара по продажам в каждой категории?
???
Пронумеровать строки внутри каждой категории и отфильтровать во внешнем запросе:

```sql
SELECT category_id, name, sales
FROM (
  SELECT
    p.*,
    row_number() OVER (PARTITION BY category_id ORDER BY sales DESC) AS rn
  FROM products p
) ranked
WHERE rn <= 3
ORDER BY category_id, rn;
```

Фильтровать по `rn` прямо в `WHERE` нельзя: оконные функции вычисляются на этапе `SELECT`, уже после `WHERE`.

Если при равенстве продаж нужно взять **всех** претендентов на третье место, замени `row_number` на `dense_rank`.

Альтернатива в PostgreSQL — `LATERAL`: для каждой категории выполнить подзапрос с `LIMIT 3`. Это быстрее, когда категорий мало, а товаров много и есть индекс `(category_id, sales DESC)`:

```sql
SELECT c.id, top.*
FROM categories c
CROSS JOIN LATERAL (
  SELECT name, sales FROM products
  WHERE category_id = c.id
  ORDER BY sales DESC
  LIMIT 3
) top;
```

@@@ sql-58 | задача, даты
Как посчитать заказы по месяцам, включая месяцы без заказов?
???
Группировка по началу месяца через `date_trunc`:

```sql
SELECT date_trunc('month', created_at) AS month, count(*) AS orders
FROM orders
GROUP BY 1
ORDER BY 1;
```

Месяцы без заказов здесь просто пропадут, а графику нужны нули. Сгенерируем все месяцы и присоединим данные:

```sql
SELECT m.month, count(o.id) AS orders
FROM generate_series('2026-01-01'::date, '2026-12-01'::date, interval '1 month') AS m(month)
LEFT JOIN orders o
  ON o.created_at >= m.month
 AND o.created_at <  m.month + interval '1 month'
GROUP BY m.month
ORDER BY m.month;
```

- `count(o.id)`, а не `count(*)` — иначе пустые месяцы получат 1;
- условие в `ON`, а не в `WHERE` — иначе `LEFT JOIN` превратится во внутренний;
- для `timestamptz` границы месяца зависят от часового пояса сессии — для отчёта в нужном поясе используй `created_at AT TIME ZONE 'Europe/Moscow'`.

@@@ sql-59 | postgres, lateral
Что такое `LATERAL JOIN`?
???
Обычный подзапрос в `FROM` не видит колонки соседних таблиц. `LATERAL` разрешает подзапросу ссылаться на строки, стоящие **левее**, — он выполняется для каждой из них, как цикл:

```sql
-- три последних заказа каждого пользователя
SELECT u.name, o.id, o.total
FROM users u
LEFT JOIN LATERAL (
  SELECT id, total
  FROM orders
  WHERE orders.user_id = u.id
  ORDER BY created_at DESC
  LIMIT 3
) o ON true;
```

- `LEFT JOIN LATERAL … ON true` оставляет пользователей без заказов (с `NULL`);
- `CROSS JOIN LATERAL` выбросит их.

Где полезен: «топ-N в каждой группе», несколько колонок из одного коррелированного подзапроса, вызов функций, которые возвращают набор строк (`jsonb_array_elements`, `unnest`), для каждой строки.

С индексом `orders (user_id, created_at DESC)` такой запрос очень быстрый: для каждого пользователя читаются ровно три записи.
