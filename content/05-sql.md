@@@ sql-01 | join
Какие бывают JOIN?
???
`JOIN` объединяет строки двух таблиц по условию в `ON`. Типы отличаются тем, что происходит со строками, **для которых пары не нашлось**.

Пример: `users` (Аня, Боб, Вика) и `orders` (два заказа Ани, один заказ без пользователя).

- **`INNER JOIN`** (или просто `JOIN`) — только строки, у которых нашлась пара в обеих таблицах. Результат: два заказа Ани. Боб и Вика без заказов пропадут.
- **`LEFT JOIN`** — **все** строки левой таблицы плюс совпадения справа. Если пары нет, колонки правой таблицы заполняются `NULL`. Результат: два заказа Ани, Боб с `NULL`, Вика с `NULL`.
- **`RIGHT JOIN`** — наоборот: все строки правой. На практике почти не используют: таблицы меняют местами и пишут `LEFT`.
- **`FULL JOIN`** — все строки обеих таблиц: пары, плюс «одинокие» слева и справа с `NULL`.
- **`CROSS JOIN`** — каждая строка с каждой (декартово произведение): 3 пользователя × 3 заказа = 9 строк. Нужен для генерации комбинаций (все размеры × все цвета).

Классический приём — найти строки **без пары** через `LEFT JOIN` и проверку на `NULL`:

```sql
-- пользователи без заказов
SELECT u.*
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

`o.id IS NULL` срабатывает только у тех, к кому ничего не присоединилось.

Ловушка: если в правой таблице на одну строку слева приходится несколько совпадений, строка слева **размножится**. Пользователь с 5 заказами даст 5 строк — об этом стоит помнить при подсчётах.

@@@ sql-02 | группировка
Чем `WHERE` отличается от `HAVING`?
???
`WHERE` фильтрует **строки до** группировки. `HAVING` — **группы после** `GROUP BY`, и только в нём можно использовать агрегаты:

```sql
SELECT user_id, count(*) AS orders
FROM orders
WHERE created_at > now() - interval '30 days'  -- отбросить старые строки
GROUP BY user_id
HAVING count(*) >= 5;                          -- оставить активных
```

`WHERE count(*) > 5` — ошибка: на этапе `WHERE` групп ещё нет.

Читается так: «возьми заказы за последние 30 дней, сгруппируй по пользователю и оставь только тех, у кого их 5 и больше».

Совет для производительности: всё, что можно отфильтровать по строкам, пиши в `WHERE`. Тогда в группировку попадёт меньше данных, а условие сможет использовать индекс.

@@@ sql-03 | основы
В каком порядке логически выполняется `SELECT`?
???
`FROM / JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT / OFFSET`.

Из этого порядка следуют частые ошибки:

- алиас из `SELECT` нельзя использовать в `WHERE` — он ещё не вычислен; в `ORDER BY` можно (в PostgreSQL ещё и в `GROUP BY`);
- агрегаты нельзя писать в `WHERE`, только в `HAVING`;
- оконные функции считаются на этапе `SELECT`, поэтому фильтровать по ним можно только во внешнем запросе или CTE.

```sql
SELECT price * qty AS total FROM items
WHERE total > 100;        -- ошибка
-- нужно: WHERE price * qty > 100
```

Это **логический** порядок: планировщик физически может выполнять шаги иначе, если результат тот же.

Как запомнить: сначала нужно понять, **откуда** брать данные (`FROM`), потом **какие строки** оставить (`WHERE`), как **сгруппировать** и какие группы оставить, и только потом — **что показать** (`SELECT`) и в каком порядке.

@@@ sql-04 | индексы
Что такое индекс и как работает B-tree?
???
**Индекс** — отдельная структура данных, которая помогает быстро найти строки, не просматривая всю таблицу. Аналогия — предметный указатель в конце книги: чтобы найти «замыкание», не листаешь 500 страниц, а открываешь указатель и сразу видишь номер страницы.

Без индекса запрос `WHERE email = 'ann@mail.ru'` по таблице из миллиона строк проверяет **каждую** строку (Seq Scan — последовательное сканирование).

**B-tree** (тип по умолчанию в PostgreSQL) — сбалансированное дерево, в котором ключи хранятся **отсортированными**:

- корень и промежуточные узлы указывают, в какую ветку идти («значения меньше M — налево»);
- листья содержат значения и ссылки на строки таблицы;
- все листья на одной глубине, поэтому любой поиск занимает примерно одинаковое время.

Поиск — O(log n): для миллиона строк это 3–4 перехода по дереву вместо миллиона проверок.

Так как значения отсортированы, B-tree подходит для:

- равенства `=`;
- диапазонов `<`, `>`, `BETWEEN`;
- сортировки `ORDER BY` (данные уже лежат по порядку);
- поиска по началу строки `LIKE 'abc%'`.

**Цена индекса:** он занимает место на диске и **замедляет запись** — при каждом `INSERT`, `UPDATE`, `DELETE` его тоже нужно обновлять.

Другие типы: Hash (только `=`), GIN (массивы, JSONB, полнотекстовый поиск), GiST (геоданные, диапазоны), BRIN (огромные таблицы, упорядоченные по времени вставки).

Первичный ключ и `UNIQUE` создают B-tree индекс автоматически.

@@@ sql-05 | индексы, производительность
Почему запрос не использует индекс?
???
Индекс есть, а в `EXPLAIN` всё равно `Seq Scan`. Частые причины:

**1. Функция над колонкой.** Индекс построен по значениям `email`, а не по `lower(email)`:

```sql
WHERE lower(email) = 'ann@mail.ru'      -- обычный индекс по email не поможет
CREATE INDEX ON users (lower(email));    -- нужен индекс по выражению
```

То же с `date(created_at) = …` и `price * 1.2 > …`.

**2. `LIKE '%abc'`.** B-tree упорядочен по началу строки, а здесь начало неизвестно. Нужен триграммный индекс (`pg_trgm`).

**3. Несовпадение типов.** Колонка `text`, а сравнивают с числом — PostgreSQL приводит тип, и индекс может не подойти.

**4. Низкая селективность.** Если условие выбирает большую часть таблицы (`WHERE is_active = true`, а активны 90%), прочитать всю таблицу подряд дешевле, чем прыгать по индексу. Планировщик выбирает Seq Scan **специально**, и это правильно.

**5. Неверный порядок в составном индексе.** Индекс `(a, b)`, а фильтр только по `b` — как искать в телефонном справочнике только по имени.

**6. Устаревшая статистика.** Планировщик думает, что в таблице 100 строк, а их миллион. Поможет `ANALYZE table_name`.

**7. Маленькая таблица.** На сотне строк Seq Scan быстрее любого индекса.

Как проверять: `EXPLAIN ANALYZE` покажет, какой план выбран и сколько времени занял каждый шаг.

@@@ sql-06 | индексы
Как порядок колонок влияет на составной индекс?
???
Составной индекс `(a, b, c)` отсортирован сначала по `a`, внутри одинаковых `a` — по `b`, внутри одинаковых `b` — по `c`. Как телефонный справочник: сначала по фамилии, потом по имени.

По справочнику легко найти:

- всех **Ивановых** (`WHERE a = …`);
- **Иванова Петра** (`WHERE a = … AND b = …`).

Но найти всех **Петров** без фамилии он не поможет — Петры разбросаны по всему справочнику.

Это правило **левого префикса**: индекс `(a, b, c)` работает для условий по `a`, `a + b`, `a + b + c`, но не по одному `b` или `c`.

**Как выбирать порядок:** сначала колонки с **равенством**, потом — с **диапазоном** или сортировкой:

```sql
CREATE INDEX ON orders (user_id, created_at DESC);

-- быстро: найти пользователя, внутри — заказы уже отсортированы по дате
SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC LIMIT 20;
```

PostgreSQL находит в индексе блок `user_id = 1`, а в нём заказы уже лежат по убыванию даты — достаточно прочитать первые 20. Сортировка не нужна.

Если поменять порядок на `(created_at, user_id)`, заказы одного пользователя окажутся разбросаны по всему индексу.

Порядок условий в `WHERE` значения не имеет: `WHERE b = 1 AND a = 2` использует индекс `(a, b)` так же.

@@@ sql-07 | производительность, explain
Как читать `EXPLAIN ANALYZE`?
???
`EXPLAIN` показывает **план** — как PostgreSQL собирается выполнить запрос. `EXPLAIN ANALYZE` ещё и **выполняет** запрос и добавляет реальное время и число строк для каждого шага.

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
```

```
Index Scan using orders_user_id_idx on orders
  (cost=0.43..8.45 rows=3 width=40)
  (actual time=0.02..0.03 rows=3 loops=1)
Execution Time: 0.05 ms
```

План — это дерево: читается **изнутри наружу**, самые вложенные узлы выполняются первыми.

- `cost` — оценка стоимости в условных единицах (до первой строки..всего);
- `rows` — сколько строк **ожидал** планировщик;
- `actual time` — реальное время в миллисекундах;
- `actual rows` — сколько строк **получилось** на самом деле;
- `loops` — сколько раз выполнялся узел (время указано на один раз).

На что смотреть:

- **`Seq Scan`** по большой таблице там, где ждёшь `Index Scan`, — не хватает индекса или он не подходит;
- **большая разница между `rows` и `actual rows`** (ожидал 10, получил 100 000) — устаревшая статистика, планировщик выбрал неверную стратегию. Лечится `ANALYZE`;
- **`Nested Loop`** с большим числом `loops` — запрос выполняется в цикле тысячи раз;
- **`Sort` с `external merge Disk`** — сортировке не хватило памяти, данные пишутся на диск;
- **самый дорогой узел** по `actual time` — узкое место.

Осторожно: `EXPLAIN ANALYZE` действительно выполняет запрос, включая `UPDATE` и `DELETE`. Для них оборачивай в транзакцию с `ROLLBACK`. Опция `BUFFERS` покажет, сколько данных прочитано с диска и из кэша.

@@@ sql-08 | ключи, основы
Что такое первичный и внешний ключ?
???
**Первичный ключ (PRIMARY KEY)** — колонка (или набор колонок), которая **однозначно идентифицирует** строку. Как номер паспорта для человека.

- значения уникальны — двух строк с одним id быть не может;
- не может быть `NULL`;
- в таблице только один первичный ключ;
- PostgreSQL автоматически создаёт для него индекс.

**Внешний ключ (FOREIGN KEY)** — колонка, которая **ссылается** на первичный ключ другой таблицы. Он связывает таблицы и гарантирует **ссылочную целостность**: нельзя сослаться на строку, которой нет.

```sql
CREATE TABLE users (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE
);

CREATE TABLE orders (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total numeric(10, 2)
);

INSERT INTO orders (user_id, total) VALUES (999, 100);
-- ошибка: пользователя 999 не существует
```

`ON DELETE` задаёт, что делать с заказами при удалении пользователя:

- `CASCADE` — удалить их вместе с ним;
- `SET NULL` — оставить, обнулив `user_id`;
- `RESTRICT` / `NO ACTION` (по умолчанию) — запретить удаление, пока есть заказы.

Ловушка: внешний ключ в PostgreSQL **не индексируется сам**. Индекс по `orders.user_id` нужно создать вручную — иначе запросы «заказы пользователя» и удаление пользователей будут медленными.

@@@ sql-09 | проектирование
Что такое нормализация? Кратко про 1НФ, 2НФ, 3НФ.
???
**Нормализация** — способ разложить данные по таблицам так, чтобы каждый факт хранился **один раз**. Цель — избежать **аномалий**: когда одно и то же значение лежит в нескольких местах, при изменении его легко обновить в одном и забыть в другом.

Пример проблемы: в таблице заказов хранится и адрес клиента. Клиент переехал — нужно обновить все его 50 заказов, а если пропустить один, данные противоречат друг другу.

**1НФ (первая нормальная форма)** — в каждой ячейке одно **атомарное** значение, нет повторяющихся групп.

```
✗ tags: "react, typescript, css"
✓ отдельная таблица post_tags (post_id, tag) — по строке на тег
```

С тегами через запятую нельзя нормально искать по тегу, считать их и проверять уникальность.

**2НФ** — 1НФ, и каждое неключевое поле зависит от **всего** составного ключа, а не от его части.

```
✗ order_items (order_id, product_id, qty, product_name)
   product_name зависит только от product_id — часть ключа
✓ product_name переносится в таблицу products
```

**3НФ** — 2НФ, и неключевые поля не зависят **друг от друга** (нет транзитивных зависимостей).

```
✗ users (id, city_id, city_name)
   city_name зависит от city_id, а не от id пользователя
✓ city_name — в таблице cities
```

Короткая формулировка 3НФ: «каждое поле зависит от ключа, от всего ключа и ни от чего, кроме ключа».

**Денормализация** — осознанное дублирование ради скорости чтения (счётчик комментариев в посте). Делают её после замеров, а не заранее.

@@@ sql-10 | транзакции
Что такое транзакция и ACID?
???
**Транзакция** — группа операций, которая выполняется по принципу «**всё или ничего**».

Классический пример — перевод денег:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

Если сервер упадёт между двумя `UPDATE`, без транзакции деньги спишутся, но не зачислятся. С транзакцией изменения либо применятся оба, либо ни одно. `ROLLBACK` вместо `COMMIT` отменяет всё сделанное.

**ACID** — четыре гарантии транзакций:

- **Atomicity (атомарность)** — транзакция неделима: применяются либо все изменения, либо ни одного.
- **Consistency (согласованность)** — после транзакции база в корректном состоянии: соблюдены все ограничения (`NOT NULL`, `UNIQUE`, внешние ключи, `CHECK`). Если ограничение нарушено, транзакция откатится.
- **Isolation (изоляция)** — параллельные транзакции не видят промежуточных результатов друг друга. Насколько строго — задаёт уровень изоляции.
- **Durability (долговечность)** — после `COMMIT` данные сохранены и переживут сбой питания. PostgreSQL сначала записывает изменения в журнал на диске (WAL — Write-Ahead Log) и только потом подтверждает коммит.

В PostgreSQL **каждый** отдельный запрос без `BEGIN` и так выполняется в своей транзакции (autocommit). Явный `BEGIN` нужен, чтобы объединить несколько запросов.

В Prisma это `prisma.$transaction([...])`.

@@@ sql-11 | транзакции, изоляция
Какие уровни изоляции транзакций есть и какие аномалии они допускают?
???
Когда несколько транзакций работают одновременно, они могут «видеть» изменения друг друга в неудачный момент. Такие эффекты называются **аномалиями**:

- **Dirty read (грязное чтение)** — транзакция читает данные, которые другая ещё **не закоммитила** (и может откатить).
- **Non-repeatable read (неповторяемое чтение)** — читаешь строку дважды в одной транзакции и получаешь **разные значения**: между чтениями другая транзакция её изменила.
- **Phantom read (фантомы)** — повторный запрос с тем же условием возвращает **другой набор строк**: кто-то добавил или удалил подходящие строки.
- **Serialization anomaly** — результат параллельного выполнения невозможно получить ни при каком последовательном порядке транзакций.

Уровни изоляции (от слабого к строгому):

- **Read Uncommitted** — в PostgreSQL работает как Read Committed: грязного чтения в PG не бывает вообще.
- **Read Committed** (по умолчанию в PG) — каждый **запрос** видит данные, закоммиченные на момент **его** начала. Два `SELECT` в одной транзакции могут увидеть разное.
- **Repeatable Read** — снимок данных берётся в начале **транзакции**, и все запросы видят его. В PostgreSQL фантомов на этом уровне тоже нет.
- **Serializable** — результат гарантированно такой, как если бы транзакции шли строго по очереди. Если PostgreSQL обнаружит конфликт, одна транзакция упадёт с ошибкой сериализации, и её нужно **повторить**.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT sum(balance) FROM accounts;  -- оба запроса увидят один снимок
SELECT count(*) FROM accounts;
COMMIT;
```

Чем строже уровень, тем меньше аномалий, но больше конфликтов и повторов. Для большинства задач хватает Read Committed плюс явных блокировок там, где нужно.

@@@ sql-12 | postgres, mvcc
Что такое MVCC в PostgreSQL и зачем нужен `VACUUM`?
???
**MVCC (Multi-Version Concurrency Control)** — способ, которым PostgreSQL позволяет многим транзакциям работать одновременно.

Главная идея: `UPDATE` **не перезаписывает** строку на месте. Он помечает старую версию как устаревшую и создаёт **новую версию** строки. `DELETE` тоже не удаляет физически, а только помечает строку.

Зачем: транзакция, которая началась раньше, продолжает видеть старую версию — свой согласованный снимок данных. Поэтому:

- **читатели не блокируют писателей** — отчёт на 10 минут не мешает обновлять данные;
- **писатели не блокируют читателей** — `SELECT` не ждёт, пока кто-то закончит `UPDATE`.

Обратная сторона — **мёртвые версии строк** (dead tuples). Когда ни одна транзакция их больше не видит, они просто занимают место. Таблица, где часто делают `UPDATE`, «раздувается» (bloat) и работает медленнее.

**`VACUUM`** убирает мусор:

- помечает место мёртвых строк как свободное для новых записей (сам файл таблицы при этом обычно не уменьшается — это делает только `VACUUM FULL`, который блокирует таблицу);
- обновляет карту видимости — без неё не работает быстрый index-only scan;
- «замораживает» старые строки, чтобы не переполнился 32-битный счётчик транзакций (transaction ID wraparound). Если до этого дойдёт, PostgreSQL остановит запись, чтобы не потерять данные.

Обычно всё это делает **autovacuum** в фоне, заодно запуская `ANALYZE` для обновления статистики. Вручную его вызывают после массовых удалений или загрузок.

Практический вывод: долгие открытые транзакции вредны — пока они живы, `VACUUM` не может удалить версии, которые они ещё теоретически могут увидеть.

@@@ sql-13 | производительность, orm
Что такое проблема N+1?
???
Ситуация, когда для показа списка из N элементов выполняется **1 запрос** за список и ещё **N запросов** — по одному на каждый элемент:

```ts
const posts = await db.post.findMany(); // 1 запрос: 100 постов
for (const p of posts) {
  // + 100 запросов: автор каждого поста
  p.author = await db.user.findUnique({ where: { id: p.authorId } });
}
```

Итого 101 запрос. Каждый по отдельности быстрый, но у каждого есть накладные расходы: поездка по сети до базы, разбор, планирование. 101 × 2 мс = 200 мс вместо 5.

Коварство в том, что на локальной базе с 10 постами проблема незаметна, а в продакшене с тысячами записей страница тормозит.

Решения:

```sql
-- 1. JOIN — всё одним запросом
SELECT p.*, u.name FROM posts p JOIN users u ON u.id = p.author_id;

-- 2. Два запроса: список + все нужные авторы разом
SELECT * FROM users WHERE id IN (1, 2, 3, …);
```

```ts
// 3. В ORM — загрузка связей
const posts = await prisma.post.findMany({ include: { author: true } });
```

Prisma в этом случае делает два запроса (посты и авторы через `IN`) или один с `JOIN` — в зависимости от настройки `relationLoadStrategy`.

В GraphQL эту проблему решает **DataLoader**: он собирает все запросы за одну итерацию event loop и выполняет их пакетом.

Как обнаружить: включить логирование запросов в ORM и посмотреть, нет ли повторяющихся запросов в цикле.

@@@ sql-14 | оконные функции
Что такое оконные функции? Приведи пример.
???
Оконная функция считает значение по **набору строк, связанных с текущей** (окну), но, в отличие от `GROUP BY`, **не схлопывает** строки: каждая строка остаётся на месте и получает дополнительную колонку с результатом.

Синтаксис: `функция() OVER (PARTITION BY … ORDER BY …)`:

- `PARTITION BY` — на какие группы делить строки (как `GROUP BY`, но без схлопывания);
- `ORDER BY` — порядок строк внутри окна.

Классическая задача — **топ-N в каждой группе**:

```sql
-- три последних заказа каждого пользователя
SELECT *
FROM (
  SELECT o.*,
         row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM orders o
) t
WHERE rn <= 3;
```

Что происходит: заказы делятся на группы по `user_id`, внутри каждой сортируются по дате, и `row_number` нумерует их 1, 2, 3… Самый свежий заказ каждого пользователя получает 1. Внешний запрос оставляет первые три.

Подзапрос нужен, потому что оконные функции вычисляются на этапе `SELECT` — уже после `WHERE`, и фильтровать по `rn` сразу нельзя.

Самые частые оконные функции:

- `row_number()`, `rank()`, `dense_rank()` — нумерация и места;
- `lag(col)` / `lead(col)` — значение из предыдущей / следующей строки;
- `sum(col) OVER (ORDER BY …)` — нарастающий итог;
- `avg(col) OVER (PARTITION BY …)` — среднее по группе рядом с каждой строкой.

@@@ sql-15 | оконные функции
Чем отличаются `ROW_NUMBER`, `RANK` и `DENSE_RANK`?
???
Все три нумеруют строки внутри окна по `ORDER BY`, но по-разному ведут себя при равных значениях. Для 100, 90, 90, 80:

- `row_number` → 1, 2, 3, 4 — всегда уникальный, порядок среди равных случаен
- `rank` → 1, 2, 2, 4 — равные делят место, после них пропуск
- `dense_rank` → 1, 2, 2, 3 — без пропусков

```sql
SELECT name, salary,
       dense_rank() OVER (ORDER BY salary DESC) AS place
FROM employees;
```

Что выбрать: «ровно N строк на группу» (последний заказ, топ-3) — `row_number`; «все, кто на 2-м месте» или «вторая по величине зарплата» — `dense_rank`; места как в спорте — `rank`.

Аналогия со спортом: два бегуна пришли вторыми одновременно. `rank` — оба вторые, следующий четвёртый (третьего места нет). `dense_rank` — оба вторые, следующий третий.

Чтобы `row_number` был предсказуемым при равенстве, добавляют в `ORDER BY` уникальную колонку: `ORDER BY salary DESC, id`.

@@@ sql-16 | cte
Что такое CTE (`WITH`)? А рекурсивный CTE?
???
**CTE (Common Table Expression)** — именованный подзапрос, объявленный перед основным запросом. Как переменная в коде: даёшь промежуточному результату понятное имя и используешь его дальше.

```sql
WITH active AS (
  SELECT * FROM users WHERE last_seen > now() - interval '7 days'
),
active_orders AS (
  SELECT o.* FROM orders o JOIN active a ON a.id = o.user_id
)
SELECT count(*) FROM active_orders;
```

Без CTE это были бы вложенные подзапросы, которые читаются изнутри наружу. С CTE запрос читается сверху вниз, как код.

С PostgreSQL 12 простые CTE встраиваются в основной запрос и оптимизируются вместе с ним — по скорости они не хуже подзапросов. Если нужно вычислить CTE один раз и переиспользовать, пишут `AS MATERIALIZED`.

**Рекурсивный CTE** — для обхода **деревьев и графов**: категории с подкатегориями, комментарии с ответами, оргструктура.

```sql
WITH RECURSIVE tree AS (
  -- 1. стартовая часть: корень
  SELECT id, parent_id, name, 1 AS depth FROM categories WHERE id = 1
  UNION ALL
  -- 2. рекурсивная часть: дети уже найденных
  SELECT c.id, c.parent_id, c.name, t.depth + 1
  FROM categories c
  JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree;
```

Как работает: сначала выполняется стартовая часть (корень). Затем рекурсивная часть ищет детей найденных строк, потом детей детей — и так, пока очередной шаг не вернёт пустой результат.

Ловушка: при цикле в данных (категория ссылается сама на себя через цепочку) рекурсия станет бесконечной. Защищаются ограничением глубины `WHERE depth < 10` или конструкцией `CYCLE` (PostgreSQL 14+).

@@@ sql-17 | основы
`UNION` против `UNION ALL`?
???
`UNION` объединяет результаты и **убирает дубликаты** — для этого нужна сортировка или хеширование всего результата, это дороже.

`UNION ALL` просто склеивает строки. Если дублей быть не может (например, данные из разных таблиц с разными id) или они нужны — бери `UNION ALL`.

```sql
SELECT email FROM customers
UNION ALL
SELECT email FROM subscribers;
```

Правила: число колонок и их типы должны совпадать, имена колонок берутся из первого запроса, `ORDER BY` пишется один раз в конце и сортирует общий результат.

Родственники: `INTERSECT` — строки, которые есть в обоих результатах, `EXCEPT` — есть в первом, но нет во втором.

Отличие от `JOIN`: `JOIN` склеивает таблицы **по горизонтали** (добавляет колонки), а `UNION` — **по вертикали** (добавляет строки).

@@@ sql-18 | основы
`DELETE`, `TRUNCATE` и `DROP` — в чём разница?
???
Три команды «удаления» работают на разных уровнях:

**`DELETE`** — удаляет **строки**, можно выборочно:

```sql
DELETE FROM sessions WHERE expires_at < now();
```

- обрабатывает строки по одной: проверяет внешние ключи, запускает триггеры `ON DELETE`, может вернуть удалённое через `RETURNING`;
- из-за MVCC строки не исчезают физически сразу — место освободит `VACUUM`;
- на миллионах строк — медленно.

**`TRUNCATE`** — мгновенно очищает **всю таблицу**:

```sql
TRUNCATE logs RESTART IDENTITY;
```

- не обрабатывает строки по одной, а просто выбрасывает файлы данных — быстро на любом объёме;
- `WHERE` нет — только всё целиком;
- `RESTART IDENTITY` сбрасывает счётчик автоинкремента;
- не запускает построчные триггеры;
- берёт эксклюзивную блокировку таблицы;
- если на таблицу ссылаются внешние ключи, нужен `CASCADE` (очистит и ссылающиеся таблицы — осторожно).

**`DROP TABLE`** — удаляет **саму таблицу**: структуру, данные, индексы, ограничения. После этого таблицы просто нет.

```sql
DROP TABLE IF EXISTS temp_import;
```

Особенность PostgreSQL: все три команды **транзакционны** — их можно откатить, если они выполнены внутри `BEGIN … ROLLBACK`. Во многих других СУБД (например, MySQL) `TRUNCATE` и `DROP` откатить нельзя.

@@@ sql-19 | null, ловушка
Какие подводные камни у `NULL`?
???
`NULL` — это «неизвестно». Любое сравнение с ним даёт `NULL`, а не true/false, а `WHERE` пропускает только true.

Логика простая: если возраст человека неизвестен, нельзя сказать ни «ему больше 18», ни «ему не больше 18». Ответ — «неизвестно». Поэтому SQL использует трёхзначную логику: true, false и unknown.

- `WHERE x = NULL` ничего не найдёт → нужно `IS NULL`.
- `WHERE status <> 'done'` не вернёт строки, где `status IS NULL`.
- `NOT IN (подзапрос, где есть NULL)` вернёт пустоту: `x <> NULL` — неизвестно.
- Агрегаты (`sum`, `avg`, `count(col)`) пропускают `NULL`, а `sum` по пустому набору даёт `NULL`, а не 0.
- `'a' || NULL` → `NULL`.

```sql
SELECT coalesce(sum(amount), 0) FROM payments WHERE user_id = 1;
SELECT * FROM tasks WHERE status IS DISTINCT FROM 'done';
```

Помогают `COALESCE`, `IS DISTINCT FROM` и `NOT EXISTS` вместо `NOT IN`.

`IS DISTINCT FROM` — сравнение, которое считает `NULL` обычным значением: `NULL IS DISTINCT FROM 'done'` даёт true. `avg` по колонке с `NULL` делит только на число непустых значений — средняя оценка не учитывает тех, кто не оценил.

@@@ sql-20 | агрегаты
`COUNT(*)`, `COUNT(column)` и `COUNT(DISTINCT column)`?
???
- `count(*)` — число строк;
- `count(col)` — число строк, где `col` **не** `NULL`;
- `count(DISTINCT col)` — число уникальных непустых значений.

Пример: заказы с `promo_code` = `'A'`, `'A'`, `NULL`, `'B'` → `count(*)` = 4, `count(promo_code)` = 3, `count(DISTINCT promo_code)` = 2.

Ловушка с `LEFT JOIN`: у пользователя без заказов всё равно есть одна строка (с `NULL` в колонках заказа), поэтому `count(*)` даст 1 вместо 0.

```sql
SELECT u.id, count(o.id) AS orders   -- не count(*)
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;
```

Миф: `count(1)` быстрее `count(*)`. В PostgreSQL это одно и то же, а `count(*)` даже чуть понятнее планировщику. Точный `count(*)` по большой таблице медленный (MVCC требует проверить видимость строк), поэтому для «примерно 1,2 млн» берут оценку из `pg_class.reltuples`.

@@@ sql-21 | подзапросы
`EXISTS` или `IN`? Подзапрос или `JOIN`?
???
**`IN`** проверяет, входит ли значение в список:

```sql
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders);
```

**`EXISTS`** проверяет, что подзапрос вернул **хотя бы одну строку**:

```sql
SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

`SELECT 1` — содержимое не важно, важен сам факт наличия строки. `EXISTS` останавливается на первой найденной.

Для положительной проверки PostgreSQL обычно превращает и `IN`, и `EXISTS` в одинаковый **semi-join** — по скорости разницы нет.

**Разница появляется с отрицанием.** `NOT IN` ломается, если в подзапросе есть `NULL`:

```sql
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);
-- если хоть у одного заказа user_id IS NULL — результат пустой
```

`id <> NULL` даёт «неизвестно», и все строки отбрасываются. `NOT EXISTS` такой проблемы не имеет — поэтому для отрицания всегда используй его.

**Подзапрос или `JOIN`?**

- нужны **колонки** второй таблицы (имя автора, сумма заказа) → `JOIN`;
- нужна только **проверка наличия** («у пользователя есть заказы») → `EXISTS`.

Почему не `JOIN` для проверки: пользователь с пятью заказами после `JOIN` превратится в пять строк, придётся добавлять `DISTINCT`. `EXISTS` вернёт его один раз.

@@@ sql-22 | пагинация, производительность
OFFSET-пагинация или keyset (курсорная)?
???
**OFFSET-пагинация** — «пропусти N строк, дай следующие 20»:

```sql
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 10000;
```

Проблемы:

- **медленно на дальних страницах.** База не умеет прыгнуть сразу на 10 000-ю строку — она читает 10 020 строк и выбрасывает первые 10 000. Чем дальше страница, тем медленнее;
- **строки «съезжают».** Пока пользователь смотрел страницу 1, появилось 3 новых поста. На странице 2 он увидит 3 поста, которые уже видел.

**Keyset (курсорная) пагинация** — «дай 20 строк **после** последней, которую я видел»:

```sql
SELECT * FROM posts
WHERE (created_at, id) < ($1, $2)   -- значения последнего поста с прошлой страницы
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

- с индексом `(created_at DESC, id DESC)` база сразу находит место продолжения — одинаково быстро на любой глубине;
- новые записи не сдвигают выдачу;
- `id` в сортировке нужен как «разрешение ничьей»: у двух постов может совпасть время, и без него строки могли бы потеряться или повториться.

Минус keyset: нельзя перейти сразу на страницу 57 — только «следующая» и «предыдущая».

Выбор: бесконечная лента, чаты, API — keyset. Админка с номерами страниц и небольшими таблицами — OFFSET. В Prisma keyset делается через параметр `cursor`.

@@@ sql-23 | postgres, upsert
Как сделать «вставить или обновить» (upsert) в PostgreSQL?
???
```sql
INSERT INTO stats (user_id, views)
VALUES (1, 1)
ON CONFLICT (user_id)
DO UPDATE SET views = stats.views + EXCLUDED.views;
```

- Нужен уникальный индекс или ограничение на колонке конфликта — по нему PostgreSQL понимает, что строка «уже есть».
- `EXCLUDED` — строка, которую пытались вставить.
- `ON CONFLICT DO NOTHING` — просто пропустить дубликат.
- Можно добавить условие: `DO UPDATE SET … WHERE stats.updated_at < EXCLUDED.updated_at`.

Главное преимущество перед «SELECT, потом INSERT или UPDATE» — **атомарность**: два параллельных запроса не создадут дубль и не упадут на уникальном ключе. Начиная с PostgreSQL 15 есть ещё `MERGE` для сложных сценариев синхронизации.

Почему «сначала SELECT» ненадёжен: два запроса одновременно проверяют, есть ли запись, оба видят «нет», оба делают `INSERT` — и второй падает на уникальном индексе (или, без индекса, появляется дубль). В Prisma upsert — это `prisma.stats.upsert({ where, create, update })`.

@@@ sql-24 | postgres, jsonb
`json` или `jsonb` в PostgreSQL? Когда их использовать?
???
Оба типа хранят JSON, но по-разному:

- **`json`** — хранит **текст как есть**: с пробелами, порядком ключей и даже дублирующимися ключами. При каждом обращении текст разбирается заново.
- **`jsonb`** — хранит JSON в **разобранном бинарном** виде: пробелы и порядок ключей теряются, при дублях остаётся последний ключ. Запись чуть медленнее (нужно разобрать), зато чтение и поиск — быстрые.

Только `jsonb` поддерживает GIN-индексы и удобные операторы:

```sql
SELECT * FROM products WHERE attrs @> '{"color": "red"}'; -- содержит пару
SELECT * FROM products WHERE attrs ? 'size';              -- есть ключ
SELECT attrs->>'color' FROM products;                     -- значение как текст
SELECT attrs->'dims'->>'width' FROM products;             -- вложенное поле

CREATE INDEX ON products USING gin (attrs);
```

`->` возвращает `jsonb`, `->>` — текст.

Почти всегда выбирают `jsonb`. `json` нужен, только если важно сохранить исходный текст точь-в-точь (например, хранение вебхуков для аудита).

**Когда использовать JSON в базе:**

- гибкие атрибуты, разные у разных записей (характеристики товаров разных категорий);
- настройки пользователя;
- данные из внешних API, которые хранятся «как есть».

**Когда не стоит:** поля, по которым часто фильтруют, сортируют и джойнят, а также данные со связями. Их лучше держать в обычных колонках: там строгие типы, ограничения и внешние ключи, а статистика для планировщика точнее.

@@@ sql-25 | транзакции, блокировки
Что такое deadlock и как его избежать?
???
**Deadlock (взаимоблокировка)** — две транзакции ждут друг друга, и ни одна не может продолжить:

```
T1: блокирует счёт A  →  хочет счёт B (ждёт T2)
T2: блокирует счёт B  →  хочет счёт A (ждёт T1)
```

Как в узком коридоре: двое встали лицом к лицу и ждут, пока уступит другой.

Типичный сценарий — два встречных перевода одновременно:

```sql
-- T1: перевод с 1 на 2           -- T2: перевод с 2 на 1
UPDATE accounts … WHERE id = 1;   UPDATE accounts … WHERE id = 2;
UPDATE accounts … WHERE id = 2;   UPDATE accounts … WHERE id = 1;  -- deadlock
```

PostgreSQL периодически (по умолчанию через `deadlock_timeout` = 1 секунда ожидания) проверяет граф ожиданий. Найдя цикл, он **отменяет одну из транзакций** с ошибкой `deadlock detected`, и вторая продолжает работу.

Как избегать:

- **блокировать ресурсы в одном порядке** — например, всегда по возрастанию id. Тогда оба перевода сначала возьмут счёт 1, второй подождёт, и цикла не будет;
- **держать транзакции короткими** — не делать внутри транзакции HTTP-запросов и долгих вычислений;
- **повторять транзакцию** при ошибке deadlock — это нормальная часть работы с базой;
- блокировать заранее и явно: `SELECT … FOR UPDATE` сразу для всех нужных строк.

```sql
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
```

@@@ sql-26 | безопасность
Что такое SQL-инъекция и как защититься?
???
**SQL-инъекция** — атака, при которой пользовательский ввод попадает **прямо в текст запроса** и меняет его смысл.

Уязвимый код:

```ts
const sql = `SELECT * FROM users WHERE email = '${email}' AND password = '${password}'`;
```

Злоумышленник вводит в поле email: `' OR 1=1 --`. Запрос превращается в:

```sql
SELECT * FROM users WHERE email = '' OR 1=1 --' AND password = '…'
```

`OR 1=1` всегда истинно, а `--` закомментировал проверку пароля — вход выполнен без пароля. Так же можно прочитать чужие данные или удалить таблицу.

**Защита — параметризованные запросы.** Значения передаются базе **отдельно** от текста SQL. База никогда не интерпретирует их как код — только как данные:

```ts
await pool.query("SELECT * FROM users WHERE email = $1", [email]);
```

Даже если `email` содержит кавычки и `OR 1=1`, база будет искать пользователя с таким странным email — и не найдёт.

**ORM и query builder'ы** (Prisma, Drizzle) параметризуют запросы сами. Опасны «сырые» запросы со строковой склейкой:

```ts
prisma.$queryRaw`SELECT * FROM users WHERE email = ${email}`;          // ✓ безопасно
prisma.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${email}'`); // ✗ инъекция
```

Шаблонная строка с тегом `$queryRaw` превращает `${…}` в параметры, а `Unsafe`-версия склеивает строку.

Дополнительные меры: у пользователя базы, под которым работает приложение, — минимальные права (не суперпользователь); имена таблиц и колонок, которые нельзя параметризовать, выбирать из белого списка.

@@@ sql-27 | join, ловушка
Почему `LEFT JOIN` превращается во `INNER JOIN`, если добавить условие в `WHERE`?
???
```sql
-- ✗ пользователи без оплаченных заказов пропадут
SELECT u.name, o.id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';

-- ✓ условие на правую таблицу — в ON
SELECT u.name, o.id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid';
```

У пользователей без подходящих заказов все поля `o` равны `NULL`, а `NULL = 'paid'` не даёт true — `WHERE` выбрасывает эти строки. Условие в `ON` только решает, какие заказы присоединить, и сохраняет всех пользователей.

Как запомнить: `ON` отвечает на вопрос «что приклеить», `WHERE` — «что оставить в итоге». Условие на **левую** таблицу (`u.country = 'RU'`) в `WHERE` безопасно, на **правую** в `LEFT JOIN` — почти всегда должно быть в `ON`. Исключение — намеренная проверка `o.id IS NULL`.

@@@ sql-28 | join
Что такое self join? Пример.
???
Соединение таблицы **с самой собой** — для иерархий и сравнения строк одной таблицы:

@@@ sql-29 | postgres, distinct on
Как в PostgreSQL выбрать последний заказ каждого пользователя?
???
`DISTINCT ON` оставляет первую строку в каждой группе согласно `ORDER BY`:

```sql
SELECT DISTINCT ON (user_id) user_id, id, created_at
FROM orders
ORDER BY user_id, created_at DESC;
```

Как работает: строки сортируются по `user_id`, а внутри — от новых заказов к старым. Из каждой группы с одинаковым `user_id` берётся первая — то есть самый свежий заказ.

`ORDER BY` должен начинаться с тех же выражений, что в `DISTINCT ON`. Переносимый вариант для любой СУБД — `row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC)` и фильтр `rn = 1`.

`DISTINCT ON` — особенность PostgreSQL: короче оконной функции и часто быстрее на индексе `(user_id, created_at DESC)`. Но взять «топ-3» им нельзя — только одну строку на группу.

@@@ sql-30 | задача, оконные функции
Как найти вторую по величине зарплату?
???
```sql
-- 1) через DISTINCT + OFFSET
SELECT DISTINCT salary
FROM salaries
ORDER BY salary DESC
OFFSET 1 LIMIT 1;

-- 2) через dense_rank — заодно видно, у кого она
SELECT emp, salary
FROM (
  SELECT emp, salary, dense_rank() OVER (ORDER BY salary DESC) AS r
  FROM salaries
) t
WHERE r = 2;
```

Ловушка: без `DISTINCT` (или с `row_number` вместо `dense_rank`) при двух одинаковых максимальных зарплатах «второй» окажется та же максимальная.

Пример: зарплаты 300, 300, 200. Без `DISTINCT` второй строкой будет 300. С `DISTINCT` уникальные значения 300, 200 — и вторая 200, что и требуется.

Ещё вариант без оконных функций: `SELECT max(salary) FROM salaries WHERE salary < (SELECT max(salary) FROM salaries)`. Если второй зарплаты нет (все одинаковые), он вернёт `NULL`, а первые два — пустой результат; на собесе стоит это проговорить.

@@@ sql-31 | задача, дубликаты
Как найти и удалить дубликаты, оставив одну запись?
???
Найти:

```sql
SELECT email, count(*)
FROM emails
GROUP BY email
HAVING count(*) > 1;
```

Удалить, оставив строку с наименьшим `id` (PostgreSQL):

```sql
DELETE FROM emails a
USING emails b
WHERE a.email = b.email
  AND a.id > b.id;
```

Как читать: для каждой строки `a` ищем строку `b` с тем же email, но меньшим id. Если такая нашлась — значит, `a` не первая, удаляем её. У самой первой строки (наименьший id) пары с меньшим id нет, она остаётся.

Вариант через оконную функцию — удобнее, если нужно оставить, например, самую свежую:

```sql
DELETE FROM emails
WHERE id IN (
  SELECT id FROM (
    SELECT id, row_number() OVER (PARTITION BY email ORDER BY created_at DESC) AS rn
    FROM emails
  ) t
  WHERE rn > 1
);
```

После чистки — уникальный индекс `CREATE UNIQUE INDEX ON emails (email)`, чтобы дубли не появились снова.

@@@ sql-32 | null, выражения
Что делают `COALESCE`, `NULLIF` и `CASE`?
???
- `COALESCE(a, b, c)` — первое не-`NULL` значение: `COALESCE(nickname, name, 'Аноним')`.
- `NULLIF(a, b)` — `NULL`, если `a = b`, иначе `a`. Классика — защита от деления на ноль: `total / NULLIF(count, 0)` вернёт `NULL` вместо ошибки.
- `CASE` — условие внутри запроса:

```sql
SELECT name,
       CASE WHEN manager_id IS NULL THEN 'boss' ELSE 'staff' END AS role
FROM users;
```

`CASE` работает как `if/else if/else`: условия проверяются сверху вниз, срабатывает первое истинное. Если ни одно не подошло и нет `ELSE` — результат `NULL`.

```sql
SELECT name,
       CASE
         WHEN score >= 90 THEN 'отлично'
         WHEN score >= 70 THEN 'хорошо'
         ELSE 'нужно подтянуть'
       END AS grade
FROM results;
```

Их часто комбинируют: `COALESCE(NULLIF(trim(nickname), ''), name)` — взять никнейм, но если он пустая строка или из пробелов, подставить имя.

`CASE` работает и внутри агрегатов: `sum(CASE WHEN status = 'paid' THEN amount ELSE 0 END)`.

@@@ sql-33 | индексы, postgres
Что такое частичный индекс, индекс по выражению и покрывающий индекс?
???
```sql
-- частичный: индексирует только нужные строки — меньше и быстрее
CREATE INDEX ON orders (user_id) WHERE status = 'new';

-- по выражению: для поиска без учёта регистра
CREATE INDEX ON users (lower(email));
-- используется запросом WHERE lower(email) = lower($1)

-- покрывающий: INCLUDE хранит доп. колонки в индексе,
-- запрос может обойтись без чтения таблицы (index-only scan)
CREATE INDEX ON orders (user_id) INCLUDE (total);
```

Частичный индекс используется, только если условие запроса совпадает с условием индекса или следует из него.

Когда что нужно:

- **частичный** — когда запросы касаются маленькой части таблицы: «новые заказы» из миллиона выполненных. Индекс крошечный и быстро обновляется. Ещё один популярный приём — уникальность только среди активных записей: `CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL`;
- **по выражению** — когда в `WHERE` стоит функция над колонкой. Выражение в запросе должно совпадать с выражением в индексе;
- **покрывающий** — когда запрос читает пару колонок: все нужные данные лежат прямо в индексе, и обращаться к таблице не нужно.

@@@ sql-34 | postgres, типы
`SERIAL` или `GENERATED AS IDENTITY`? Что выбрать для первичного ключа?
???
`GENERATED ... AS IDENTITY` — стандарт SQL, рекомендуемый в современном PostgreSQL. `SERIAL` — старый способ: это обычный `int` + отдельная последовательность, с ней проще ошибиться при правах и копировании таблиц.

```sql
CREATE TABLE users (
  id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text
);
INSERT INTO users (id, name) VALUES (5, 'x');
-- ошибка: cannot insert a non-DEFAULT value into column "id"
```

`ALWAYS` защищает от ручной вставки id, `BY DEFAULT` разрешает её. Для распределённых систем и публичных идентификаторов часто берут `uuid`.

Что не так с `SERIAL`: под капотом это колонка с `DEFAULT nextval('users_id_seq')` и отдельный объект-последовательность. Можно вставить id вручную, и последовательность об этом не узнает — следующая автоматическая вставка упадёт на дубликате. Права на последовательность нужно выдавать отдельно.

Для больших таблиц берут `bigint`: лимит `int` — около 2,1 млрд, и его реально исчерпать.

@@@ sql-35 | postgres, представления
Чем обычное представление (VIEW) отличается от материализованного?
???
- **VIEW** — сохранённый запрос. Данные не хранит, при каждом обращении выполняет запрос заново: всегда актуально, но не быстрее исходного запроса.
- **MATERIALIZED VIEW** — результат запроса **сохранён на диск**: читается быстро, можно индексировать, но устаревает, пока его не обновят.

```sql
CREATE MATERIALIZED VIEW sales_by_user AS
SELECT user_id, sum(total) AS total FROM orders GROUP BY user_id;

REFRESH MATERIALIZED VIEW sales_by_user;
-- без блокировки чтения, но нужен уникальный индекс:
CREATE UNIQUE INDEX ON sales_by_user (user_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY sales_by_user;
```

Подходит для отчётов и дашбордов, где допустимо небольшое отставание.

Зачем обычный VIEW, если он не ускоряет: чтобы спрятать сложный `JOIN` за простым именем (`SELECT * FROM active_customers`), выдать доступ к части колонок без доступа к таблице и не дублировать одинаковый запрос в коде.

Обновлять материализованное представление приходится самому — по расписанию (cron, `pg_cron`) или после изменения данных.

@@@ sql-36 | транзакции, блокировки
Оптимистичная или пессимистичная блокировка — в чём разница?
???
**Пессимистичная** — заблокировать строку заранее, другие ждут:

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

**Оптимистичная** — не блокировать, а при записи проверить, что строку никто не изменил (колонка `version`):

```sql
UPDATE accounts
SET balance = 50, version = version + 1
WHERE id = 1 AND version = 1;
-- 0 обновлённых строк = кто-то успел раньше → перечитать и повторить
```

Пессимистичная — при частых конфликтах и коротких транзакциях. Оптимистичная — когда конфликты редки, а держать блокировку долго нельзя (например, пока пользователь редактирует форму).

Названия отражают отношение к конфликтам: пессимист заранее уверен, что кто-то помешает, и запирает дверь. Оптимист верит, что никто не помешает, и только в конце проверяет, не изменилось ли что-то.

Пример с формой: два администратора открыли одну карточку товара. Первый сохранил, `version` стала 2. Второй жмёт «Сохранить» со старой `version = 1` — обновится 0 строк, и интерфейс скажет «данные изменились, обновите страницу», вместо того чтобы молча затереть чужие правки.

@@@ sql-37 | postgres, типы
`text`, `varchar(n)` или `char(n)` в PostgreSQL?
???
В PostgreSQL между ними **нет разницы в скорости**. `text` и `varchar` без ограничения — одно и то же по сути, `varchar(n)` лишь добавляет проверку длины.

`char(n)` дополняет строку пробелами до `n` и ведёт себя неочевидно (хвостовые пробелы игнорируются в сравнениях) — его почти не используют.

Практика: `text`, а ограничение длины, если нужно, — через `CHECK (char_length(name) <= 100)` или `varchar(n)`.

Почему `CHECK` удобнее: если лимит придётся увеличить, `varchar(100)` → `varchar(200)` меняется командой `ALTER`, а `CHECK` можно заменить, не трогая тип колонки. Важнее, что лимит длины — это бизнес-правило, и его всё равно нужно проверять в приложении, чтобы показать понятную ошибку.

Это особенность PostgreSQL: в других СУБД (например, MySQL) `varchar` и `text` хранятся и индексируются по-разному.

@@@ sql-38 | postgres, даты
`timestamp` или `timestamptz`?
???
Почти всегда `timestamptz` (`timestamp with time zone`). Он хранит **момент времени** (внутри — UTC) и при выводе переводит в часовой пояс сессии.

`timestamp` хранит «время на стенных часах» без пояса и **молча отбрасывает** смещение:

```sql
SET TIME ZONE 'Europe/Moscow';
SELECT '2026-01-01 12:00:00+00'::timestamptz; -- 2026-01-01 15:00:00+03
SELECT '2026-01-01 12:00:00+00'::timestamp;   -- 2026-01-01 12:00:00 (пояс потерян)
```

С `timestamp` события из разных часовых поясов становится невозможно корректно сравнить.

Несмотря на название, `timestamptz` **не хранит** часовой пояс — только момент в UTC. Пояс применяется при вводе и выводе. Оба типа занимают одинаково, 8 байт.

Когда уместен `timestamp`: «будильник на 9:00 по местному времени» или расписание магазина — где важно время на часах, а не момент. Для дат без времени (день рождения) есть тип `date`.

@@@ sql-39 | группировка, основы
Почему нельзя выбрать колонку, которой нет в `GROUP BY`?
???
После группировки от каждой группы остаётся **одна строка**. Если в группе пять заказов с разными датами, неясно, какую дату показать:

```sql
SELECT user_id, created_at, count(*)  -- ошибка: created_at не сгруппирован
FROM orders
GROUP BY user_id;
```

В `SELECT` можно указывать только колонки из `GROUP BY` и агрегаты: `max(created_at)`, `count(*)`, `string_agg(...)`.

Исключение в PostgreSQL: если сгруппировать по **первичному ключу**, можно брать остальные колонки той же таблицы — они однозначно определяются ключом:

```sql
SELECT u.id, u.name, count(o.id)
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;  -- u.name можно, потому что u.id — первичный ключ
```

MySQL в старых режимах разрешал любые колонки и возвращал случайное значение из группы — источник тихих багов.

Если нужна вся строка, а не агрегат (например, данные последнего заказа), это уже задача не для `GROUP BY`, а для `DISTINCT ON` или оконной функции.

@@@ sql-40 | связи, ограничения
Что делают `ON DELETE CASCADE`, `SET NULL` и `RESTRICT`?
???
Определяют, что случится с дочерними строками, когда удаляют родительскую:

```sql
CREATE TABLE comments (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  post_id bigint NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  user_id bigint REFERENCES users(id) ON DELETE SET NULL,
  rating  int CHECK (rating BETWEEN 1 AND 5)
);
```

- `CASCADE` — удалить детей вместе с родителем (комментарии вместе с постом);
- `SET NULL` — оставить детей, обнулив ссылку (комментарий остаётся, автор «удалён»);
- `RESTRICT` / `NO ACTION` (по умолчанию) — запретить удаление, пока есть дети. `NO ACTION` можно отложить до конца транзакции, `RESTRICT` проверяется сразу.

`CHECK` — произвольное условие на значения строки.

Ловушка, о которой часто спрашивают: PostgreSQL **не создаёт индекс** на колонке внешнего ключа автоматически. Без индекса на `comments.post_id` каждое удаление поста будет сканировать всю таблицу комментариев.

Ещё про `CASCADE`: каскад распространяется дальше по цепочке. Удаление пользователя может удалить его посты, а с ними — все комментарии к этим постам. Для важных данных лучше `RESTRICT` и явное удаление или «мягкое удаление» через колонку `deleted_at`.

@@@ sql-41 | связи, проектирование
Как в таблицах реализуются связи один-к-одному, один-ко-многим и многие-ко-многим?
???
**Один-ко-многим** — внешний ключ на стороне «многих»: у заказа есть `user_id`, у пользователя много заказов.

**Один-к-одному** — тот же внешний ключ, но с `UNIQUE`, чтобы на одного родителя была максимум одна строка:

```sql
CREATE TABLE profiles (
  user_id bigint PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  bio text
);
```

**Многие-ко-многим** — отдельная связующая таблица с двумя внешними ключами и составным первичным ключом:

```sql
CREATE TABLE user_roles (
  user_id bigint REFERENCES users(id) ON DELETE CASCADE,
  role_id bigint REFERENCES roles(id) ON DELETE CASCADE,
  granted_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, role_id)
);
```

Составной ключ не даёт выдать одну роль дважды. В связующую таблицу удобно класть данные о самой связи: дату, кто выдал, порядок.

Почему для «многие-ко-многим» нужна отдельная таблица: у пользователя много ролей, у роли много пользователей. Положить `role_id` в `users` нельзя — там поместится только одна роль. Хранить список через запятую нарушает 1НФ. Связующая таблица хранит каждую пару отдельной строкой.

Зачем один-к-одному, если можно добавить колонки в `users`: чтобы вынести редко нужные или тяжёлые данные (биография, настройки) и не читать их при каждом запросе пользователя.

@@@ sql-42 | индексы, производительность
Почему нельзя просто повесить индекс на каждую колонку?
???
Индекс ускоряет чтение, но у него есть цена:

- **Медленнее запись.** Каждый `INSERT`, `UPDATE` и `DELETE` обновляет все индексы таблицы. Десять индексов — десять дополнительных структур на каждую вставку.
- **Место на диске и в памяти.** Индексы конкурируют с данными за кэш, и в памяти помещается меньше полезного.
- **Нет HOT-обновлений.** Если меняется проиндексированная колонка, PostgreSQL не может обновить строку «на месте» — таблица и индексы разбухают быстрее.
- **Бесполезность при низкой селективности.** Индекс по `is_active`, где 95% строк `true`, планировщик просто проигнорирует.

Как правильно: индексы под **реальные запросы** (`WHERE`, `JOIN`, `ORDER BY`), составные — в нужном порядке колонок, проверка через `EXPLAIN ANALYZE`. Неиспользуемые индексы находят по `pg_stat_user_indexes`, где `idx_scan = 0`.

Ещё один довод: десять одиночных индексов по колонкам не заменят один правильный составной. Запрос `WHERE user_id = 1 AND status = 'new' ORDER BY created_at` лучше всего обслужит индекс `(user_id, status, created_at)`.

@@@ sql-43 | индексы, postgres
Какие типы индексов есть в PostgreSQL?
???
- **B-tree** (по умолчанию) — равенство, диапазоны (`<`, `BETWEEN`), сортировка, `LIKE 'abc%'`. Подходит в 90% случаев.
- **Hash** — только равенство `=`. Бывает компактнее B-tree для длинных значений, но не умеет диапазоны и сортировку.
- **GIN** — «обратный» индекс для значений, внутри которых много элементов: массивы (`@>`), `jsonb`, полнотекстовый поиск, поиск по подстроке через `pg_trgm`.
- **GiST** — геометрия и PostGIS, диапазоны (`tstzrange`), поиск ближайших соседей, exclusion constraints («бронирования не пересекаются»).
- **BRIN** — очень маленький индекс для огромных таблиц, где данные физически упорядочены: логи и события по времени вставки.

```sql
CREATE INDEX ON products USING gin (tags);           -- WHERE tags @> '{sale}'
CREATE INDEX ON events USING brin (created_at);       -- миллиарды строк логов
```

Почему GIN называют «обратным»: он хранит не «строка → значения», а «элемент → список строк, где он встречается». Как указатель в книге: слово «react» → страницы 12, 45, 101. Поэтому быстро отвечает на вопрос «в каких постах есть тег sale».

BRIN хранит только минимум и максимум для каждого блока страниц — поэтому он в сотни раз меньше B-tree, но полезен, только если значения в таблице идут по порядку.

@@@ sql-44 | поиск, индексы
Как быстро искать по подстроке, если `LIKE '%текст%'` не использует индекс?
???
B-tree хранит значения отсортированными, поэтому умеет искать только по **началу** строки (`LIKE 'abc%'`). Шаблон с `%` в начале требует проверить каждую строку.

**Вариант 1 — триграммы** (`pg_trgm`). Строка разбивается на тройки символов, GIN-индекс по ним ускоряет `LIKE` и `ILIKE` с любым положением подстроки:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX products_name_trgm ON products USING gin (name gin_trgm_ops);

SELECT * FROM products WHERE name ILIKE '%телефон%';
```

Ещё умеет нечёткий поиск с опечатками: `similarity(name, 'тилефон')`.

**Вариант 2 — полнотекстовый поиск.** Слова приводятся к основе (стемминг), поэтому по запросу «кошки» найдутся «кошка», «кошку», «кошкой». Стеммер работает по правилам, а не по словарю: форму с беглой гласной «кошек» он не свяжет — для этого подключают словари (hunspell).

```sql
CREATE INDEX ON posts USING gin (to_tsvector('russian', body));

SELECT * FROM posts
WHERE to_tsvector('russian', body) @@ plainto_tsquery('russian', 'кошки');
```

Для сложного поиска с ранжированием, фасетами и подсказками берут Elasticsearch или Meilisearch.

Как выбрать: поиск по названию товара или имени, части слова, опечаткам — триграммы. Поиск по статьям и описаниям, где важны слова и их формы, — полнотекстовый.

@@@ sql-45 | оконные функции
Как посчитать нарастающий итог и разницу с предыдущей строкой?
???
Оконные функции с `ORDER BY` внутри `OVER`:

```sql
SELECT
  day,
  revenue,
  sum(revenue) OVER (ORDER BY day) AS running_total,
  revenue - lag(revenue) OVER (ORDER BY day) AS diff,
  avg(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg_7d
FROM daily_revenue;
```

- `sum(...) OVER (ORDER BY day)` — сумма от первой строки до текущей;
- `lag(col)` — значение из предыдущей строки (`lead` — из следующей); для первой строки — `NULL`;
- `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` — скользящее окно из 7 строк, например среднее за неделю.

Ловушка: рамка по умолчанию — `RANGE`, а не `ROWS`. Строки с одинаковым значением `day` получат **одинаковый** нарастающий итог — сразу с учётом их всех. Если нужен построчный итог, укажи `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` или сделай сортировку уникальной.

`lag(revenue, 1, 0)` — второй аргумент задаёт сдвиг, третий — значение по умолчанию вместо `NULL` для первой строки.

@@@ sql-46 | оконные функции, группировка
Чем `PARTITION BY` отличается от `GROUP BY`?
???
`GROUP BY` **схлопывает** строки: из десяти сотрудников отдела остаётся одна строка с агрегатом.

`PARTITION BY` в оконной функции считает агрегат по группе, но **оставляет все строки** — к каждой добавляется результат:

```sql
SELECT
  name,
  department,
  salary,
  avg(salary) OVER (PARTITION BY department) AS dept_avg,
  salary - avg(salary) OVER (PARTITION BY department) AS diff
FROM employees;
```

Каждый сотрудник видит среднюю зарплату своего отдела и разницу с ней. Через `GROUP BY` пришлось бы делать подзапрос и `JOIN`.

Как выбрать: нужен итог по группам (отчёт «отдел — средняя зарплата») — `GROUP BY`. Нужны строки плюс контекст группы (доля, место, отклонение от среднего) — окно.

Если одно и то же окно используется несколько раз, его можно объявить один раз: `… OVER w … WINDOW w AS (PARTITION BY department)`.

@@@ sql-47 | агрегаты, postgres
Как посчитать несколько условных агрегатов одним запросом?
???
В PostgreSQL у любого агрегата есть `FILTER`:

```sql
SELECT
  user_id,
  count(*)                                    AS total,
  count(*) FILTER (WHERE status = 'paid')     AS paid,
  count(*) FILTER (WHERE status = 'canceled') AS canceled,
  sum(amount) FILTER (WHERE status = 'paid')  AS revenue
FROM orders
GROUP BY user_id;
```

Это один проход по таблице вместо трёх запросов. В других СУБД то же делают через `sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END)`.

Склеить значения группы в строку, массив или JSON:

```sql
SELECT
  post_id,
  string_agg(tag, ', ' ORDER BY tag) AS tags,   -- 'css, react'
  array_agg(tag)                     AS tag_list,
  json_agg(json_build_object('id', id, 'tag', tag)) AS tag_json
FROM post_tags
GROUP BY post_id;
```

`json_agg` удобен, чтобы получить вложенные данные одним запросом, без N+1.

Такой запрос — типичная основа для дашборда: одна строка на пользователя со всеми нужными цифрами сразу.

@@@ sql-48 | проектирование, денормализация
Что такое денормализация и когда она оправдана?
???
Сознательное дублирование данных ради быстрого чтения. Примеры:

- счётчик `comments_count` в таблице постов вместо `count(*)` на каждый показ;
- `author_name` в заказе, чтобы не делать `JOIN` (и сохранить имя на момент покупки);
- готовая таблица с отчётом по дням вместо агрегации миллионов строк.

Цена — **согласованность**. При каждом новом комментарии счётчик нужно обновить в той же транзакции или триггером, иначе данные разъедутся.

```sql
BEGIN;
INSERT INTO comments (post_id, body) VALUES (1, 'Отлично!');
UPDATE posts SET comments_count = comments_count + 1 WHERE id = 1;
COMMIT;
```

Порядок действий: сначала нормализованная схема и индексы. Денормализовать — когда замеры показали, что чтение действительно узкое место. Альтернативы: материализованное представление или кэш.

Иногда дублирование нужно бизнесу, а не скорости: цена товара в заказе должна остаться прежней, даже если в каталоге её поменяли.

@@@ sql-49 | масштабирование
Чем отличаются репликация, партиционирование и шардирование?
???
- **Репликация** — полные копии одной базы на нескольких серверах. Пишут в основной (primary), читают в том числе с реплик. Даёт отказоустойчивость и масштабирование **чтения**.
- **Партиционирование** — одна большая таблица делится на части **внутри одного сервера**, например по месяцам. Запрос за октябрь читает только нужную часть, старые данные легко удалить целой партицией.
- **Шардирование** — данные делятся между **разными серверами** по ключу (например, `user_id`). Масштабирует **запись** и объём, но сложнее всего.

```sql
CREATE TABLE events (id bigint, created_at timestamptz, payload jsonb)
  PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

Подводные камни: у реплик есть **задержка** (пользователь сохранил профиль, а с реплики прочитал старый), а при шардировании трудно делать `JOIN` и транзакции между шардами.

Аналогия с библиотекой: репликация — несколько одинаковых библиотек в разных районах; партиционирование — одна библиотека, где книги разложены по залам по годам; шардирование — разные библиотеки хранят разные книги (А–М в одной, Н–Я в другой).

@@@ sql-50 | блокировки, очередь
Как сделать очередь задач на PostgreSQL?
???
Несколько воркеров должны забирать задачи, не мешая друг другу и не беря одну задачу дважды. Для этого есть `FOR UPDATE SKIP LOCKED`:

```sql
UPDATE jobs
SET status = 'running', started_at = now()
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'queued'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

- `FOR UPDATE` блокирует выбранную строку до конца транзакции;
- `SKIP LOCKED` пропускает строки, которые уже заблокировал другой воркер, — без ожидания;
- `RETURNING` сразу отдаёт задачу воркеру.

Без `SKIP LOCKED` воркеры выстроились бы в очередь за одной и той же строкой.

Так устроены библиотеки вроде pg-boss и graphile-worker: отдельный брокер (Redis, RabbitMQ) для небольших и средних нагрузок не нужен, а задача создаётся в той же транзакции, что и бизнес-данные.

Последнее — серьёзное преимущество: если заказ сохранился, задача «отправить письмо» гарантированно тоже создана. С внешним брокером одно могло пройти, а другое — нет.

@@@ sql-51 | соединения, serverless
Что такое пул соединений и зачем PgBouncer?
???
Каждое соединение с PostgreSQL — отдельный процесс на сервере, который занимает память и долго устанавливается. По умолчанию `max_connections = 100`.

Проблема serverless: каждая функция на Vercel может открыть своё соединение. Сто параллельных запросов — сто соединений, и база отвечает `too many connections`.

**Пул** держит небольшое число постоянных соединений и раздаёт их запросам по очереди:

- внутри приложения — пул драйвера (`pg.Pool`) или ORM;
- снаружи — PgBouncer или встроенный пулер хостинга (у Neon и Supabase есть отдельный «pooled» URL).

Режим **transaction pooling** отдаёт соединение только на время транзакции, поэтому ломает то, что живёт на уровне сессии: `SET` без `LOCAL`, `LISTEN/NOTIFY`, сессионные advisory-блокировки.

Практика с Prisma: приложение ходит через pooled URL, а миграции — через прямое (direct) соединение.

Аналогия — такси в аэропорту: вместо того чтобы каждому пассажиру покупать машину (соединение), есть стоянка из 20 машин, которые возят всех по очереди.

@@@ sql-52 | первичный ключ, uuid
UUID или `bigint` для первичного ключа?
???
**`bigint` (identity)**:

- 8 байт, компактные индексы;
- последовательный — новые строки дописываются в конец индекса, вставка быстрая;
- но легко перебрать (`/orders/1001`, `/orders/1002`) и видно, сколько у вас заказов.

**UUID v4** (`gen_random_uuid()`):

- 16 байт;
- можно сгенерировать на клиенте до сохранения, удобно для офлайна и слияния баз;
- не угадывается;
- но случайный: вставки разбрасываются по всему индексу, индекс фрагментируется и хуже помещается в кэш.

**UUID v7** — компромисс: начинается с метки времени, поэтому упорядочен почти как `bigint`, но остаётся уникальным глобально. В PostgreSQL 18 есть встроенная функция `uuidv7()`.

Частая схема: `bigint` как внутренний ключ для связей и отдельный публичный идентификатор (UUID или короткий id) для URL и API.

Хранить UUID нужно в типе `uuid`, а не `text`: строка занимает 36+ байт против 16, и сравнение медленнее.

@@@ sql-53 | postgres, returning
Что делает `RETURNING` в PostgreSQL?
???
Возвращает строки, которые затронул `INSERT`, `UPDATE` или `DELETE`, — без отдельного `SELECT`:

```sql
INSERT INTO users (email) VALUES ('ann@example.com')
RETURNING id, created_at;

UPDATE products SET stock = stock - 1
WHERE id = 42 AND stock > 0
RETURNING stock;            -- пусто, если товар закончился

DELETE FROM sessions WHERE expires_at < now()
RETURNING user_id;
```

Зачем:

- получить сгенерированный id и значения по умолчанию сразу после вставки;
- атомарно изменить и узнать результат — между `UPDATE` и `SELECT` никто не вклинится;
- меньше запросов к базе.

С CTE можно перенести данные одним запросом: `WITH moved AS (DELETE FROM queue … RETURNING *) INSERT INTO archive SELECT * FROM moved`.

Prisma использует `RETURNING` под капотом, когда возвращает созданную запись. В PostgreSQL 18 в `RETURNING` можно получить и старые значения: `RETURNING old.price, new.price`.

Пример со складом показывает главную пользу: условие `stock > 0` и уменьшение выполняются одной командой. Если два покупателя одновременно берут последний товар, один получит строку, а второй — пустой результат, и продажи в минус не будет.

@@@ sql-54 | null, сортировка, unique
Как `NULL` ведёт себя в `ORDER BY` и в уникальных ограничениях?
???
**Сортировка.** В PostgreSQL `NULL` считается **больше** любого значения: при `ASC` он в конце, при `DESC` — в начале. Это часто ломает «сортировку по рейтингу»: товары без рейтинга оказываются наверху.

```sql
SELECT * FROM products ORDER BY rating DESC NULLS LAST;
```

Индекс тоже можно создать с `NULLS LAST`, чтобы он подходил под такую сортировку.

**Уникальность.** `NULL` не равен другому `NULL`, поэтому в колонке с `UNIQUE` может быть сколько угодно `NULL`:

```sql
CREATE TABLE users (email text UNIQUE);
INSERT INTO users VALUES (NULL), (NULL);  -- обе строки вставятся
```

Обычно это и нужно (email необязательный, но если указан — уникальный). Если нужно иначе, в PostgreSQL 15+ есть `UNIQUE NULLS NOT DISTINCT`.

Логика та же, что и везде с `NULL`: два «неизвестных» значения нельзя считать одинаковыми, поэтому уникальность не нарушается.

@@@ sql-55 | даты, ловушка
Почему `created_at BETWEEN '2026-01-01' AND '2026-01-31'` теряет данные?
???
`BETWEEN` включает обе границы, а строка `'2026-01-31'` для `timestamp` означает `2026-01-31 00:00:00`. Всё, что создано 31 января после полуночи, в выборку **не попадёт**.

Правильно — полуинтервал «от включительно, до исключительно»:

```sql
SELECT * FROM orders
WHERE created_at >= '2026-01-01'
  AND created_at <  '2026-02-01';
```

Плюсы: не нужно знать, сколько дней в месяце, нет проблем с долями секунды, а соседние периоды не пересекаются и не теряют строки на стыке.

Вторая ловушка — часовой пояс. Для `timestamptz` граница `'2026-01-01'` трактуется в часовом поясе сессии. Если отчёт нужен по московскому времени, укажи пояс явно: `'2026-01-01 00:00+03'`.

Ещё один анти-паттерн: `WHERE date(created_at) = '2026-01-15'` — функция над колонкой мешает использовать обычный индекс по `created_at`.

Почему не `'2026-01-31 23:59:59'`: заказ в `23:59:59.500` всё равно потеряется — у `timestamp` есть доли секунды.

@@@ sql-56 | задача, join
Как найти пользователей, у которых нет ни одного заказа?
???
Три способа:

```sql
-- 1. NOT EXISTS — обычно лучший вариант
SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- 2. LEFT JOIN + проверка на NULL
SELECT u.* FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

-- 3. NOT IN — с ловушкой
SELECT * FROM users
WHERE id NOT IN (SELECT user_id FROM orders);
```

Первые два PostgreSQL выполняет одинаково эффективно (anti join).

`NOT IN` опасен: если в подзапросе встретится хотя бы один `NULL` (например, заказ без пользователя), результат будет **пустым**. Сравнение `id <> NULL` даёт «неизвестно», и строка отбрасывается.

В варианте с `LEFT JOIN` проверяй на `NULL` колонку, которая в найденной строке не может быть пустой, — первичный ключ `o.id`.

**Anti join** — операция «оставить строки слева, для которых справа нет пары». Чтобы она была быстрой, нужен индекс по `orders.user_id`.

@@@ sql-57 | задача, оконные функции
Как выбрать топ-3 товара по продажам в каждой категории?
???
Пронумеровать строки внутри каждой категории и отфильтровать во внешнем запросе:

```sql
SELECT category_id, name, sales
FROM (
  SELECT
    p.*,
    row_number() OVER (PARTITION BY category_id ORDER BY sales DESC) AS rn
  FROM products p
) ranked
WHERE rn <= 3
ORDER BY category_id, rn;
```

Фильтровать по `rn` прямо в `WHERE` нельзя: оконные функции вычисляются на этапе `SELECT`, уже после `WHERE`.

Если при равенстве продаж нужно взять **всех** претендентов на третье место, замени `row_number` на `dense_rank`.

Альтернатива в PostgreSQL — `LATERAL`: для каждой категории выполнить подзапрос с `LIMIT 3`. Это быстрее, когда категорий мало, а товаров много и есть индекс `(category_id, sales DESC)`:

```sql
SELECT c.id, top.*
FROM categories c
CROSS JOIN LATERAL (
  SELECT name, sales FROM products
  WHERE category_id = c.id
  ORDER BY sales DESC
  LIMIT 3
) top;
```

Почему `LATERAL` бывает быстрее: оконная функция нумерует **все** товары, а `LATERAL` с индексом читает по три строки на категорию и останавливается.

@@@ sql-58 | задача, даты
Как посчитать заказы по месяцам, включая месяцы без заказов?
???
Группировка по началу месяца через `date_trunc`:

```sql
SELECT date_trunc('month', created_at) AS month, count(*) AS orders
FROM orders
GROUP BY 1
ORDER BY 1;
```

Месяцы без заказов здесь просто пропадут, а графику нужны нули. Сгенерируем все месяцы и присоединим данные:

```sql
SELECT m.month, count(o.id) AS orders
FROM generate_series('2026-01-01'::date, '2026-12-01'::date, interval '1 month') AS m(month)
LEFT JOIN orders o
  ON o.created_at >= m.month
 AND o.created_at <  m.month + interval '1 month'
GROUP BY m.month
ORDER BY m.month;
```

- `count(o.id)`, а не `count(*)` — иначе пустые месяцы получат 1;
- условие в `ON`, а не в `WHERE` — иначе `LEFT JOIN` превратится во внутренний;
- для `timestamptz` границы месяца зависят от часового пояса сессии — для отчёта в нужном поясе используй `created_at AT TIME ZONE 'Europe/Moscow'`.

`date_trunc('month', …)` обрезает дату до начала месяца: `2026-03-17 14:05` → `2026-03-01 00:00`. `GROUP BY 1` — группировать по первой колонке из `SELECT`.

@@@ sql-59 | postgres, lateral
Что такое `LATERAL JOIN`?
???
Обычный подзапрос в `FROM` не видит колонки соседних таблиц. `LATERAL` разрешает подзапросу ссылаться на строки, стоящие **левее**, — он выполняется для каждой из них, как цикл:

```sql
-- три последних заказа каждого пользователя
SELECT u.name, o.id, o.total
FROM users u
LEFT JOIN LATERAL (
  SELECT id, total
  FROM orders
  WHERE orders.user_id = u.id
  ORDER BY created_at DESC
  LIMIT 3
) o ON true;
```

- `LEFT JOIN LATERAL … ON true` оставляет пользователей без заказов (с `NULL`);
- `CROSS JOIN LATERAL` выбросит их.

Где полезен: «топ-N в каждой группе», несколько колонок из одного коррелированного подзапроса, вызов функций, которые возвращают набор строк (`jsonb_array_elements`, `unnest`), для каждой строки.

С индексом `orders (user_id, created_at DESC)` такой запрос очень быстрый: для каждого пользователя читаются ровно три записи.

Мысленная модель — цикл `for (const u of users) { подзапрос(u) }`. `ON true` нужен, потому что условие связи уже стоит внутри подзапроса.
