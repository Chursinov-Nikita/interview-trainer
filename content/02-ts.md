@@@ ts-01 | основы
Чем `type` отличается от `interface`?
???
Оба умеют описывать форму объекта, и в большинстве случаев взаимозаменяемы:

```ts
interface User { id: number; name: string }
type User2 = { id: number; name: string };
```

Отличия:

- **Только `interface`** поддерживает **declaration merging**: два объявления с одним именем сливаются в одно. Так расширяют чужие типы (`Window`, `Session` из next-auth). Повторный `type` с тем же именем — ошибка.
- **Только `type`** умеет всё, что не является объектом: union (`"a" | "b"`), кортежи, примитивы, mapped и conditional types.
- **Расширение**: `interface B extends A` при конфликте полей сразу даёт понятную ошибку. А `type B = A & { ... }` молча превращает конфликтующее поле в `never`, и проблема всплывёт позже.

```ts
type Status = "idle" | "loading";        // interface так не умеет
interface Admin extends User { role: "admin" }
type Admin2 = User & { role: "admin" };   // то же через пересечение
```

Компилятор кэширует интерфейсы, поэтому в больших проектах глубокие иерархии через `extends` проверяются чуть быстрее, чем цепочки `&`.

На практике: `interface` — для объектных контрактов и публичного API библиотек, `type` — для union и вычисляемых типов. Главное — договориться и писать единообразно.

@@@ ts-02 | основы, unknown, never
`any`, `unknown` и `never` — в чём разница?
???
- **`any`** — полностью отключает проверку типов. С таким значением можно сделать что угодно: вызвать несуществующий метод, передать куда угодно. Хуже того, `any` «заражает»: результат операции с ним тоже становится `any`, и ошибки расползаются по коду.
- **`unknown`** — «здесь может быть что угодно, но сначала проверь». Присвоить в `unknown` можно любое значение, а **использовать** его нельзя, пока не сузишь тип проверкой. Это безопасная замена `any` для данных извне: ответов API, `JSON.parse`, `catch (e)`.
- **`never`** — тип, у которого нет ни одного значения. Его получают функции, которые никогда не завершаются нормально (всегда бросают ошибку или бесконечный цикл), пустой union и ветка, в которую код никогда не попадёт.

```ts
function parse(raw: unknown) {
  raw.trim();                                     // ошибка: unknown нельзя использовать
  if (typeof raw === "string") return raw.trim(); // здесь raw: string
  throw new Error("not a string");                // дальше этой строки — never
}

const data: any = 42;
data.foo.bar(); // компилируется, но упадёт в рантайме
```

Простое правило: если не знаешь тип — пиши `unknown`, а не `any`. `never` чаще всего используют для проверки, что в `switch` обработаны все варианты (exhaustive check).

@@@ ts-03 | generics
Что такое дженерики? Приведи пример с ограничением.
???
Дженерик — это **параметр типа**: функция или тип получает тип как аргумент, примерно как функция получает значение. Это нужно, чтобы код работал с разными типами и при этом не терял связь между входом и выходом.

Без дженерика пришлось бы выбирать между конкретным типом и `any`:

```ts
function firstAny(items: any[]): any { return items[0]; }
const a = firstAny([1, 2]); // any — тип потерян

function first<T>(items: T[]): T | undefined {
  return items[0];
}
const n = first([1, 2]);     // number — T вывелся из аргумента
const s = first(["a", "b"]); // string
```

TS сам выводит `T` из переданного массива, указывать его вручную (`first<number>(...)`) обычно не нужно.

**Ограничение (`extends`)** говорит: `T` может быть любым типом, но обязательно с определёнными полями:

```ts
function byId<T extends { id: string }>(items: T[], id: string) {
  return items.find((i) => i.id === id); // можно обращаться к .id
}

byId(users, "42");   // вернёт User | undefined, а не просто { id: string }
byId([1, 2], "42");  // ошибка: у number нет id
```

Без `extends` обращаться к `.id` нельзя: `T` может оказаться чем угодно, хоть числом. При этом возвращается **исходный** тип `T` со всеми его полями — в этом и смысл дженерика.

@@@ ts-04 | keyof, typeof
Что делают `keyof` и `typeof` на уровне типов?
???
**`typeof значение`** в позиции типа берёт тип из существующей переменной. Это позволяет не описывать тип вручную, а вывести его из кода:

```ts
const config = { theme: "dark", lang: "ru" };
type Config = typeof config; // { theme: string; lang: string }
```

Не путай с JS-оператором `typeof x === "string"` — тот работает в рантайме и возвращает строку. TS-версия работает только в типах.

**`keyof Тип`** даёт union имён всех ключей типа:

```ts
type Key = keyof Config; // "theme" | "lang"
```

Вместе они позволяют писать типобезопасный доступ к полям:

```ts
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

get(config, "theme"); // string
get(config, "color"); // ошибка: такого ключа нет
```

Здесь `K extends keyof T` — «ключ должен быть одним из ключей `obj`», а `T[K]` — тип значения по этому ключу. IDE при этом подсказывает доступные ключи.

Частая связка: `keyof typeof obj` — union ключей конкретного объекта-константы.

@@@ ts-05 | indexed access, as const
Что такое indexed access types? Как получить тип элемента массива?
???
`T[K]` — «тип свойства `K` в типе `T`». Синтаксис как у доступа к полю объекта, только на уровне типов:

```ts
type User = { id: number; roles: ("admin" | "user")[] };
type Id = User["id"];              // number
type Roles = User["roles"];        // ("admin" | "user")[]
type Role = User["roles"][number]; // "admin" | "user"
```

`[number]` означает «тип по любому числовому индексу», то есть тип элемента массива.

Главный практический приём — список значений хранится в коде **один раз**, а тип выводится из него:

```ts
const SIZES = ["s", "m", "l"] as const;
type Size = (typeof SIZES)[number]; // "s" | "m" | "l"

SIZES.map((s) => <option key={s}>{s}</option>); // массив для рендера
function setSize(size: Size) {}                 // тип для проверки
```

Без `as const` массив имел бы тип `string[]`, и `Size` стал бы просто `string`.

Плюс: добавил `"xl"` в массив — тип обновился сам, и всё остаётся согласованным. Так сделаны оценки в этом приложении.

Можно брать и несколько полей сразу: `User["id" | "roles"]` даст union их типов.

@@@ ts-06 | utility types
Назови основные utility types.
???
Это встроенные типы-«функции», которые преобразуют другие типы. Самые нужные:

**Для объектов:**

- `Partial<T>` — все поля необязательные. Для патчей и форм: `update(id, patch: Partial<User>)`.
- `Required<T>` — все поля обязательные.
- `Readonly<T>` — все поля только для чтения.
- `Pick<T, "a" | "b">` — оставить только указанные поля.
- `Omit<T, "password">` — убрать указанные поля. Например, публичный профиль без пароля.
- `Record<K, V>` — объект с ключами `K` и значениями `V`: `Record<Status, string>`.

**Для union:**

- `Exclude<U, X>` — убрать члены union: `Exclude<"a" | "b" | "c", "a">` → `"b" | "c"`.
- `Extract<U, X>` — оставить только подходящие.
- `NonNullable<T>` — убрать `null` и `undefined`.

**Для функций и промисов:**

- `ReturnType<typeof fn>` — тип результата функции.
- `Parameters<typeof fn>` — кортеж типов аргументов.
- `Awaited<T>` — что лежит внутри промиса.

```ts
type User = { id: number; name: string; password: string };
type PublicUser = Omit<User, "password">;        // { id; name }
type UserPatch = Partial<Pick<User, "name">>;    // { name?: string }
type Labels = Record<"idle" | "error", string>;  // { idle: string; error: string }
```

Utility types можно комбинировать, как в примере с `Partial<Pick<...>>`.

@@@ ts-07 | mapped types
Что такое mapped types? Напиши свой `Partial`.
???
Mapped type — это «цикл по ключам» на уровне типов. Синтаксис `{ [K in Ключи]: Тип }` создаёт объектный тип, перебирая каждый ключ:

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] };
```

Читается так: «для каждого ключа `K` из `T` создай необязательное поле с тем же типом `T[K]`». Именно так устроены встроенные `Partial`, `Readonly`, `Required`.

```ts
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };

type User = { id: number; name: string };
type Draft = MyPartial<User>; // { id?: number; name?: string }
```

Модификаторы можно не только добавлять, но и **снимать** минусом:

```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type Concrete<T> = { [K in keyof T]-?: T[K] }; // это и есть Required
```

Ключи можно **переименовывать** через `as`:

```ts
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};
type G = Getters<User>; // { getId: () => number; getName: () => string }
```

Перебирать можно и обычный union: `{ [K in "a" | "b"]: number }` даст `{ a: number; b: number }` — так устроен `Record`.

@@@ ts-08 | conditional types
Что такое условные типы? Что значит «дистрибутивность»?
???
Условный тип — тернарный оператор на уровне типов: `T extends U ? X : Y`. «Если `T` подходит под `U`, то тип `X`, иначе `Y`». Слово `extends` здесь означает «совместим с», а не наследование.

```ts
type IsString<T> = T extends string ? true : false;
type A = IsString<"hi">; // true
type B = IsString<42>;   // false
```

Сами по себе они редко нужны, но на них построены `Exclude`, `Extract`, `NonNullable`, `ReturnType`.

**Дистрибутивность.** Если в условие подставить union, а проверяемый тип — «голый» параметр `T`, условие применится **к каждому члену union отдельно**, и результаты соберутся обратно в union:

```ts
type ToArray<T> = T extends unknown ? T[] : never;
type C = ToArray<string | number>;
// = ToArray<string> | ToArray<number>
// = string[] | number[]
```

Именно поэтому работает `Exclude`:

```ts
type MyExclude<T, U> = T extends U ? never : T;
type D = MyExclude<"a" | "b" | "c", "a">; // never | "b" | "c" = "b" | "c"
```

`never` в union исчезает, остаётся то, что нужно.

Отключить дистрибутивность — обернуть обе стороны в кортеж: `[T] extends [unknown] ? T[] : never` даст `(string | number)[]` — один массив со смешанными элементами.

@@@ ts-09 | infer, conditional types
Для чего нужно ключевое слово `infer`?
???
`infer` — «вытащи этот тип и дай ему имя». Работает только внутри условного типа: ты описываешь шаблон, а TS сам подставляет на место `infer X` подходящую часть.

Аналогия — деструктуризация, только для типов:

```ts
type Unwrap<T> = T extends Promise<infer V> ? V : T;
type A = Unwrap<Promise<number>>; // number — V «вытащился» из Promise<…>
type B = Unwrap<string>;          // string — не промис, возвращаем как есть
```

Читается так: «если `T` выглядит как `Promise<что-то>`, назови это что-то `V` и верни его».

Так устроены встроенные утилиты:

```ts
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;
type MyParameters<F> = F extends (...args: infer P) => any ? P : never;
type ElementOf<T> = T extends (infer E)[] ? E : never;

type R = MyReturnType<() => Promise<number>>; // Promise<number>
type E = ElementOf<string[]>;                  // string
```

`infer` работает и в шаблонных строках:

```ts
type Id<T> = T extends `user_${infer N}` ? N : never;
type N = Id<"user_42">; // "42"
```

Где пригодится: достать тип пропсов из компонента, данные из ответа API, параметры маршрута из строки `"/users/:id"`.

@@@ ts-10 | narrowing, type guards
Как сужать типы? Что такое type guard?
???
**Сужение (narrowing)** — TS понимает тип точнее после проверки в коде. До `if` переменная `string | number`, внутри ветки `typeof x === "string"` — уже точно `string`.

Проверки, которые TS понимает сам:

```ts
function show(x: string | number | Date | null) {
  if (x === null) return;              // дальше x не null
  if (typeof x === "string") x.trim(); // string
  else if (x instanceof Date) x.getTime(); // Date
  else x.toFixed();                    // осталось только number
}

if ("swim" in pet) pet.swim();         // проверка наличия поля
if (user) user.name;                   // проверка на truthy
```

Обрати внимание на последнюю ветку `else`: TS отбросил всё уже проверенное и понял, что остался только `number`.

**Type guard** — своя функция-проверка, которая сообщает TS результат. Её тип возврата пишется как `pet is Fish`:

```ts
type Fish = { swim(): void };
type Bird = { fly(): void };

function isFish(pet: Fish | Bird): pet is Fish {
  return "swim" in pet;
}

if (isFish(pet)) pet.swim(); // pet: Fish
else pet.fly();              // pet: Bird
```

Если бы функция возвращала просто `boolean`, TS не связал бы результат с типом `pet`. Важно: TS **верит** предикату на слово — если внутри ошибка в логике, типы будут врать.

Есть ещё assertion-функции: `function assert(x: unknown): asserts x is string` — после её вызова тип сужен до конца блока.

@@@ ts-11 | union, never
Что такое discriminated union и exhaustive check?
???
**Discriminated union** — union из объектов, у которых есть общее поле с **литеральным** значением (дискриминант). Обычно его называют `type`, `kind` или `status`. Проверив это поле, TS точно знает, какой из вариантов перед ним и какие поля доступны.

```ts
type State =
  | { status: "loading" }
  | { status: "error"; error: string }
  | { status: "ok"; data: string[] };

function render(s: State) {
  switch (s.status) {
    case "loading": return "…";
    case "error": return s.error;        // здесь TS знает, что есть error
    case "ok": return s.data.join();     // а здесь — data
    default: {
      const never: never = s; // новый статус → ошибка компиляции здесь
      return never;
    }
  }
}
```

Зачем это нужно: невозможно описать «невозможное» состояние. С отдельными полями `{ loading: boolean; error?: string; data?: string[] }` легко получить `loading: true` и одновременно `error` — с union так нельзя.

**Exhaustive check** — приём в `default`. Если все варианты обработаны, в `default` у `s` остаётся тип `never`, и присвоить его в `never` можно. Когда кто-то добавит `{ status: "empty" }`, в `default` попадёт этот новый вариант, присвоение в `never` станет ошибкой — и компилятор покажет все `switch`, которые нужно дополнить.

Так типизируют состояния запросов, экшены Redux и `useReducer`, ответы API.

@@@ ts-12 | satisfies
Что делает оператор `satisfies` и чем он лучше аннотации?
???
`satisfies` **проверяет**, что значение подходит под тип, но **оставляет** переменной тот тип, который TS вывел сам — точный и узкий.

Аннотация `const a: Type = …` делает наоборот: проверяет и **заменяет** выведенный тип на `Type`. Детали теряются:

```ts
type Colors = Record<string, string | [number, number, number]>;

const a: Colors = { red: [255, 0, 0], blue: "#00f" };
a.red.map;          // ошибка: для TS a.red — string | кортеж
a.green;            // компилируется, хотя green нет

const b = { red: [255, 0, 0], blue: "#00f" } satisfies Colors;
b.red.map;          // ок: TS помнит, что red — кортеж
b.blue.toUpperCase(); // ок: blue — строка
b.green;            // ошибка: такого ключа нет
```

Что даёт `satisfies`:

- проверку структуры и опечаток в ключах, как у аннотации;
- точные типы полей, литералы и список конкретных ключей;
- удобно для конфигов, словарей переводов, карт маршрутов.

```ts
const routes = {
  home: "/",
  profile: "/me",
} satisfies Record<string, `/${string}`>;
// routes.home имеет тип string, ключи — только home и profile
```

Можно сочетать с `as const`: `{ … } as const satisfies Config` — и литералы, и проверка.

@@@ ts-13 | as const
Что делает `as const`?
???
`as const` просит TS вывести **самый узкий** возможный тип и сделать значение неизменяемым:

- строки и числа становятся литеральными типами (`"get"`, а не `string`);
- массивы — `readonly`-кортежами фиксированной длины;
- все поля объектов — `readonly`, на всю глубину.

```ts
const a = ["get", "post"];          // string[]
const b = ["get", "post"] as const; // readonly ["get", "post"]
type Method = (typeof b)[number];   // "get" | "post"

const cfg = { mode: "dark", size: 2 } as const;
// { readonly mode: "dark"; readonly size: 2 }
cfg.mode = "light"; // ошибка: поле только для чтения
```

Почему без него тип широкий: обычный `const arr = ["get"]` — массив можно изменить (`arr.push("put")`), поэтому TS честно выводит `string[]`. `as const` обещает, что меняться ничего не будет.

Где применяют:

- список допустимых значений + тип из него (вместо `enum`);
- объекты-константы: роли, статусы, ключи кэша;
- возврат кортежа из хука: `return [value, setValue] as const` — иначе TS выведет массив `(string | Function)[]`, и деструктуризация потеряет типы.

Важно: `as const` работает только при компиляции. В рантайме объект можно изменить; если нужна реальная защита — `Object.freeze`.

@@@ ts-14 | enum, union
`enum` или union строковых литералов?
???
`enum` — одна из немногих конструкций TS, которая **генерирует код**. Из

```ts
enum Direction { Up = "UP", Down = "DOWN" }
```

получается настоящий JS-объект в бандле. А union литералов полностью исчезает после компиляции:

```ts
type Direction = "UP" | "DOWN";
```

Недостатки `enum`:

- лишний код в бандле, хуже удаляется tree-shaking'ом;
- **числовые** enum слабо защищены: в переменную такого типа можно записать любое значение типа `number`;
- enum номинальный: строку `"UP"` нельзя передать туда, где ждут `Direction.Up`, — нужен импорт enum;
- не работает с флагом `erasableSyntaxOnly` и с запуском TS в Node без сборки (type stripping), где разрешён только синтаксис, который можно просто стереть.

Современная альтернатива, если нужен и объект, и тип:

```ts
const Direction = { Up: "UP", Down: "DOWN" } as const;
type Direction = (typeof Direction)[keyof typeof Direction]; // "UP" | "DOWN"

move(Direction.Up); // можно так
move("UP");         // и так
```

Поэтому сейчас чаще выбирают union или объект `as const`. Enum встречается в старых кодовых базах — его стоит понимать, но в новом коде он не обязателен.

@@@ ts-15 | основы
Что значит «структурная типизация»?
???
В TypeScript совместимость типов определяется **формой** (набором полей), а не **именем** типа. Если у объекта есть все поля, которые требует тип, он подходит, как бы ни назывался его тип.

```ts
type Point = { x: number; y: number };
type Vector = { x: number; y: number };

const v: Vector = { x: 1, y: 2 };
const p: Point = v; // ок: имена разные, форма одинаковая
```

В Java или C# (номинальная типизация) так нельзя: `Point` и `Vector` были бы разными типами.

Лишние поля тоже не мешают — объект с большим набором полей подходит под тип с меньшим:

```ts
const p3 = { x: 1, y: 2, z: 3 };
const ok: Point = p3; // ок: z просто игнорируется
```

**Исключение — excess property check.** Если объектный литерал пишется **прямо в месте присваивания**, лишние поля — ошибка:

```ts
const bad: Point = { x: 1, y: 2, z: 3 }; // ошибка: z не существует в Point
```

Логика: здесь лишнее поле почти наверняка опечатка (`colour` вместо `color`), а не осознанное решение.

Минус структурной типизации: `UserId` и `OrderId`, оба `string`, взаимозаменяемы, и их легко перепутать. Чтобы различать одинаковые по форме типы, используют branded types.

@@@ ts-16 | branded types
Что такое branded (номинальные) типы?
???
Приём, который имитирует номинальную типизацию в структурном TypeScript. Проблема, которую он решает:

```ts
function getUser(id: string) {}
getUser(orderId); // компилируется, хотя это id заказа — баг
```

Решение — «пометить» строку несуществующим полем-маркером:

```ts
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };

const toUserId = (s: string) => s as UserId;

function getUser(id: UserId) {}

getUser(toUserId("42")); // ок
getUser("42");           // ошибка: обычная строка — не UserId
getUser(orderId);        // ошибка: у OrderId другой __brand
```

Как это работает: тип `string & { __brand: "UserId" }` требует поле `__brand`, которого у обычной строки нет. В рантайме этого поля и не появляется — `as` просто убеждает компилятор. Значение остаётся обычной строкой, со всеми методами.

Где полезно:

- разные виды id, которые легко перепутать;
- проверенные значения: `Email`, `PositiveNumber`, `SafeHtml` — создать их можно только через функцию-валидатор, поэтому наличие типа гарантирует, что проверка была;
- единицы измерения: `Meters` и `Seconds`.

Библиотеки валидации поддерживают это из коробки: в zod — `.brand<"UserId">()`.

@@@ ts-17 | template literal types
Что такое template literal types?
???
Это шаблонные строки на уровне типов — тот же синтаксис `` `${…}` ``, только подставляются типы, а результат — строковый литеральный тип.

```ts
type Size = "sm" | "lg";
type Color = "red" | "blue";
type Cls = `${Color}-${Size}`;
// "red-sm" | "red-lg" | "blue-sm" | "blue-lg"
```

Если подставить union, TS перемножит все варианты. Это удобно, но осторожно: три union по 10 вариантов дадут 1000 строк и замедлят проверку.

Встроенные помощники для преобразования: `Uppercase`, `Lowercase`, `Capitalize`, `Uncapitalize`.

```ts
type EventName<T extends string> = `on${Capitalize<T>}`;
type E = EventName<"click">; // "onClick"
```

Шаблоны работают и как **маска** для проверки строк:

```ts
type Px = `${number}px`;
const ok: Px = "12px";
const bad: Px = "12em"; // ошибка

type ApiRoute = `/api/${string}`;
```

Где применяют:

- имена CSS-классов и design-токенов;
- имена обработчиков (`onClick` из `click`);
- ключи в объектах, построенных из других ключей (`getName` из `name`);
- разбор строк вместе с `infer`: параметры маршрута из `"/users/:id"`.

@@@ ts-18 | функции
Как описать перегрузки функций?
???
Перегрузки нужны, когда **тип результата зависит от типа аргументов**, и обычного union для этого мало:

```ts
function parseU(x: string | number): string | number { … }
const r = parseU("1"); // string | number — непонятно, что вернулось
```

Перегрузка — это несколько **сигнатур** (только объявления, без тела) и одна **реализация**, совместимая со всеми:

```ts
function parse(x: string): number;
function parse(x: number): string;
function parse(x: string | number) {
  return typeof x === "string" ? Number(x) : String(x);
}

const n = parse("1"); // number
const s = parse(1);   // string
parse(true);          // ошибка: нет подходящей сигнатуры
```

Как это работает:

- снаружи видны **только** сигнатуры-перегрузки; сигнатура реализации вызывающему коду недоступна;
- TS перебирает перегрузки **сверху вниз** и берёт первую подходящую, поэтому более конкретные пишут выше общих;
- реализация должна уметь обработать все случаи, и TS внутри неё не проверяет, что ты вернул правильный тип для каждой перегрузки — это на твоей совести.

Пример из DOM: `document.createElement("input")` возвращает `HTMLInputElement`, а `createElement("div")` — `HTMLDivElement`.

Часто перегрузки можно заменить дженериком с условным типом:

```ts
function parse2<T extends string | number>(x: T): T extends string ? number : string;
```

@@@ ts-19 | основы, assertion
Чем `as` отличается от аннотации типа? Что делает `!`?
???
**Аннотация** `const u: User = data` — проверка. TS сравнивает значение с типом и ругается, если что-то не сходится.

**Утверждение (assertion)** `data as User` — приказ: «считай, что это `User`, я знаю лучше». Проверка почти отключается: TS запретит только совсем несовместимые типы (например, `"abc" as number`), а всё остальное примет на веру.

```ts
const a: User = { name: "Ann" };    // ошибка: нет поля id
const b = { name: "Ann" } as User;  // компилируется — и врёт
b.id.toFixed();                     // упадёт в рантайме
```

**`x!` (non-null assertion)** убирает `null` и `undefined` из типа без всякой проверки:

```ts
const el = document.querySelector("#root")!; // Element, а не Element | null
el.append("…"); // если элемента нет — TypeError в рантайме
```

Оба приёма — места, где ты берёшь ответственность на себя. Ошибка в таком месте не будет найдена компилятором.

Лучше:

- сужать тип проверкой: `if (!el) throw new Error("нет #root")`;
- данные извне проверять схемой (zod) и выводить тип из неё;
- для DOM-элементов писать обработку отсутствия.

Когда `as` уместен: TS объективно не может вывести тип, а ты точно знаешь (например, `{}` в начале сборки объекта, `as const`, сужение `event.target as HTMLInputElement`).

@@@ ts-20 | readonly, mapped types
Как сделать данные неизменяемыми на уровне типов?
???
Инструменты:

```ts
type User = { readonly id: number; name: string }; // одно поле
type Frozen = Readonly<User>;                      // все поля
const list: readonly string[] = ["a"];             // массив (или ReadonlyArray<string>)
const cfg = { mode: "dark" } as const;              // всё дерево + литералы

list.push("b"); // ошибка: у readonly-массива нет push
```

У `readonly`-массива нет мутирующих методов (`push`, `sort`, `splice`), но есть `map`, `filter`, `toSorted`.

**Важно понимать два ограничения:**

1. Это только проверка компилятора. В рантайме объект можно изменить — через `as`, из JS-кода, из библиотеки. Для настоящей защиты нужен `Object.freeze`.
2. `Readonly<T>` **поверхностный**: вложенные объекты остаются изменяемыми.

```ts
const state: Readonly<{ user: { name: string } }> = { user: { name: "Ann" } };
state.user = …;        // ошибка
state.user.name = "Bob"; // а это можно
```

Глубокую версию пишут рекурсивно:

```ts
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
```

Зачем это на практике: пометить стейт Redux, пропсы и данные из кэша как неизменяемые — тогда случайная мутация, которая сломает ререндер, станет ошибкой компиляции.

@@@ ts-21 | union, utility types, ловушка
Почему `Omit` на union-типе ломает discriminated union?
???
`Omit<A | B, "id">` работает с `keyof (A | B)` — а это только **общие** ключи. Результат схлопывается в один объект, уникальные поля и связь «тип → поля» теряются:

```ts
type Shape =
  | { id: string; kind: "circle"; radius: number }
  | { id: string; kind: "square"; size: number };

type Bad = Omit<Shape, "id">;
// { kind: "circle" | "square" } — radius и size пропали
```

Почему только общие: у значения типа `A | B` гарантированно есть только те поля, которые есть у обоих вариантов. `Omit` не дистрибутивен — он видит union как одно целое.

Решение — дистрибутивный `Omit`: условный тип применяет `Omit` к каждому члену union отдельно.

```ts
type DistributiveOmit<T, K extends PropertyKey> =
  T extends unknown ? Omit<T, K> : never;

type Good = DistributiveOmit<Shape, "id">;
// { kind: "circle"; radius: number } | { kind: "square"; size: number }
```

`T extends unknown` всегда истинно — условие нужно только ради дистрибутивности.

То же касается `Pick` и любых своих mapped types поверх union. Типичная ситуация: тип пропсов компонента — union вариантов, и его «наследник» через `Omit` внезапно перестаёт работать.

@@@ ts-22 | react
Как типизировать пропсы React-компонента и `children`?
???
Пропсы описывают обычным объектным типом и указывают у параметра функции:

```tsx
type CardProps = {
  title: string;
  subtitle?: string;            // необязательный
  children: React.ReactNode;    // любое содержимое
  onClose?: () => void;
};

function Card({ title, subtitle, children, onClose }: CardProps) {
  return <section>…</section>;
}
```

**`children`**: тип `React.ReactNode` — всё, что React умеет отрендерить: JSX, строки, числа, массивы, `null`, `undefined`, `false`. Если нужен строго один JSX-элемент — `React.ReactElement`.

**Обёртка над нативным элементом** должна принимать все его родные атрибуты (`disabled`, `type`, `aria-*`, `onClick`):

```tsx
type ButtonProps = React.ComponentProps<"button"> & {
  variant?: "primary" | "ghost";
};

function Button({ variant = "primary", ...rest }: ButtonProps) {
  return <button data-variant={variant} {...rest} />;
}

<Button type="submit" disabled>Сохранить</Button> // всё типизировано
```

Ещё полезное:

- `React.FC` сейчас используют редко: он ничего не даёт сверх обычной функции, а раньше неявно добавлял `children`;
- события: `React.ChangeEvent<HTMLInputElement>`, `React.MouseEvent<HTMLButtonElement>`;
- стили: `React.CSSProperties`;
- взять пропсы чужого компонента: `React.ComponentProps<typeof Card>`.

@@@ ts-23 | react, generics
Как сделать дженерик-компонент в React?
???
Компонент — это функция, поэтому дженерик объявляется так же, как у функции. Это нужно, когда компонент принимает данные любого типа и должен сохранить его в колбэках:

```tsx
type ListProps<T> = {
  items: T[];
  render: (item: T) => React.ReactNode;
  getKey: (item: T) => string;
};

function List<T>({ items, render, getKey }: ListProps<T>) {
  return <ul>{items.map((i) => <li key={getKey(i)}>{render(i)}</li>)}</ul>;
}
```

Использование — тип указывать не нужно, TS выведет `T` из `items`:

```tsx
<List
  items={users}                      // T = User
  getKey={(u) => u.id}               // u: User
  render={(u) => <b>{u.name}</b>}    // u: User, есть подсказки
/>
```

Без дженерика пришлось бы писать `items: unknown[]` или `any[]`, и в `render` пришлось бы приводить тип вручную.

Синтаксическая ловушка: стрелочная функция-дженерик в файле `.tsx` пишется с запятой — `<T,>(props: ListProps<T>) => …`. Без запятой `<T>` парсер примет за открывающий JSX-тег.

Ограничение тоже работает: `function Select<T extends { id: string }>(…)` — элементы обязаны иметь `id`.

Так делают таблицы, списки, выпадающие меню и формы, которые работают с данными разной формы.

@@@ ts-24 | d.ts, модули
Что такое `.d.ts` и declaration merging? Как расширить чужой тип?
???
`.d.ts` — файл только с типами, без кода. Так поставляются типы библиотек (`@types/*`) и описываются глобальные объекты. Компилятор читает их, но в JS ничего не попадает.

**Declaration merging**: интерфейсы с одним именем в одной области сливаются в один. С `type` так не получится — повторное объявление будет ошибкой. Через слияние расширяют чужие типы:

```ts
declare module "next-auth" {
  interface Session {
    user: { id: string; role: "admin" | "user" };
  }
}

declare global {
  interface Window {
    analytics: Analytics;
  }
}

export {}; // файл должен быть модулем, чтобы работал declare global
```

После этого `session.user.role` и `window.analytics` типизированы во всём проекте. Это и есть способ «добавить поле» в тип, который тебе не принадлежит.

Для файлов без типов: `declare module "*.svg" { const src: string; export default src; }`.

`declare` означает «это существует в рантайме, поверь мне» — TS не создаёт код, а только запоминает тип.

@@@ ts-25 | tsconfig
Что включает `strict: true` в tsconfig?
???
`strict: true` — один флаг, который включает целый набор строгих проверок. Новые проекты стоит начинать сразу с ним.

Самые важные:

- **`strictNullChecks`** — `null` и `undefined` становятся отдельными типами. Без флага `string` молча включает `null`, и `user.name.length` компилируется, даже если `user` может быть пустым. Это главный источник пользы от TS.
- **`noImplicitAny`** — ошибка, если TS не смог вывести тип и подставил бы `any` (например, параметр функции без типа).
- **`strictFunctionTypes`** — корректная проверка типов параметров у функций-колбэков.
- **`strictPropertyInitialization`** — поля класса должны быть инициализированы в конструкторе.
- **`useUnknownInCatchVariables`** — ошибка в `catch (e)` получает тип `unknown`, а не `any`.
- ещё `strictBindCallApply`, `noImplicitThis`, `alwaysStrict`.

```ts
function len(s: string | null) {
  return s.length; // со strictNullChecks — ошибка: s может быть null
}
```

Полезно добавить сверху:

- **`noUncheckedIndexedAccess`** — `arr[i]` и `obj[key]` получают тип `T | undefined`. Ловит обращения за пределы массива и к несуществующим ключам.
- **`exactOptionalPropertyTypes`** — различает «поле отсутствует» и «поле есть со значением `undefined`».

Когда в TS появляются новые строгие проверки, их добавляют в `strict`, поэтому после обновления версии могут появиться новые ошибки — это нормально.

@@@ ts-26 | unknown, ошибки
Какой тип у ошибки в `catch` и как с ней работать?
???
При `strict` (флаг `useUnknownInCatchVariables`) — `unknown`. Причина: бросить можно что угодно — строку, объект, `null`, а не только `Error`. Без флага там `any`, и `e.message` компилируется, даже если его нет.

```js
throw "что-то пошло не так"; // в JS так можно
throw { code: 42 };          // и так
```

Сужай перед использованием:

```ts
try {
  await save();
} catch (e) {
  const message = e instanceof Error ? e.message : String(e);
  toast(message);
}
```

Аннотировать `catch (e: Error)` нельзя — разрешены только `unknown` и `any`. Для своих ошибок удобно завести класс `class ApiError extends Error { status = 0 }` и проверять `e instanceof ApiError`.

Если такая обработка повторяется, её выносят в функцию `getErrorMessage(e: unknown): string`.

@@@ ts-27 | utility types, async
Как получить тип данных, которые возвращает async-функция?
???
`ReturnType` даст `Promise<…>`, поэтому оборачиваем в `Awaited`:

```ts
async function getUser() {
  return { id: 1, name: "Ann" };
}

type User = Awaited<ReturnType<typeof getUser>>;
// { id: number; name: string }
```

Читаем изнутри наружу: `typeof getUser` берёт тип функции, `ReturnType` — её результат (`Promise<{…}>`), `Awaited` разворачивает промис. Он работает рекурсивно: `Awaited<Promise<Promise<string>>>` → `string`.

Так типы выводятся из реализации и не расходятся с ней. Аналогично `Parameters<typeof fn>[0]` даёт тип первого аргумента.

Где это полезно: функция получения данных в серверном компоненте Next.js или Prisma-запрос — тип результата берётся прямо из них, и не нужно вручную описывать интерфейс, который рано или поздно устареет.

@@@ ts-28 | record, ловушка
`Record<string, T>` против `Record<"a" | "b", T>`. Какая ловушка у индексных сигнатур?
???
**`Record<"a" | "b", T>`** — объект с **конкретными** ключами, и TS требует их все:

```ts
type Status = "idle" | "error";
const labels: Record<Status, string> = { idle: "Ожидание" };
// ошибка: нет ключа error
```

Это полезно: добавил новый статус в union — компилятор покажет все словари, где его забыли описать.

**`Record<string, T>`** (то же, что индексная сигнатура `{ [key: string]: T }`) — подходят **любые** ключи. И тут ловушка: TS считает, что по любому ключу значение **есть всегда**:

```ts
const prices: Record<string, number> = {};
prices.apple.toFixed(); // компилируется, а в рантайме:
// TypeError: Cannot read properties of undefined
```

Тип `prices.apple` — `number`, хотя на самом деле там `undefined`. TS не может знать, какие ключи появятся в рантайме, и по умолчанию оптимистичен.

Как лечить:

- флаг **`noUncheckedIndexedAccess`** — тогда `prices.apple` имеет тип `number | undefined`, и проверку придётся написать;
- `Partial<Record<string, number>>` — то же самое для конкретного типа;
- `Map<string, number>` — у него `get` честно возвращает `number | undefined`.

Правило: если ключи известны заранее — union-ключи; если это словарь с произвольными ключами — учитывай, что значения может не быть.

@@@ ts-29 | вариантность, функции
Что такое ковариантность и контравариантность?
???
Это ответ на вопрос: если `Dog` — подтип `Animal`, то как связаны «составные» типы из них?

**Ковариантность** — связь сохраняется в ту же сторону. Так ведут себя массивы и **возвращаемые значения**:

```ts
const getDog = (): Dog => dog;
const getAnimal: () => Animal = getDog; // ок: собака — это животное
```

Функция, которая возвращает собаку, подходит туда, где ждут «что-то, возвращающее животное».

**Контравариантность** — связь **переворачивается**. Так ведут себя **параметры функций**:

```ts
const feedAnimal = (a: Animal) => {};
const feedDog: (d: Dog) => void = feedAnimal; // ок

const walkDog = (d: Dog) => d.bark();
const walkAnimal: (a: Animal) => void = walkDog; // ошибка
```

Почему так: `walkAnimal` могут вызвать с кошкой, а `walkDog` попытается вызвать у неё `bark()`. А функция, умеющая кормить любое животное, справится и с собакой.

Запомнить: **на выходе** можно отдать более конкретное, **на входе** нужно принимать более общее.

Нюанс: проверку параметров включает флаг `strictFunctionTypes` (входит в `strict`), и работает она для свойств-функций (`onClick: (e) => void`), но **не для методов** (`onClick(e): void`). Методы проверяются бивариантно — в обе стороны, — ради совместимости со старым кодом. Поэтому для строгих колбэков лучше синтаксис свойства.

Массивы в TS ковариантны, хотя это не полностью безопасно: в `Animal[]`, который на самом деле `Dog[]`, можно положить кошку.

@@@ ts-30 | generics, новое
Что делает `NoInfer<T>`?
???
(TS 5.4) Запрещает выводить дженерик из этого места. Параметр всё равно проверяется, но не влияет на то, каким получится `T`:

```ts
function createFSM<S extends string>(states: S[], initial: NoInfer<S>) {}

createFSM(["idle", "run"], "idle"); // ок
createFSM(["idle", "run"], "jump"); // ошибка: S выводится только из states
```

Без `NoInfer` TS собрал бы `S` из обоих аргументов — `"idle" | "run" | "jump"` — и опечатка прошла бы молча.

Как это понять: по умолчанию TS собирает кандидатов для `T` из **всех** мест, где он встречается, и объединяет их. `NoInfer` говорит: «это место — только для проверки, источник правды — другие аргументы».

Типичные места: значение по умолчанию, начальное состояние, `fallback`-аргумент, который должен быть одним из уже переданных вариантов.

@@@ ts-31 | union, основы
Чем отличаются `A | B` и `A & B`?
???
**`A | B` (union, объединение)** — значение является **одним из** типов: или `A`, или `B`. Пока не проверишь, какой именно, доступны только поля, которые есть у обоих:

```ts
function show(x: string | string[]) {
  x.length;          // ок: есть у обоих
  x.toUpperCase();   // ошибка: у массива нет
  if (typeof x === "string") x.toUpperCase(); // после проверки — можно
}
```

**`A & B` (intersection, пересечение)** — значение является **обоими** сразу: у него есть все поля и `A`, и `B`. Это способ «сложить» объектные типы:

```ts
type User = { id: number; name: string };
type Admin = User & { permissions: string[] };

const a: Admin = { id: 1, name: "Ann", permissions: ["all"] }; // нужны все поля
```

Если пересечь несовместимые типы, получится `never` — значения, которое одновременно и строка, и число, не существует: `string & number` → `never`.

**Интуиция через множества.** Тип — это множество допустимых значений.

- Union **расширяет** множество: значений больше, но про каждое известно меньше (только общее).
- Пересечение **сужает** множество: значений меньше, но про каждое известно больше (все поля).

Отсюда кажущийся парадокс: у `A | B` **меньше** доступных полей, а у `A & B` — **больше**, хотя слова «или» и «и» подсказывают обратное.

@@@ ts-32 | валидация, zod
Почему типы TS не защищают от неверных данных с сервера? Как быть?
???
Типы существуют только при компиляции. После сборки остаётся обычный JS, где никаких проверок нет. Поэтому запись

```ts

```

не проверяет ничего — это просто обещание компилятору. Если бэкенд переименовал поле `name` в `fullName`, TS не узнает: `user.name` будет `undefined`, и ошибка вылезет где-нибудь в интерфейсе.

Всё, что приходит **извне программы**, нужно проверять в рантайме:

- ответы API;
- `localStorage`, `URLSearchParams`, cookies;
- данные форм;
- `JSON.parse`, сообщения из `postMessage` и WebSocket.

Удобнее всего — схемами (zod, valibot, arktype). Схема одновременно проверяет данные и даёт TS-тип, поэтому описывать структуру дважды не нужно:

```ts
import { z } from "zod";

const User = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof User>; // { id: number; name: string }

const user = User.parse(await res.json()); // бросит ZodError, если формат не тот
const result = User.safeParse(data);       // или вернёт { success, data | error }
```

Ошибка возникает **сразу на границе** с понятным описанием, какое поле не так, а дальше по коду данные гарантированно правильные. Те же схемы используют для валидации форм (react-hook-form) и входных данных Server Actions.

@@@ ts-33 | классы, private
Чем `private` в TypeScript отличается от `#private` в JavaScript?
???
- `private` — проверка **только при компиляции**. В JS-коде поле обычное: его видно в консоли, и даже TS разрешает доступ через скобки `obj["secret"]`.
- `#secret` — настоящая приватность **в рантайме**: снаружи класса поле недоступно никак.

```ts
class Account {
  private secret = 1;
  #real = 2;
}
const acc = new Account();
acc.secret;    // ошибка компиляции
acc["secret"]; // компилируется — лазейка
// acc.#real   — синтаксическая ошибка вне класса
```

После компиляции `private secret` превращается в обычное `this.secret`, и любой JS-код (или `JSON.stringify(acc)`) его увидит. А `#real` не попадёт ни в `JSON.stringify`, ни в `Object.keys`.

`protected` доступен в наследниках, `public` — везде (по умолчанию).

Когда что выбирать: `#` — если важна настоящая инкапсуляция (библиотеки, чувствительные данные). `private` — когда достаточно договорённости для своей команды; его удобнее тестировать и отлаживать.

@@@ ts-34 | основы, unknown
Чем отличаются типы `{}`, `object` и `unknown`?
???
Это три «широких» типа, которые часто путают:

- **`unknown`** — вообще любое значение, включая `null` и `undefined`.
- **`{}`** — любое значение, **кроме** `null` и `undefined`. Неожиданно, но сюда подходят и примитивы: `42`, `"str"`, `true`.
- **`object`** — только непримитивы: объекты, массивы, функции, `Date`.

```ts
const a: {} = 42;       // ок: у числа есть свойства (toFixed и др.)
const b: {} = null;     // ошибка
const c: object = 42;   // ошибка: число — примитив
const d: object = [];   // ок
```

Почему `{}` принимает числа: `{}` означает «объектный тип без обязательных полей». По структурной типизации подходит всё, у чего можно прочитать свойства, — а у числа можно (`(42).toFixed()`). Нельзя только у `null` и `undefined`.

Частая ошибка — писать `{}` в значении «любой объект»:

```ts
function save(data: {}) {}
save("строка"); // компилируется, хотя ждали объект
```

Что писать вместо:

- «объект с любыми ключами» — `Record<string, unknown>`;
- «любое не-null значение» — `NonNullable<unknown>` (это и есть `{}`, но читается понятнее);
- «пока не знаю что» — `unknown`.

@@@ ts-35 | функции, совместимость
Почему функцию с меньшим числом параметров можно передать туда, где ждут больше?
???
Потому что это безопасно: функция, которой не нужны лишние аргументы, их просто проигнорирует. JS так работает всегда — передать функции больше аргументов, чем она объявила, не ошибка.

```ts
type Callback = (value: number, index: number, array: number[]) => void;

const cb: Callback = (v) => console.log(v); // ок: index и array не нужны

[1, 2, 3].forEach((n) => console.log(n)); // forEach передаст 3 аргумента, используем 1
```

Если бы TS это запрещал, пришлось бы писать `(n, _i, _arr) => …` в каждом `map` и `forEach`.

Обратное запрещено:

```ts
type OneArg = (value: number) => void;
const fn: OneArg = (v, i) => {}; // ошибка: i будет получать undefined
```

Функция, которой **нужны** два аргумента, при вызове с одним получит `undefined` во втором — и сломается.

Запомнить: «функция с меньшими требованиями подходит туда, где обещают больше». Это частный случай правила для параметров: на вход можно принимать меньше и шире.

Ловушка из жизни: `["1", "2", "3"].map(parseInt)` даёт `[1, NaN, NaN]`. `map` передаёт вторым аргументом индекс, а `parseInt` воспринимает его как систему счисления. TS это пропускает, потому что сигнатуры совместимы.

@@@ ts-36 | as const, enum
Как сделать «enum» из обычного объекта?
???
Объект-константа с `as const` плюс тип, выведенный из его значений:

```ts
const ROLE = {
  Admin: "admin",
  User: "user",
} as const;

type Role = (typeof ROLE)[keyof typeof ROLE]; // "admin" | "user"

function can(role: Role) {}
can(ROLE.Admin); // ок
can("user");     // тоже ок — это просто строка
can("guest");    // ошибка
```

Как читается тип по шагам:

1. `typeof ROLE` — тип объекта: `{ readonly Admin: "admin"; readonly User: "user" }`;
2. `keyof typeof ROLE` — его ключи: `"Admin" | "User"`;
3. `(typeof ROLE)[...]` — значения по этим ключам: `"admin" | "user"`.

Без `as const` значения были бы типа `string`, и `Role` получился бы просто `string`.

Плюсы перед `enum`:

- обычный JS-объект без особого синтаксиса, работает с type stripping в Node;
- в функцию можно передать и `ROLE.Admin`, и просто `"admin"` — удобно с данными из API;
- можно перебрать: `Object.values(ROLE)` для `<select>`;
- никакого лишнего кода, кроме самого объекта.

Имя типа и константы можно сделать одинаковым — `const Role` и `type Role` живут в разных пространствах имён и не конфликтуют.

@@@ ts-37 | type guards, массивы
Как правильно отфильтровать `undefined` из массива, чтобы TypeScript понял тип?
???
С TS 5.5 тип-предикат **выводится автоматически** для простых проверок:

```ts
const mixed = [1, undefined, 2];
const nums = mixed.filter((x) => x !== undefined); // number[]
```

TS видит, что стрелка возвращает результат проверки `x !== undefined`, и сам делает её type guard'ом `(x) => x is number`. А у `filter` есть перегрузка: если колбэк — type guard, результат сужается.

Для сложных условий предикат пишут явно:

```ts
const strs = ["a", 1, "b"].filter((x): x is string => typeof x === "string"); // string[]
```

До 5.5 первый пример давал `(number | undefined)[]`, и часто встречалось `filter(Boolean)` — оно тоже не сужает тип и вдобавок выкидывает `0` и `""`.

Автовывод работает только для «честных» проверок: если функция может вернуть `false` и для подходящего значения (например, `x => !!x`, отбрасывающая `0`), TS предикат не выведет — и правильно сделает.

@@@ ts-38 | utility types, задача
Напиши тип `PartialBy<T, K>`, который делает необязательными только указанные поля.
???
```ts
type PartialBy<T, K extends keyof T> = Omit<T, K> & Partial<Pick<T, K>>;

```

Разбор по шагам на примере `PartialBy<User, "email">`:

1. `Omit<User, "email">` → `{ id: number; name: string }` — всё, кроме `email`, остаётся обязательным;
2. `Pick<User, "email">` → `{ email: string }` — только нужное поле;
3. `Partial<…>` → `{ email?: string }` — делаем его необязательным;
4. `&` склеивает обе части обратно в один тип.

Где пригодится: форма создания, где `id` ещё нет (`PartialBy<User, "id">`), или пропсы компонента, у которых часть полей имеет значения по умолчанию.

В подсказке IDE тип покажется как пересечение. Чтобы увидеть «плоский» объект, оборачивают в помощник: `type Prettify<T> = { [K in keyof T]: T[K] } & {}`.

Так же собирают `RequiredBy`, `ReadonlyBy` и другие.

???
```ts

  return (...args: Parameters<F>): ReturnType<F> => {
    console.log(fn.name, args);
    return fn(...args);
  };
}

const add = (x: number, y: number) => x + y;
const loggedAdd = withLog(add); // (x: number, y: number) => number
loggedAdd("1", 2);              // ошибка типа
```

Как это работает: `F` — тип переданной функции целиком. `Parameters<F>` достаёт из него кортеж аргументов `[x: number, y: number]`, `ReturnType<F>` — тип результата. Обёртка объявляет ровно такие же параметры и результат, поэтому для вызывающего кода она неотличима от оригинала.

`any[]` в ограничении здесь уместен: нам нужно принять функцию с любыми параметрами, а конкретные типы всё равно берутся из `F`.

Альтернатива — дженерики отдельно по аргументам и результату: `<A extends unknown[], R>(fn: (...args: A) => R) => (...args: A): R => …`. Она проще для TS и не требует `any`.

Так пишут декораторы, `debounce`, `memoize`, обёртки для логирования и обработки ошибок в API.

@@@ ts-40 | generics, const
Что такое `const`-параметры типа (`<const T>`)?
???
(TS 5.0) Просят TypeScript выводить для аргумента максимально узкий тип, как будто вызывающий написал `as const`:

```ts
}

  return paths;
}
const p = plain(["/", "/about"]); // string[]
```

Почему по умолчанию широкий тип: TS предполагает, что массив `["/", "/about"]` могут потом изменить, поэтому выводит `string[]`. Модификатор `const` у параметра говорит: «этот аргумент — константа, сохрани литералы».

Удобно для конфигов, роутов, ключей — тип API строится из переданных литералов без `as const` у пользователя.

@@@ ts-41 | generics, события
Как типизировать event emitter, чтобы данные события зависели от его имени?
???

```ts
type Events = {
```

@@@ ts-42 | mapped types, задача
Как получить union ключей объекта, значения которых — функции?
???
```ts
type FunctionKeys<T> = {
  [K in keyof T]: T[K] extends (...args: any[]) => any ? K : never;

type Service = { id: number; load(): void; save(x: number): boolean };

```

1. Mapped type превращает каждое поле в его имя или `never`.
2. Индексирование `[keyof T]` собирает значения в union.

Промежуточный результат после шага 1 выглядит так:

```ts
{ id: never; load: "load"; save: "save" }
```

Альтернатива — ремаппинг ключей через `as`: `{ [K in keyof T as T[K] extends Function ? K : never]: T[K] }`. Он сразу даёт объект только с методами, а не union ключей.

@@@ ts-43 | utility types
Чем `Exclude` отличается от `Omit`?
???
- `Exclude<Union, Members>` работает с **union-типами**: убирает члены объединения.
- `Omit<Object, Keys>` работает с **объектами**: убирает поля.

```ts
type Status = "idle" | "loading" | "error";
type Busy = Exclude<Status, "idle">; // "loading" | "error"

type User = { id: number; name: string; email: string };
type Public = Omit<User, "email">;   // { id: number; name: string }
```

Внутри `Omit<T, K>` как раз использует `Exclude`: `Pick<T, Exclude<keyof T, K>>`. То есть: взять все ключи, исключить ненужные, оставить объект только с оставшимися.

Частая ошибка — применить не тот: `Omit<Status, "idle">` вернёт что-то странное (поля строки вроде `charAt`), а `Exclude<User, "email">` вернёт `User` без изменений.

Ещё нюанс: `Omit` не проверяет, что ключ существует, — `Omit<User, "emial">` с опечаткой молча вернёт `User`. Для строгой версии пишут `type StrictOmit<T, K extends keyof T> = Omit<T, K>`.

@@@ ts-44 | пересечения, never
Что будет при пересечении типов с конфликтующими полями?
???
Зависит от того, что конфликтует:

```ts
type P = { v: string } & { v: number };
// объект остаётся, но поле v: string & number = never

type X = { kind: "x" } & { kind: "y" };
// never целиком: литеральные поля-дискриминанты несовместимы
```

TypeScript сворачивает в `never` весь объект, если конфликтуют литеральные типы (как у дискриминанта в union). Отсюда и разница между `interface extends` (сразу понятная ошибка при конфликте) и `&` (тихий `never`).

Почему это опасно: тип `P` выглядит нормально, ошибка появится только при попытке создать значение — `const p: P = { v: "a" }` упадёт с непонятным сообщением про `never`. Если же сделать то же через интерфейсы:

```ts
interface A { v: string }
interface B extends A { v: number } // ошибка сразу здесь: свойство v несовместимо
```

Поэтому для иерархий объектов `extends` надёжнее, а `&` хорош для сложения независимых частей.

@@@ ts-45 | рекурсивные типы, mapped types
Напиши `DeepPartial<T>` — `Partial`, который работает на всех уровнях вложенности.
???
Встроенный `Partial` делает необязательными только поля верхнего уровня. Рекурсивный тип обходит вложенные объекты:

```ts
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

type Config = { db: { host: string; port: number }; debug: boolean };

const patch: DeepPartial<Config> = { db: { port: 5433 } }; // ок
```

Как работает: для каждого поля проверяем, объект ли это. Если да — снова применяем `DeepPartial` к нему (рекурсия). Если примитив (`string`, `number`) — оставляем как есть, это база рекурсии.

Для массивов и функций это условие тоже сработает (они `object`). Массивы mapped type обработает корректно, а функции лучше пропускать отдельной веткой: `T extends (...args: any[]) => unknown ? T : …`.

По тому же шаблону пишут `DeepReadonly<T>` — с модификатором `readonly` вместо `?`. Где применяют: патчи конфигов, моки в тестах, частичные обновления форм.

@@@ ts-46 | generics, keyof
Как типизировать функцию `pick(obj, keys)`?
???
Ключи ограничиваем `keyof T`, а результат собираем встроенным `Pick`:

```ts
function pick<T extends object, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const out = {} as Pick<T, K>;
  for (const key of keys) out[key] = obj[key];
  return out;
}

const user = { id: 1, name: "Аня", password: "secret" };
const safe = pick(user, ["id", "name"]); // { id: number; name: string }
pick(user, ["email"]); // ошибка: "email" нет в keyof
```

Как это работает: TS выводит `K` из массива как union литералов `"id" | "name"`. `as Pick<T, K>` нужен, потому что пустой объект ещё не соответствует результату — это осознанное утверждение внутри реализации, а снаружи функция полностью типобезопасна.

Результат точный: у `safe` нет поля `password`, и обратиться к нему — ошибка компиляции. Такой `pick` удобен, чтобы не отдать клиенту лишние поля из ответа базы.

@@@ ts-47 | narrowing, assertion functions
Чем assertion-функция (`asserts x is T`) отличается от type guard?
???
Type guard возвращает `boolean`, и тип сужается **внутри `if`**. Assertion-функция ничего не возвращает: она либо бросает ошибку, либо гарантирует тип **до конца области видимости**.

```ts
function assertIsDefined<T>(value: T, name: string): asserts value is NonNullable<T> {
  if (value === null || value === undefined) {
    throw new Error(`${name} не задан`);
  }
}

const el = document.querySelector("#root");
assertIsDefined(el, "#root");
el.append("ok"); // el: Element, без if и без !
```

Логика: если функция вернулась без ошибки, значит, проверка прошла. Поэтому TS считает тип суженным во всём коде ниже вызова.

Есть короткая форма `asserts condition` — как в `node:assert`.

Ограничение: такую функцию нужно вызывать через явно типизированное имя (объявление `function` или переменная с аннотацией типа), иначе TS выдаст ошибку о том, что assertion требует явной аннотации.

Когда что выбирать: type guard — когда нужно обработать обе ветки (`if/else`). Assertion — когда отсутствие значения означает баг, и дальше без него работать нет смысла.

@@@ ts-48 | классы, ооп
Чем `abstract class` отличается от `interface`? Что делает `implements`?
???
**Интерфейс** — только контракт: что должно быть у объекта. После компиляции от него ничего не остаётся.

**Абстрактный класс** — частичная реализация: в нём может быть общий код, поля, конструктор, а абстрактные методы обязаны реализовать наследники. Создать его экземпляр нельзя, а в JS он остаётся обычным классом.

```ts
interface Storage {
  get(key: string): string | null;
}

abstract class Repository<T> {
  protected cache = new Map<string, T>();
  abstract load(id: string): Promise<T>;
  async get(id: string) {
    if (!this.cache.has(id)) this.cache.set(id, await this.load(id));
    return this.cache.get(id)!;
  }
}

class UserRepo extends Repository<User> implements Storage { … }
```

Здесь вся логика кэширования написана один раз в `Repository`, а `UserRepo` реализует только `load` — как получить пользователя.

`implements` лишь **проверяет**, что класс соответствует интерфейсу, — ничего не наследует. Наследовать (`extends`) можно один класс, реализовать — сколько угодно интерфейсов.

Когда что: интерфейс — когда нужен только контракт; абстрактный класс — когда у наследников много общего кода. Во фронтенде на React классы встречаются редко, но в сервисах, SDK и на бэкенде (NestJS) — часто.

@@@ ts-49 | generics, кортежи
Что такое variadic tuple types и именованные элементы кортежа?
???
Кортеж с `...` внутри может склеивать другие кортежи:

```ts
type Concat<A extends unknown[], B extends unknown[]> = [...A, ...B];
type R = Concat<[1, 2], ["a"]>; // [1, 2, "a"]

type Range = [start: number, end: number]; // имена видны в подсказках IDE
type Args = [id: string, ...tags: string[]]; // rest внутри кортежа
```

Главное применение — типизация функций, которые работают с аргументами других функций:

```ts
function partial<A extends unknown[], R>(
  fn: (first: string, ...rest: A) => R,
  first: string,
) {
  return (...rest: A) => fn(first, ...rest);
}

const greet = (name: string, age: number) => `${name}, ${age}`;
const greetAnn = partial(greet, "Аня"); // (age: number) => string
```

Как это работает: TS сопоставляет `greet` с шаблоном `(first: string, ...rest: A) => R` и выводит `A = [age: number]` — всё, что идёт после первого параметра. Именно так типизируются `bind`, каррирование и middleware.

Имена элементов ни на что не влияют при проверке типов — они только для читаемости.

@@@ ts-50 | рекурсивные типы, json
Как описать тип для любого JSON-значения?
???
Рекурсивным union — тип ссылается сам на себя:

```ts
type Json =
  | string
  | number
  | boolean
  | null
  | Json[]
  | { [key: string]: Json };

const ok: Json = { a: [1, "two", { b: null }] };
const bad: Json = { date: new Date() }; // ошибка: Date — не Json
```

Читается так: JSON — это примитив, **или** массив JSON-значений, **или** объект, где каждое значение — снова JSON. Рекурсия позволяет описать вложенность любой глубины.

Зачем: так описывают то, что гарантированно переживёт `JSON.stringify`, — например, данные для `localStorage`, тело запроса или пропсы, которые серверный компонент передаёт в клиентский.

`undefined`, функции, `Date`, `Map` и `bigint` в JSON не входят — `JSON.stringify` их потеряет, превратит в строку или упадёт с ошибкой.

@@@ ts-51 | mapped types, template literals
Как переименовать ключи в mapped type? Напиши `Getters<T>`.
???
В mapped type после `as` можно задать новое имя ключа (key remapping, TS 4.1):

```ts
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type User = { name: string; age: number };
type UserGetters = Getters<User>;
// { getName: () => string; getAge: () => number }
```

`string & K` нужен, потому что ключом может быть `number` или `symbol`, а `Capitalize` работает только со строками.

Если после `as` вернуть `never`, ключ исчезнет — так фильтруют поля:

```ts
type OnlyStrings<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K];
};
type R = OnlyStrings<User>; // { name: string }
```

Разница с обычным mapped type: без `as` ключи остаются прежними, меняются только типы значений. С `as` можно и переименовать, и выбросить ключ, и даже размножить один ключ в несколько через union.

@@@ ts-52 | функции, void
Чем `void` отличается от `undefined` в типе возврата?
???
`undefined` — конкретное значение: функция обязана вернуть `undefined`.

`void` — «результат не используется». Поэтому функцию, которая **что-то** возвращает, можно передать туда, где ждут `() => void`:

```ts
const nums: number[] = [];
[1, 2].forEach((n) => nums.push(n)); // push возвращает number — и это ок

type Handler = () => void;
const h: Handler = () => 42; // разрешено
const x = h(); // x: void — использовать нельзя
```

Это сделано специально, чтобы колбэки вроде `forEach` и обработчиков событий принимали любые функции.

Ловушка: при **объявлении** функции `function f(): void { return 42; }` — уже ошибка. Послабление работает только при присваивании типа функции. Для асинхронных колбэков `() => void` скрывает промис — линтер `no-misused-promises` ловит такие места.

Пример проблемы: `onClick={async () => { await save(); }}` — React не ждёт промис, и если `save` упадёт, ошибка станет unhandled rejection. Типы это пропустят, потому что `() => Promise<void>` совместима с `() => void`.

@@@ ts-53 | react, события
Как типизировать события в React и расширить пропсы нативного элемента?
???
События — дженерики по типу элемента:

```tsx

const onSubmit = (e: React.FormEvent<HTMLFormElement>) => e.preventDefault();
```

@@@ ts-54 | react, хуки
Как типизировать `useState`, `useRef` и `useReducer`?
???
**useState** — тип выводится из начального значения. Указывать явно нужно, когда начальное значение «уже» реального:

```tsx
const [count, setCount] = useState(0);              // number — вывелся сам
const [user, setUser] = useState<User | null>(null); // иначе был бы тип null
const [tags, setTags] = useState<string[]>([]);      // иначе never[]
```

**useRef** — два сценария:

```tsx
const inputRef = useRef<HTMLInputElement>(null); // ссылка на DOM, React заполнит сам
const timer = useRef<number | undefined>(undefined); // изменяемое значение
```

В первом случае `inputRef.current` имеет тип `HTMLInputElement | null` — перед использованием нужна проверка: `inputRef.current?.focus()`.

**useReducer** — тип выводится из редьюсера; экшены удобно описать discriminated union:

```tsx
type Action = { type: "add"; text: string } | { type: "remove"; id: string };

function reducer(state: Todo[], action: Action): Todo[] {
  switch (action.type) {
    case "add": return [...state, { id: crypto.randomUUID(), text: action.text }];
    case "remove": return state.filter((t) => t.id !== action.id);
  }
}
```

Внутри `case "add"` TS знает, что у `action` есть `text`, а в `case "remove"` — `id`. А `dispatch({ type: "add" })` без `text` — ошибка компиляции.

@@@ ts-55 | mapped types, модификаторы
Как убрать `readonly` и `?` в mapped type?
???
Модификаторы можно не только добавлять (`+`, по умолчанию), но и снимать минусом:

```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type Concrete<T> = { [K in keyof T]-?: T[K] }; // так устроен Required<T>

type Frozen = { readonly id: number; readonly name?: string };
type Editable = Mutable<Frozen>;   // { id: number; name?: string }
type Full = Concrete<Frozen>;      // { readonly id: number; readonly name: string }
```

`-?` убирает не только знак вопроса, но и `undefined` из типа поля, которое появилось из-за `?`.

Где пригодится: получить изменяемую копию типа из `as const`-объекта, сделать тип «после валидации», где все поля уже заполнены, или написать свой `PartialBy` / `RequiredBy`.

Обрати внимание: модификаторы независимы. `Mutable` снял только `readonly`, необязательность `name` осталась. `Concrete` — наоборот.

@@@ ts-56 | object.keys, ловушка
Почему `Object.keys(obj)` возвращает `string[]`, а не `(keyof T)[]`?
???
Из-за структурной типизации у объекта в рантайме может быть **больше** ключей, чем описано в типе:

```ts
type Point = { x: number; y: number };
const p3 = { x: 1, y: 2, z: 3 };
const p: Point = p3; // разрешено: лишние поля не мешают

Object.keys(p); // ["x", "y", "z"] — "z" не входит в keyof Point
```

Если бы TS возвращал `("x" | "y")[]`, код `p[key].toFixed()` мог бы упасть на `z`. Поэтому `string[]` — честный тип.

Как быть, когда объект точно под твоим контролем (константа, `as const`):

```ts
const keys = Object.keys(config) as (keyof typeof config)[];
// или
for (const [key, value] of Object.entries(config)) { … }
```

Утверждение `as` — твоя ответственность: используй его только там, где лишних ключей быть не может.

Это популярный вопрос на собесе как раз потому, что проверяет понимание структурной типизации: тип описывает **минимум** полей, а не точный их набор.

@@@ ts-57 | template literals, infer
Как вывести параметры из строки маршрута `"/users/:id/posts/:postId"`?
???
Рекурсивный условный тип с `infer` в шаблонной строке:

```ts
type Params<Path extends string> =
  Path extends `${string}:${infer Param}/${infer Rest}`
    ? { [K in Param | keyof Params<Rest>]: string }
    : Path extends `${string}:${infer Param}`
      ? { [K in Param]: string }
      : {};

type P = Params<"/users/:id/posts/:postId">;
// { id: string; postId: string }

function href<T extends string>(path: T, params: Params<T>) { … }
href("/users/:id", { id: "42" });  // ок
href("/users/:id", { uid: "42" }); // ошибка
```

Как работает: `infer Param` захватывает текст между `:` и `/`, `Rest` — остаток строки, который обрабатывается тем же типом рекурсивно.

Трассировка: `"/users/:id/posts/:postId"` → первая ветка, `Param = "id"`, `Rest = "posts/:postId"` → для `Rest` первая ветка не подходит (после `:postId` нет `/`), срабатывает вторая, `Param = "postId"` → ключи собираются: `"id" | "postId"`.

Так устроены типизированные роуты в tRPC, Hono, Express и TanStack Router. На собесе ценят не запоминание, а умение объяснить, что делает каждый `infer`.

@@@ ts-58 | модули, tsconfig
Зачем нужен `import type` и флаг `verbatimModuleSyntax`?
???
`import type` говорит, что импорт нужен **только для типов**, и компилятор гарантированно удалит его из JS:

```ts
import type { User } from "./types";
import { api, type Session } from "./api"; // смешанный вариант
```

Почему это важно:

- сборщики (esbuild, SWC, Babel) компилируют каждый файл отдельно и не знают, тип это или значение. Импорт несуществующего в рантайме значения ломает сборку или оставляет лишний код;
- импорт ради типов не тянет модуль с побочными эффектами в бандл;
- явно видно, что зависимость только «типовая».

`verbatimModuleSyntax: true` (TS 5.0) делает правило строгим: импорты без `type` остаются в JS **как есть**, а импорт, используемый только как тип, но без пометки `type`, — ошибка. Он заменил старые флаги `importsNotUsedAsValues` и `preserveValueImports`. Похожий по смыслу `isolatedModules` проверяет, что каждый файл можно скомпилировать отдельно.

Практический случай: в Next.js клиентский компонент импортирует тип из серверного модуля с доступом к базе. С `import type` модуль базы не попадёт в клиентский бандл.

@@@ ts-59 | fetch, безопасность типов
Как типизировать обёртку над `fetch` и почему `res.json() as T` небезопасно?
???
Простой вариант — дженерик:

```ts
async function getJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json() as Promise<T>;
}

const user = await getJson<User>("/api/me");
```

Но это **обещание**, а не проверка: `res.json()` возвращает `any`, и если сервер пришлёт другую структуру, TypeScript не узнает — ошибка вылезет дальше по коду.

Надёжный вариант — проверять данные в рантайме схемой и выводить тип из неё:

```ts
const UserSchema = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof UserSchema>;

async function getUser() {
  const res = await fetch("/api/me");
  return UserSchema.parse(await res.json()); // бросит, если формат не тот
}
```

Тип и проверка получаются из одного источника и не разъедутся.

Компромисс: валидация стоит времени выполнения. Для своего бэкенда с общими типами (монорепозиторий, tRPC) часто обходятся дженериком, а схемы ставят на внешние API и пользовательский ввод.

@@@ ts-60 | conditional types, never
Почему `IsNever<never>` не даёт `true`, и как это исправить?
???
```ts
type IsNever<T> = T extends never ? true : false;
type A = IsNever<never>; // never, а не true!
```

Условный тип над «голым» параметром **дистрибутивен**: он применяется к каждому члену union по отдельности. `never` — это пустой union, членов нет, поэтому и результат пустой — `never`.

Аналогия: `[].map(fn)` вернёт `[]`, сколько бы ни было логики в `fn`, — применять её не к чему.

Исправление — обернуть обе стороны в кортеж, чтобы отключить дистрибутивность:

```ts
type IsNever<T> = [T] extends [never] ? true : false;
type B = IsNever<never>;  // true
type C = IsNever<string>; // false
```

Тот же приём нужен, когда условный тип должен работать с union **целиком**: `[T] extends [string]` проверит весь `"a" | 1` разом, а не каждый член отдельно.
