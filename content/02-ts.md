@@@ ts-01 | основы
Чем `type` отличается от `interface`?
???
Оба описывают форму объекта. Отличия:

- `interface` можно **дополнять** повторным объявлением (declaration merging) и расширять через `extends`.
- `type` умеет больше: union, пересечения, кортежи, mapped и conditional types, примитивы.
- `extends` у интерфейсов даёт понятную ошибку при конфликте полей, а `&` молча превращает поле в `never`.

На практике: `interface` — для объектных контрактов, `type` — для остального. Главное — единообразие в проекте.

@@@ ts-02 | основы, unknown, never
`any`, `unknown` и `never` — в чём разница?
???
- `any` — отключает проверку и «заражает» всё, к чему прикасается.
- `unknown` — «что угодно, но сначала проверь»: без сужения типа использовать нельзя.
- `never` — значения не бывает: функция, которая всегда бросает исключение, пустой union, исчерпанная проверка.

```ts
function parse(raw: unknown) {
  if (typeof raw === "string") return raw.trim(); // здесь raw: string
  throw new Error("not a string");                // тип never
}
```

@@@ ts-03 | generics
Что такое дженерики? Приведи пример с ограничением.
???
Параметры типов: функция или тип работает с разными типами и сохраняет связь между входом и выходом.

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}

// ограничение через extends
function byId<T extends { id: string }>(items: T[], id: string) {
  return items.find((i) => i.id === id);
}
```

Без `extends` обращаться к `.id` нельзя: `T` может быть чем угодно.

@@@ ts-04 | keyof, typeof
Что делают `keyof` и `typeof` на уровне типов?
???
`typeof value` — берёт тип из значения. `keyof T` — union ключей типа.

```ts
const config = { theme: "dark", lang: "ru" };
type Config = typeof config; // { theme: string; lang: string }
type Key = keyof Config;     // "theme" | "lang"

function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
```

@@@ ts-05 | indexed access, as const
Что такое indexed access types? Как получить тип элемента массива?
???
`T[K]` — тип свойства по ключу.

```ts
type User = { id: number; roles: ("admin" | "user")[] };
type Id = User["id"];              // number
type Role = User["roles"][number]; // "admin" | "user"

const SIZES = ["s", "m", "l"] as const;
type Size = (typeof SIZES)[number]; // "s" | "m" | "l"
```

Приём `(typeof ARR)[number]` + `as const` держит источник правды в одном месте. Так сделаны оценки в этом приложении.

@@@ ts-06 | utility types
Назови основные utility types.
???
- `Partial<T>` / `Required<T>` — все поля необязательные / обязательные
- `Readonly<T>` — только чтение
- `Pick<T, K>` / `Omit<T, K>` — оставить / убрать поля
- `Record<K, V>` — объект с ключами `K` и значениями `V`
- `Exclude<U, X>` / `Extract<U, X>` — убрать / оставить члены union
- `NonNullable<T>` — убрать `null` и `undefined`
- `ReturnType<F>`, `Parameters<F>`, `Awaited<T>` — результат, аргументы, значение промиса

@@@ ts-07 | mapped types
Что такое mapped types? Напиши свой `Partial`.
???
Тип, который проходит по ключам другого типа:

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] };
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };

// модификаторы можно снимать: -? и -readonly
type Mutable<T> = { -readonly [K in keyof T]: T[K] };

// переименование ключей через as
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};
```

@@@ ts-08 | conditional types
Что такое условные типы? Что значит «дистрибутивность»?
???
Тернарник на уровне типов: `T extends U ? X : Y`.

```ts
type IsString<T> = T extends string ? true : false;
type A = IsString<"hi">; // true
```

На union-типе они **дистрибутивны** — применяются к каждому члену отдельно:

```ts
type ToArray<T> = T extends unknown ? T[] : never;
type B = ToArray<string | number>; // string[] | number[]
```

Отключить: `[T] extends [unknown] ? T[] : never` → `(string | number)[]`.

@@@ ts-09 | infer, conditional types
Для чего нужно ключевое слово `infer`?
???
Внутри conditional type «вытаскивает» тип из структуры:

```ts
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;
type Unwrap<T> = T extends Promise<infer V> ? V : T;
type ElementOf<T> = T extends (infer E)[] ? E : never;

type R = MyReturnType<() => Promise<number>>; // Promise<number>
type V = Unwrap<R>;                            // number
```

@@@ ts-10 | narrowing, type guards
Как сужать типы? Что такое type guard?
???
TS сужает тип после проверок: `typeof`, `instanceof`, `in`, сравнения с литералом, проверки на truthy.

Свой предикат:

```ts
type Fish = { swim(): void };
type Bird = { fly(): void };

function isFish(pet: Fish | Bird): pet is Fish {
  return "swim" in pet;
}

if (isFish(pet)) pet.swim(); // pet: Fish
```

Есть ещё assertion-функции: `function assert(x: unknown): asserts x is string`.

@@@ ts-11 | union, never
Что такое discriminated union и exhaustive check?
???
Union объектов с общим полем-литералом (дискриминантом). По нему TS сужает тип в `switch`, а `never` в `default` ловит забытые варианты при компиляции:

```ts
type State =
  | { status: "loading" }
  | { status: "error"; error: string }
  | { status: "ok"; data: string[] };

function render(s: State) {
  switch (s.status) {
    case "loading": return "…";
    case "error": return s.error;
    case "ok": return s.data.join();
    default: {
      const never: never = s; // новый статус → ошибка компиляции здесь
      return never;
    }
  }
}
```

@@@ ts-12 | satisfies
Что делает оператор `satisfies` и чем он лучше аннотации?
???
Проверяет, что значение подходит под тип, но **не расширяет** выведенный тип:

```ts
type Colors = Record<string, string | [number, number, number]>;

const a: Colors = { red: [255, 0, 0] };
a.red.map; // ошибка: string | tuple

const b = { red: [255, 0, 0] } satisfies Colors;
b.red.map; // ок: TS помнит, что это кортеж
```

Плюс ловит опечатки в ключах и сохраняет литеральные типы.

@@@ ts-13 | as const
Что делает `as const`?
???
Делает выражение максимально узким и неизменяемым: строки → литералы, массивы → readonly-кортежи, поля → `readonly`.

```ts
const a = ["get", "post"];          // string[]
const b = ["get", "post"] as const; // readonly ["get", "post"]
type Method = (typeof b)[number];   // "get" | "post"
```

Часто заменяет `enum`.

@@@ ts-14 | enum, union
`enum` или union строковых литералов?
???
`enum` генерирует настоящий JS-объект, то есть код в бандле. Числовые enum небезопасны: им можно присвоить любое число. Enum не совместимы с флагом `erasableSyntaxOnly` и запуском TS в Node без сборки.

Union литералов (`"up" | "down"`) или объект `as const` не оставляют кода в рантайме и лучше тришейкаются. Поэтому сейчас чаще выбирают их.

@@@ ts-15 | основы
Что значит «структурная типизация»?
???
Совместимость определяется **формой**, а не именем типа: если у объекта есть все нужные поля, он подходит.

```ts
type Point = { x: number; y: number };

const p = { x: 1, y: 2, z: 3 };
const ok: Point = p; // ок: лишние поля разрешены

const bad: Point = { x: 1, y: 2, z: 3 }; // ошибка: excess property check — только для литералов
```

Чтобы различать одинаковые по форме типы (`UserId` и `OrderId`), используют branded types.

@@@ ts-16 | branded types
Что такое branded (номинальные) типы?
???
Приём, который имитирует номинальную типизацию:

```ts
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };

const toUserId = (s: string) => s as UserId;

function getUser(id: UserId) {}

getUser(toUserId("42")); // ок
getUser("42");           // ошибка
getUser(orderId);        // ошибка, хотя оба — string
```

@@@ ts-17 | template literal types
Что такое template literal types?
???
Строковые шаблоны на уровне типов:

```ts
type Size = "sm" | "lg";
type Color = "red" | "blue";
type Cls = `${Color}-${Size}`; // "red-sm" | "red-lg" | "blue-sm" | "blue-lg"

type EventName<T extends string> = `on${Capitalize<T>}`;
type E = EventName<"click">; // "onClick"
```

Встроенные помощники: `Uppercase`, `Lowercase`, `Capitalize`, `Uncapitalize`.

@@@ ts-18 | функции
Как описать перегрузки функций?
???
Несколько сигнатур + одна реализация, совместимая со всеми:

```ts
function parse(x: string): number;
function parse(x: number): string;
function parse(x: string | number) {
  return typeof x === "string" ? Number(x) : String(x);
}

const n = parse("1"); // number
```

Сигнатура реализации снаружи не видна. Часто перегрузки можно заменить дженериком с conditional type.

@@@ ts-19 | основы, assertion
Чем `as` отличается от аннотации типа? Что делает `!`?
???
Аннотация `const u: User = data` **проверяет** значение.

Утверждение `data as User` говорит компилятору «поверь мне» — проверки почти нет, соврать легко.

`x!` (non-null assertion) убирает `null | undefined` без всякой проверки.

Оба приёма — источники багов. Лучше сужать типы проверками или валидировать данные схемой (zod).

@@@ ts-20 | readonly, mapped types
Как сделать данные неизменяемыми на уровне типов?
???
`readonly` у полей, `Readonly<T>`, `readonly T[]`, `as const`.

Это только проверка компилятора — в рантайме объект можно изменить (для этого есть `Object.freeze`). `Readonly` поверхностный, глубокий пишут рекурсивно:

```ts
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
```

@@@ ts-21 | union, utility types, ловушка
Почему `Omit` на union-типе ломает discriminated union?
???
`Omit<A | B, "id">` работает с `keyof (A | B)` — а это только **общие** ключи. Результат схлопывается в один объект, уникальные поля и связь «тип → поля» теряются:

```ts
type Shape =
  | { id: string; kind: "circle"; radius: number }
  | { id: string; kind: "square"; size: number };

type Bad = Omit<Shape, "id">;
// { kind: "circle" | "square" } — radius и size пропали
```

Решение — дистрибутивный `Omit`: условный тип применяет `Omit` к каждому члену union отдельно.

```ts
type DistributiveOmit<T, K extends PropertyKey> =
  T extends unknown ? Omit<T, K> : never;

type Good = DistributiveOmit<Shape, "id">;
// { kind: "circle"; radius: number } | { kind: "square"; size: number }
```

То же касается `Pick` и любых своих mapped types поверх union.

@@@ ts-22 | react
Как типизировать пропсы React-компонента и `children`?
???
```tsx
type ButtonProps = React.ComponentProps<"button"> & {
  variant?: "primary" | "ghost";
};

function Button({ variant = "primary", ...rest }: ButtonProps) {
  return <button data-variant={variant} {...rest} />;
}
```

- `React.ReactNode` — для `children` (всё, что можно отрендерить);
- `React.FC` сейчас используют редко;
- события: `React.ChangeEvent<HTMLInputElement>`.

@@@ ts-23 | react, generics
Как сделать дженерик-компонент в React?
???
```tsx
type ListProps<T> = {
  items: T[];
  render: (item: T) => React.ReactNode;
  getKey: (item: T) => string;
};

function List<T>({ items, render, getKey }: ListProps<T>) {
  return <ul>{items.map((i) => <li key={getKey(i)}>{render(i)}</li>)}</ul>;
}
```

`T` выводится из `items`, и `render` получает правильный тип. Стрелочную функцию в `.tsx` пишут как `<T,>(props) => …` — запятая, чтобы не спутать с JSX.

@@@ ts-24 | d.ts, модули
Что такое `.d.ts` и declaration merging? Как расширить чужой тип?
???
`.d.ts` — файл только с типами, без кода. Так поставляются типы библиотек (`@types/*`) и описываются глобальные объекты.

**Declaration merging**: интерфейсы с одним именем в одной области сливаются в один. С `type` так не получится — повторное объявление будет ошибкой. Через слияние расширяют чужие типы:

```ts
declare module "next-auth" {
  interface Session {
    user: { id: string; role: "admin" | "user" };
  }
}

declare global {
  interface Window {
    analytics: Analytics;
  }
}

export {}; // файл должен быть модулем, чтобы работал declare global
```

Для файлов без типов: `declare module "*.svg" { const src: string; export default src; }`.

@@@ ts-25 | tsconfig
Что включает `strict: true` в tsconfig?
???
Набор флагов: `strictNullChecks` (самый важный: `null`/`undefined` — отдельные типы), `noImplicitAny`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `useUnknownInCatchVariables`, `alwaysStrict`.

Полезно добавить сверху: `noUncheckedIndexedAccess` (`arr[i]` → `T | undefined`) и `exactOptionalPropertyTypes`.

@@@ ts-26 | unknown, ошибки
Какой тип у ошибки в `catch` и как с ней работать?
???
При `strict` (флаг `useUnknownInCatchVariables`) — `unknown`. Причина: бросить можно что угодно — строку, объект, `null`, а не только `Error`. Без флага там `any`, и `e.message` компилируется, даже если его нет.

Сужай перед использованием:

```ts
try {
  await save();
} catch (e) {
  const message = e instanceof Error ? e.message : String(e);
  toast(message);
}
```

Аннотировать `catch (e: Error)` нельзя — разрешены только `unknown` и `any`. Для своих ошибок удобно завести класс `class ApiError extends Error { status = 0 }` и проверять `e instanceof ApiError`.

@@@ ts-27 | utility types, async
Как получить тип данных, которые возвращает async-функция?
???
`ReturnType` даст `Promise<…>`, поэтому оборачиваем в `Awaited`:

```ts
async function getUser() {
  return { id: 1, name: "Ann" };
}

type User = Awaited<ReturnType<typeof getUser>>;
// { id: number; name: string }
```

`typeof getUser` берёт тип функции, `ReturnType` — её результат, `Awaited` разворачивает промис. Он работает рекурсивно: `Awaited<Promise<Promise<string>>>` → `string`.

Так типы выводятся из реализации и не расходятся с ней. Аналогично `Parameters<typeof fn>[0]` даёт тип первого аргумента.

@@@ ts-28 | record, ловушка
`Record<string, T>` против `Record<"a" | "b", T>`. Какая ловушка у индексных сигнатур?
???
С union-ключами `Record` требует **все** ключи. Со `string` подходят любые ключи, но TS считает, что значение есть всегда:

```ts
const prices: Record<string, number> = {};
prices.apple.toFixed(); // компилируется, а в рантайме падает
```

Лечится флагом `noUncheckedIndexedAccess`, `Partial<Record<…>>` или `Map`.

@@@ ts-29 | вариантность, функции
Что такое ковариантность и контравариантность?
???
- **Ковариантность**: массивы и возвращаемые значения. `Dog[]` можно передать туда, где ждут `Animal[]`.
- **Контравариантность**: параметры функций. Где ждут `(d: Dog) => void`, можно передать `(a: Animal) => void`, но не наоборот: функция, которая умеет только с кошками, не справится с любым `Animal`.

С `strictFunctionTypes` это проверяется для свойств-функций, но не для методов — они бивариантны.

@@@ ts-30 | generics, новое
Что делает `NoInfer<T>`?
???
(TS 5.4) Запрещает выводить дженерик из этого места. Параметр всё равно проверяется, но не влияет на то, каким получится `T`:

```ts
function createFSM<S extends string>(states: S[], initial: NoInfer<S>) {}

createFSM(["idle", "run"], "idle"); // ок
createFSM(["idle", "run"], "jump"); // ошибка: S выводится только из states
```

Без `NoInfer` TS собрал бы `S` из обоих аргументов — `"idle" | "run" | "jump"` — и опечатка прошла бы молча.

Типичные места: значение по умолчанию, начальное состояние, `fallback`-аргумент, который должен быть одним из уже переданных вариантов.

@@@ ts-31 | union, основы
Чем отличаются `A | B` и `A & B`?
???
`A | B` — значение **одного** из типов. До сужения доступны только общие поля:

```ts
function show(x: string | string[]) {
  x.length;          // ок: есть у обоих
  x.toUpperCase();   // ошибка: у массива нет
}
```

`A & B` — значение **обоих** сразу: доступны все поля. Пересечение объектов — способ «сложить» типы: `type Admin = User & { permissions: string[] }`. Для несовместимых примитивов `string & number` → `never`.

Интуиция через множества: у union больше допустимых значений и меньше гарантий, у пересечения — меньше значений и больше гарантий.

@@@ ts-32 | валидация, zod
Почему типы TS не защищают от неверных данных с сервера? Как быть?
???
Типы стираются при компиляции: `res.json() as User` — просто обещание.

Данные извне (API, localStorage, формы) валидируют в рантайме схемами (zod, valibot) и выводят тип из схемы:

```ts
const User = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof User>;

const user = User.parse(await res.json()); // бросит, если формат не тот
```

@@@ ts-33 | классы, private
Чем `private` в TypeScript отличается от `#private` в JavaScript?
???
- `private` — проверка **только при компиляции**. В JS-коде поле обычное: его видно в консоли, и даже TS разрешает доступ через скобки `obj["secret"]`.
- `#secret` — настоящая приватность **в рантайме**: снаружи класса поле недоступно никак.

```ts
class Account {
  private secret = 1;
  #real = 2;
}
const acc = new Account();
acc.secret;    // ошибка компиляции
acc["secret"]; // компилируется — лазейка
// acc.#real   — синтаксическая ошибка вне класса
```

`protected` доступен в наследниках, `public` — везде (по умолчанию).

@@@ ts-34 | основы, unknown
Чем отличаются типы `{}`, `object` и `unknown`?
???
- `unknown` — вообще любое значение, включая `null` и `undefined`.
- `{}` — любое значение, **кроме** `null` и `undefined`: подходят и примитивы (`42`, `"str"`).
- `object` — только непримитивы: объекты, массивы, функции.

```ts
const a: {} = 42;       // ок
const b: {} = null;     // ошибка
const c: object = 42;   // ошибка
const d: object = [];   // ок
```

Частая ошибка — писать `{}` в значении «любой объект». Для «объект с любыми ключами» есть `Record<string, unknown>`.

@@@ ts-35 | функции, совместимость
Почему функцию с меньшим числом параметров можно передать туда, где ждут больше?
???
Это безопасно: функция просто проигнорирует лишние аргументы. Так устроены колбэки в JS:

```ts
const cb: (value: number, index: number) => void = (v) => {};

[1, 2, 3].forEach((n) => console.log(n)); // index и array не нужны
```

Обратное запрещено: функция, которой нужны два аргумента, может получить только один.

@@@ ts-36 | as const, enum
Как сделать «enum» из обычного объекта?
???
```ts
const ROLE = {
  Admin: "admin",
  User: "user",
} as const;

type Role = (typeof ROLE)[keyof typeof ROLE]; // "admin" | "user"

function can(role: Role) {}
can(ROLE.Admin); // ок
can("user");     // тоже ок — это просто строка
```

Плюсы перед `enum`: обычный JS-объект без особого синтаксиса, литеральные типы, можно перебрать через `Object.values`.

@@@ ts-37 | type guards, массивы
Как правильно отфильтровать `undefined` из массива, чтобы TypeScript понял тип?
???
С TS 5.5 тип-предикат **выводится автоматически** для простых проверок:

```ts
const mixed = [1, undefined, 2];
const nums = mixed.filter((x) => x !== undefined); // number[]
```

Для сложных условий предикат пишут явно:

```ts
const strs = ["a", 1, "b"].filter((x): x is string => typeof x === "string"); // string[]
```

До 5.5 первый пример давал `(number | undefined)[]`, и часто встречалось `filter(Boolean)` — оно тоже не сужает тип и вдобавок выкидывает `0` и `""`.

@@@ ts-38 | utility types, задача
Напиши тип `PartialBy<T, K>`, который делает необязательными только указанные поля.
???
```ts
type PartialBy<T, K extends keyof T> = Omit<T, K> & Partial<Pick<T, K>>;

type User = { id: number; name: string; email: string };

const u: PartialBy<User, "email"> = { id: 1, name: "Ann" }; // ок
```

Идея: отрезать поля `K` через `Omit`, взять их отдельно через `Pick`, сделать необязательными и склеить пересечением. Так же собирают `RequiredBy`, `ReadonlyBy` и другие.

@@@ ts-39 | generics, функции
Как типизировать функцию-обёртку, чтобы она сохраняла аргументы и результат исходной функции?
???
```ts
function withLog<F extends (...args: any[]) => any>(fn: F) {
  return (...args: Parameters<F>): ReturnType<F> => {
    console.log(fn.name, args);
    return fn(...args);
  };
}

const add = (x: number, y: number) => x + y;
const loggedAdd = withLog(add); // (x: number, y: number) => number
loggedAdd("1", 2);              // ошибка типа
```

`Parameters<F>` и `ReturnType<F>` достают типы из переданной функции — обёртка не теряет типизацию. Так пишут декораторы, `debounce`, `memoize`.

@@@ ts-40 | generics, const
Что такое `const`-параметры типа (`<const T>`)?
???
(TS 5.0) Просят TypeScript выводить для аргумента максимально узкий тип, как будто вызывающий написал `as const`:

```ts
function routes<const T extends readonly string[]>(paths: T) {
  return paths;
}
const r = routes(["/", "/about"]); // readonly ["/", "/about"]

function plain<T extends readonly string[]>(paths: T) {
  return paths;
}
const p = plain(["/", "/about"]); // string[]
```

Удобно для конфигов, роутов, ключей — тип API строится из переданных литералов без `as const` у пользователя.

@@@ ts-41 | generics, события
Как типизировать event emitter, чтобы данные события зависели от его имени?
???
Через карту событий и дженерик по её ключу:

```ts
type Events = {
  login: { userId: string };
  logout: undefined;
};

function on<K extends keyof Events>(name: K, cb: (payload: Events[K]) => void) {}

on("login", (p) => p.userId); // p: { userId: string }
on("signup", () => {});       // ошибка: нет такого события
```

`K` выводится из первого аргумента, а `Events[K]` подставляет нужный тип во второй. Тот же приём — для типизированных `fetch`-клиентов и роутеров.

@@@ ts-42 | mapped types, задача
Как получить union ключей объекта, значения которых — функции?
???
```ts
type FunctionKeys<T> = {
  [K in keyof T]: T[K] extends (...args: any[]) => any ? K : never;
}[keyof T];

type Service = { id: number; load(): void; save(x: number): boolean };
type M = FunctionKeys<Service>; // "load" | "save"
```

1. Mapped type превращает каждое поле в его имя или `never`.
2. Индексирование `[keyof T]` собирает значения в union.
3. `never` из union исчезает.

Альтернатива — ремаппинг ключей через `as`: `{ [K in keyof T as T[K] extends Function ? K : never]: T[K] }`.

@@@ ts-43 | utility types
Чем `Exclude` отличается от `Omit`?
???
- `Exclude<Union, Members>` работает с **union-типами**: убирает члены объединения.
- `Omit<Object, Keys>` работает с **объектами**: убирает поля.

```ts
type Status = "idle" | "loading" | "error";
type Busy = Exclude<Status, "idle">; // "loading" | "error"

type User = { id: number; name: string; email: string };
type Public = Omit<User, "email">;   // { id: number; name: string }
```

Внутри `Omit<T, K>` как раз использует `Exclude`: `Pick<T, Exclude<keyof T, K>>`.

@@@ ts-44 | пересечения, never
Что будет при пересечении типов с конфликтующими полями?
???
Зависит от того, что конфликтует:

```ts
type P = { v: string } & { v: number };
// объект остаётся, но поле v: string & number = never

type X = { kind: "x" } & { kind: "y" };
// never целиком: литеральные поля-дискриминанты несовместимы
```

TypeScript сворачивает в `never` весь объект, если конфликтуют литеральные типы (как у дискриминанта в union). Отсюда и разница между `interface extends` (сразу понятная ошибка при конфликте) и `&` (тихий `never`).

@@@ ts-45 | рекурсивные типы, mapped types
Напиши `DeepPartial<T>` — `Partial`, который работает на всех уровнях вложенности.
???
Встроенный `Partial` делает необязательными только поля верхнего уровня. Рекурсивный тип обходит вложенные объекты:

```ts
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

type Config = { db: { host: string; port: number }; debug: boolean };

const patch: DeepPartial<Config> = { db: { port: 5433 } }; // ок
```

Для массивов и функций это условие тоже сработает (они `object`). Массивы mapped type обработает корректно, а функции лучше пропускать отдельной веткой: `T extends (...args: any[]) => unknown ? T : …`.

По тому же шаблону пишут `DeepReadonly<T>` — с модификатором `readonly` вместо `?`. Где применяют: патчи конфигов, моки в тестах, частичные обновления форм.

@@@ ts-46 | generics, keyof
Как типизировать функцию `pick(obj, keys)`?
???
Ключи ограничиваем `keyof T`, а результат собираем встроенным `Pick`:

```ts
function pick<T extends object, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const out = {} as Pick<T, K>;
  for (const key of keys) out[key] = obj[key];
  return out;
}

const user = { id: 1, name: "Аня", password: "secret" };
const safe = pick(user, ["id", "name"]); // { id: number; name: string }
pick(user, ["email"]); // ошибка: "email" нет в keyof
```

Как это работает: TS выводит `K` из массива как union литералов `"id" | "name"`. `as Pick<T, K>` нужен, потому что пустой объект ещё не соответствует результату — это осознанное утверждение внутри реализации, а снаружи функция полностью типобезопасна.

@@@ ts-47 | narrowing, assertion functions
Чем assertion-функция (`asserts x is T`) отличается от type guard?
???
Type guard возвращает `boolean`, и тип сужается **внутри `if`**. Assertion-функция ничего не возвращает: она либо бросает ошибку, либо гарантирует тип **до конца области видимости**.

```ts
function assertIsDefined<T>(value: T, name: string): asserts value is NonNullable<T> {
  if (value === null || value === undefined) {
    throw new Error(`${name} не задан`);
  }
}

const el = document.querySelector("#root");
assertIsDefined(el, "#root");
el.append("ok"); // el: Element, без if и без !
```

Есть короткая форма `asserts condition` — как в `node:assert`.

Ограничение: такую функцию нужно вызывать через явно типизированное имя (объявление `function` или переменная с аннотацией типа), иначе TS выдаст ошибку о том, что assertion требует явной аннотации.

@@@ ts-48 | классы, ооп
Чем `abstract class` отличается от `interface`? Что делает `implements`?
???
**Интерфейс** — только контракт: что должно быть у объекта. После компиляции от него ничего не остаётся.

**Абстрактный класс** — частичная реализация: в нём может быть общий код, поля, конструктор, а абстрактные методы обязаны реализовать наследники. Создать его экземпляр нельзя, а в JS он остаётся обычным классом.

```ts
interface Storage {
  get(key: string): string | null;
}

abstract class Repository<T> {
  protected cache = new Map<string, T>();
  abstract load(id: string): Promise<T>;
  async get(id: string) {
    if (!this.cache.has(id)) this.cache.set(id, await this.load(id));
    return this.cache.get(id)!;
  }
}

class UserRepo extends Repository<User> implements Storage { … }
```

`implements` лишь **проверяет**, что класс соответствует интерфейсу, — ничего не наследует. Наследовать (`extends`) можно один класс, реализовать — сколько угодно интерфейсов.

@@@ ts-49 | generics, кортежи
Что такое variadic tuple types и именованные элементы кортежа?
???
Кортеж с `...` внутри может склеивать другие кортежи:

```ts
type Concat<A extends unknown[], B extends unknown[]> = [...A, ...B];
type R = Concat<[1, 2], ["a"]>; // [1, 2, "a"]

type Range = [start: number, end: number]; // имена видны в подсказках IDE
type Args = [id: string, ...tags: string[]]; // rest внутри кортежа
```

Главное применение — типизация функций, которые работают с аргументами других функций:

```ts
function partial<A extends unknown[], R>(
  fn: (first: string, ...rest: A) => R,
  first: string,
) {
  return (...rest: A) => fn(first, ...rest);
}

const greet = (name: string, age: number) => `${name}, ${age}`;
const greetAnn = partial(greet, "Аня"); // (age: number) => string
```

Имена элементов ни на что не влияют при проверке типов — они только для читаемости.

@@@ ts-50 | рекурсивные типы, json
Как описать тип для любого JSON-значения?
???
Рекурсивным union — тип ссылается сам на себя:

```ts
type Json =
  | string
  | number
  | boolean
  | null
  | Json[]
  | { [key: string]: Json };

const ok: Json = { a: [1, "two", { b: null }] };
const bad: Json = { date: new Date() }; // ошибка: Date — не Json
```

Зачем: так описывают то, что гарантированно переживёт `JSON.stringify`, — например, данные для `localStorage`, тело запроса или пропсы, которые серверный компонент передаёт в клиентский.

`undefined`, функции, `Date`, `Map` и `bigint` в JSON не входят — `JSON.stringify` их потеряет, превратит в строку или упадёт с ошибкой.

@@@ ts-51 | mapped types, template literals
Как переименовать ключи в mapped type? Напиши `Getters<T>`.
???
В mapped type после `as` можно задать новое имя ключа (key remapping, TS 4.1):

```ts
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type User = { name: string; age: number };
type UserGetters = Getters<User>;
// { getName: () => string; getAge: () => number }
```

`string & K` нужен, потому что ключом может быть `number` или `symbol`, а `Capitalize` работает только со строками.

Если после `as` вернуть `never`, ключ исчезнет — так фильтруют поля:

```ts
type OnlyStrings<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K];
};
type R = OnlyStrings<User>; // { name: string }
```

@@@ ts-52 | функции, void
Чем `void` отличается от `undefined` в типе возврата?
???
`undefined` — конкретное значение: функция обязана вернуть `undefined`.

`void` — «результат не используется». Поэтому функцию, которая **что-то** возвращает, можно передать туда, где ждут `() => void`:

```ts
const nums: number[] = [];
[1, 2].forEach((n) => nums.push(n)); // push возвращает number — и это ок

type Handler = () => void;
const h: Handler = () => 42; // разрешено
const x = h(); // x: void — использовать нельзя
```

Это сделано специально, чтобы колбэки вроде `forEach` и обработчиков событий принимали любые функции.

Ловушка: при **объявлении** функции `function f(): void { return 42; }` — уже ошибка. Послабление работает только при присваивании типа функции. Для асинхронных колбэков `() => void` скрывает промис — линтер `no-misused-promises` ловит такие места.

@@@ ts-53 | react, события
Как типизировать события в React и расширить пропсы нативного элемента?
???
События — дженерики по типу элемента:

```tsx
const onChange = (e: React.ChangeEvent<HTMLInputElement>) => setValue(e.target.value);
const onSubmit = (e: React.FormEvent<HTMLFormElement>) => e.preventDefault();
const onClick = (e: React.MouseEvent<HTMLButtonElement>) => {};

```

Подсказка: напиши обработчик сначала прямо в JSX и наведи курсор — IDE покажет нужный тип.

type ButtonProps = React.ComponentProps<"button"> & {

@@@ ts-54 | react, хуки
Как типизировать `useState`, `useRef` и `useReducer`?
???
**useState** — тип выводится из начального значения. Указывать явно нужно, когда начальное значение «уже» реального:

```tsx
const [count, setCount] = useState(0);              // number — вывелся сам
const [user, setUser] = useState<User | null>(null); // иначе был бы тип null
const [tags, setTags] = useState<string[]>([]);      // иначе never[]
```

**useRef** — два сценария:

```tsx
const inputRef = useRef<HTMLInputElement>(null); // ссылка на DOM, React заполнит сам
const timer = useRef<number | undefined>(undefined); // изменяемое значение
```

**useReducer** — тип выводится из редьюсера; экшены удобно описать discriminated union:

```tsx
type Action = { type: "add"; text: string } | { type: "remove"; id: string };

function reducer(state: Todo[], action: Action): Todo[] {
  switch (action.type) {
    case "add": return [...state, { id: crypto.randomUUID(), text: action.text }];
    case "remove": return state.filter((t) => t.id !== action.id);
  }
}
```

@@@ ts-55 | mapped types, модификаторы
Как убрать `readonly` и `?` в mapped type?
???
Модификаторы можно не только добавлять (`+`, по умолчанию), но и снимать минусом:

```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type Concrete<T> = { [K in keyof T]-?: T[K] }; // так устроен Required<T>

type Frozen = { readonly id: number; readonly name?: string };
type Editable = Mutable<Frozen>;   // { id: number; name?: string }
type Full = Concrete<Frozen>;      // { readonly id: number; readonly name: string }
```

`-?` убирает не только знак вопроса, но и `undefined` из типа поля, которое появилось из-за `?`.

Где пригодится: получить изменяемую копию типа из `as const`-объекта, сделать тип «после валидации», где все поля уже заполнены, или написать свой `PartialBy` / `RequiredBy`.

@@@ ts-56 | object.keys, ловушка
Почему `Object.keys(obj)` возвращает `string[]`, а не `(keyof T)[]`?
???
Из-за структурной типизации у объекта в рантайме может быть **больше** ключей, чем описано в типе:

```ts
type Point = { x: number; y: number };
const p3 = { x: 1, y: 2, z: 3 };
const p: Point = p3; // разрешено: лишние поля не мешают

Object.keys(p); // ["x", "y", "z"] — "z" не входит в keyof Point
```

Если бы TS возвращал `("x" | "y")[]`, код `p[key].toFixed()` мог бы упасть на `z`. Поэтому `string[]` — честный тип.

Как быть, когда объект точно под твоим контролем (константа, `as const`):

```ts
const keys = Object.keys(config) as (keyof typeof config)[];
// или
for (const [key, value] of Object.entries(config)) { … }
```

Утверждение `as` — твоя ответственность: используй его только там, где лишних ключей быть не может.

@@@ ts-57 | template literals, infer
Как вывести параметры из строки маршрута `"/users/:id/posts/:postId"`?
???
Рекурсивный условный тип с `infer` в шаблонной строке:

```ts
type Params<Path extends string> =
  Path extends `${string}:${infer Param}/${infer Rest}`
    ? { [K in Param | keyof Params<Rest>]: string }
    : Path extends `${string}:${infer Param}`
      ? { [K in Param]: string }
      : {};

type P = Params<"/users/:id/posts/:postId">;
// { id: string; postId: string }

function href<T extends string>(path: T, params: Params<T>) { … }
href("/users/:id", { id: "42" });  // ок
href("/users/:id", { uid: "42" }); // ошибка
```

Как работает: `infer Param` захватывает текст между `:` и `/`, `Rest` — остаток строки, который обрабатывается тем же типом рекурсивно.

Так устроены типизированные роуты в tRPC, Hono, Express и TanStack Router. На собесе ценят не запоминание, а умение объяснить, что делает каждый `infer`.

@@@ ts-58 | модули, tsconfig
Зачем нужен `import type` и флаг `verbatimModuleSyntax`?
???
`import type` говорит, что импорт нужен **только для типов**, и компилятор гарантированно удалит его из JS:

```ts
import type { User } from "./types";
import { api, type Session } from "./api"; // смешанный вариант
```

Почему это важно:

- сборщики (esbuild, SWC, Babel) компилируют каждый файл отдельно и не знают, тип это или значение. Импорт несуществующего в рантайме значения ломает сборку или оставляет лишний код;
- импорт ради типов не тянет модуль с побочными эффектами в бандл;
- явно видно, что зависимость только «типовая».

`verbatimModuleSyntax: true` (TS 5.0) делает правило строгим: импорты без `type` остаются в JS **как есть**, а импорт, используемый только как тип, но без пометки `type`, — ошибка. Он заменил старые флаги `importsNotUsedAsValues` и `preserveValueImports`. Похожий по смыслу `isolatedModules` проверяет, что каждый файл можно скомпилировать отдельно.

@@@ ts-59 | fetch, безопасность типов
Как типизировать обёртку над `fetch` и почему `res.json() as T` небезопасно?
???
Простой вариант — дженерик:

```ts
async function getJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json() as Promise<T>;
}

const user = await getJson<User>("/api/me");
```

Но это **обещание**, а не проверка: `res.json()` возвращает `any`, и если сервер пришлёт другую структуру, TypeScript не узнает — ошибка вылезет дальше по коду.

Надёжный вариант — проверять данные в рантайме схемой и выводить тип из неё:

```ts
const UserSchema = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof UserSchema>;

async function getUser() {
  const res = await fetch("/api/me");
  return UserSchema.parse(await res.json()); // бросит, если формат не тот
}
```

Тип и проверка получаются из одного источника и не разъедутся.

@@@ ts-60 | conditional types, never
Почему `IsNever<never>` не даёт `true`, и как это исправить?
???
```ts
type IsNever<T> = T extends never ? true : false;
type A = IsNever<never>; // never, а не true!
```

Условный тип над «голым» параметром **дистрибутивен**: он применяется к каждому члену union по отдельности. `never` — это пустой union, членов нет, поэтому и результат пустой — `never`.

Исправление — обернуть обе стороны в кортеж, чтобы отключить дистрибутивность:

```ts
type IsNever<T> = [T] extends [never] ? true : false;
type B = IsNever<never>;  // true
type C = IsNever<string>; // false
```

Тот же приём нужен, когда условный тип должен работать с union **целиком**: `[T] extends [string]` проверит весь `"a" | 1` разом, а не каждый член отдельно.
