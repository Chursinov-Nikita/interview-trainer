@@@ state-01 | основы
Зачем нужен стейт-менеджер, если есть `useState` и Context?
???
**`useState`** — состояние живёт **внутри одного компонента**. Если те же данные нужны соседнему или далёкому компоненту, состояние приходится поднимать к общему родителю и передавать пропсами через все уровни (prop drilling).

**Context** решает проблему передачи: данные доступны любому компоненту внутри провайдера. Но у него есть ограничение — при **любом** изменении `value` перерисовываются **все** потребители, даже если им нужно поле, которое не менялось. Для корзины, где меняется количество товара, это означает перерисовку шапки, страницы, сайдбара — всех, кто читает контекст.

**Стейт-менеджер** (Zustand, Redux) хранит состояние **вне React** — в обычном JS-объекте. Компоненты подписываются на нужный кусочек через **селектор**:

```ts
const count = useCart((s) => s.items.length); // перерисуюсь, только если изменилось число товаров
```

Компонент перерисуется, только если изменился **результат селектора**, а не всё состояние.

Что ещё даёт стейт-менеджер:

- логика изменения данных отделена от UI и лежит в одном месте;
- данные доступны вне компонентов (в утилитах, обработчиках WebSocket);
- DevTools: история всех изменений и «путешествие во времени»;
- готовые решения: сохранение в `localStorage` (persist), middleware.

Когда **не** нужен: небольшое приложение, где состояние локальное, а данные с сервера живут в TanStack Query.

@@@ state-02 | основы, server state
Чем серверное состояние отличается от клиентского? Где хранить данные из API?
???
Это два принципиально разных вида данных.

**Клиентское состояние** принадлежит интерфейсу и существует только в браузере: открыта ли модалка, выбранная вкладка, тема, черновик формы. Мы им полностью владеем — оно меняется, только когда мы его меняем.

**Серверное состояние** — это **копия** данных, которые на самом деле живут на сервере: список товаров, профиль, сообщения. Мы им не владеем:

- оно **устаревает** — другой пользователь или вкладка могли изменить данные;
- его нужно **загружать** — со статусами загрузки и ошибки;
- нужен **кэш**, чтобы не грузить одно и то же повторно;
- нужна **инвалидация** — перезагрузка после изменений;
- нужны повторы при ошибке, дедупликация одинаковых запросов, обновление при возврате на вкладку.

Если хранить серверные данные в Redux или Zustand вручную, всё это придётся писать самому — и обычно с ошибками.

Поэтому серверное состояние отдают специализированным библиотекам: **TanStack Query**, **RTK Query**, **SWR**, а в Next.js — серверным компонентам.

```tsx
const { data: todos, isPending } = useQuery({ queryKey: ["todos"], queryFn: fetchTodos });
```

В сторе остаётся только по-настоящему клиентское состояние — и его обычно оказывается удивительно мало.

@@@ state-03 | redux, основы
Три принципа Redux.
???
**1. Единый источник правды.** Всё глобальное состояние приложения хранится в **одном** объекте — сторе. Не разбросано по компонентам, а лежит в одном месте, которое можно посмотреть целиком.

**2. Состояние только для чтения.** Нельзя написать `state.user.name = "Аня"`. Единственный способ что-то изменить — **отправить action**: объект, описывающий, что произошло:

```ts
dispatch({ type: "user/renamed", payload: "Аня" });
```

**3. Изменения делают чистые функции.** Reducer получает текущее состояние и action и возвращает **новое** состояние, не трогая старое. Никаких запросов, случайных чисел и мутаций внутри:

```ts
function userReducer(state = { name: "" }, action) {
  if (action.type === "user/renamed") return { ...state, name: action.payload };
  return state;
}
```

**Поток данных** всегда один и тот же:

```
UI → dispatch(action) → reducer → новый state → UI перерисовывается
```

Зачем такие ограничения: любое изменение проходит через одну «дверь», поэтому всегда видно, **что**, **когда** и **почему** изменилось. Redux DevTools показывает список всех экшенов и позволяет «отмотать» состояние назад. Баг легко воспроизвести: те же экшены — то же состояние.

Цена — больше кода, чем в Zustand. Redux Toolkit убирает большую часть этого кода.

@@@ state-04 | redux, основы
Что такое action, reducer, dispatch и store?
???
Аналогия с банком: **store** — сейф с деньгами, **action** — заявка («снять 100 рублей»), **dispatch** — окошко, куда подают заявку, **reducer** — кассир, который по правилам выдаёт новую выписку.

- **Action** — обычный объект, описывающий **событие**. Обязательное поле `type` — строка с именем события, данные кладут в `payload`:

```ts
{ type: "todos/added", payload: "Купить молоко" }
```

- **Reducer** — чистая функция `(state, action) => newState`. Смотрит на `type` и решает, как изменить состояние. Если экшен ему не знаком — возвращает state без изменений:

```ts
function todos(state: string[] = [], action: { type: string; payload: string }) {
  switch (action.type) {
    case "todos/added":
      return [...state, action.payload]; // новый массив, старый не тронут
    default:
      return state;
  }
}
```

- **Store** — объект, который хранит текущее состояние и даёт три метода:
  - `getState()` — прочитать состояние;
  - `dispatch(action)` — отправить экшен;
  - `subscribe(listener)` — подписаться на изменения.

- **Dispatch** — единственный способ изменить состояние. Стор передаёт action в reducer, сохраняет результат и уведомляет подписчиков.

```ts
store.dispatch({ type: "todos/added", payload: "Купить молоко" });
store.getState(); // ["Купить молоко"]
```

`= []` в параметре — начальное состояние: при самом первом вызове state ещё `undefined`.

@@@ state-05 | redux, rtk
Что такое Redux Toolkit и `createSlice`?
???
**Redux Toolkit (RTK)** — официальный и рекомендуемый способ писать на Redux. Классический Redux требовал много шаблонного кода: отдельно константы типов, отдельно функции-создатели экшенов, отдельно reducer со `switch` и ручным копированием через spread. RTK убирает почти всё это.

**`createSlice`** — главная функция RTK. «Слайс» (кусочек) — часть состояния вместе с логикой её изменения. Из одного описания он сам генерирует reducer и action creators:

```ts
const todosSlice = createSlice({
  name: "todos",                 // префикс для type экшенов
  initialState: [] as Todo[],
  reducers: {
    added(state, action: PayloadAction<string>) {
      // «мутация» разрешена — внутри Immer
      state.push({ id: nanoid(), text: action.payload, done: false });
    },
    toggled(state, action: PayloadAction<string>) {
      const todo = state.find((t) => t.id === action.payload);
      if (todo) todo.done = !todo.done;
    },
  },
});

export const { added, toggled } = todosSlice.actions;
export default todosSlice.reducer;
```

Что получилось:

- `added("Купить молоко")` создаёт экшен `{ type: "todos/added", payload: "Купить молоко" }` — писать его руками не нужно;
- `todosSlice.reducer` — готовый reducer, который подключают в стор;
- внутри редьюсеров можно писать «мутирующий» код (`push`, присваивание) — Immer превратит его в иммутабельное обновление.

`PayloadAction<string>` — тип TypeScript: «экшен, у которого `payload` — строка». Благодаря ему `dispatch(added(42))` будет ошибкой компиляции.

@@@ state-06 | redux, immer
Почему в `createSlice` можно «мутировать» state?
???
Redux требует иммутабельности: новое состояние должно быть **новым объектом**, иначе подписчики не заметят изменений. Но писать иммутабельные обновления вложенных данных неудобно:

```ts
// без Immer: изменить done у одной задачи в списке внутри проекта
return {
  ...state,
  projects: state.projects.map((p) =>
    p.id === projectId
      ? { ...p, todos: p.todos.map((t) => (t.id === todoId ? { ...t, done: true } : t)) }
      : p,
  ),
};
```

RTK оборачивает каждый редьюсер в библиотеку **Immer**. Она передаёт в функцию не настоящий state, а **черновик** (draft) — Proxy-обёртку. Ты меняешь черновик как обычный объект, Immer записывает каждое изменение, а потом собирает из них **новый неизменяемый** объект:

```ts
// с Immer: то же самое
const todo = state.projects.find((p) => p.id === projectId)?.todos.find((t) => t.id === todoId);
if (todo) todo.done = true;
```

Важная деталь: Immer копирует **только изменённый путь**. Объекты, которые не менялись, сохраняют прежние ссылки, — поэтому селекторы, читающие другие части, не вызывают лишних ререндеров.

Правило: в редьюсере либо мутируй черновик, либо **возвращай** новое значение — но не то и другое одновременно:

```ts
reset: () => [],                      // ✓ вернуть новое значение
added: (state, a) => { state.push(a.payload); }, // ✓ мутировать черновик
bad: (state, a) => { state.push(a.payload); return state; }, // ✗ так нельзя
```

Мутации работают **только** внутри `createSlice` и `createReducer`. В компоненте или в обычном Redux они по-прежнему ломают обновления.

@@@ state-07 | redux, rtk, typescript
Как подключить Redux Toolkit к React с типизацией?
???
Три шага.

**1. Создать стор** и вывести из него типы:

```ts
// store.ts
export const store = configureStore({
  reducer: { todos: todosSlice.reducer },
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;

export const useAppSelector = useSelector.withTypes<RootState>();
export const useAppDispatch = useDispatch.withTypes<AppDispatch>();
```

`RootState` выводится из самого стора: добавил новый слайс — тип обновился сам. Типизированные хуки нужны, чтобы не писать `(state: RootState) =>` в каждом компоненте.

**2. Подключить провайдер** в корне приложения — он делает стор доступным всем компонентам:

```tsx
<Provider store={store}>
  <App />
</Provider>
```

**3. Использовать в компонентах:**

```tsx
function TodoList() {
  const todos = useAppSelector((s) => s.todos);  // читать
  const dispatch = useAppDispatch();
  return (
    <>
      {todos.map((t) => <p key={t.id}>{t.text}</p>)}
      <button onClick={() => dispatch(added("Новая задача"))}>Добавить</button>
    </>
  );
}
```

`useAppSelector` подписывает компонент на часть состояния, `dispatch` отправляет экшены.

`configureStore` сам подключает Redux DevTools, middleware для асинхронных thunk и проверки в dev-режиме. В Next.js стор создают на каждый запрос, а `Provider` кладут в клиентский компонент.

@@@ state-08 | redux, селекторы
Что такое селектор и зачем мемоизировать селекторы?
???
**Селектор** — функция, которая достаёт из всего состояния нужную часть: `(state) => state.todos`. Компонент через `useSelector` подписывается именно на результат селектора.

Как работает подписка: после **каждого** экшена в сторе `useSelector` заново вызывает селектор и сравнивает новый результат с прошлым через `===`. Если ссылка изменилась — компонент перерисовывается.

**Проблема:** селектор, который создаёт новый массив, возвращает новую ссылку **каждый раз**:

```ts
const done = useSelector((s: RootState) => s.todos.filter((t) => t.done));
```

`filter` всегда создаёт новый массив. Значит, компонент будет перерисовываться после любого экшена в приложении — даже если изменилось что-то, не связанное с задачами. Плюс сам `filter` выполняется каждый раз.

**Решение — мемоизированный селектор** через `createSelector` (библиотека Reselect, встроена в RTK):

```ts
const selectTodos = (s: RootState) => s.todos;

const selectDone = createSelector(
  [selectTodos],                         // входные селекторы
  (todos) => todos.filter((t) => t.done), // вычисление
);

const done = useSelector(selectDone);
```

`createSelector` запоминает входные данные и результат. Если `s.todos` — та же ссылка, что в прошлый раз, он не вызывает вычисление, а возвращает **тот же** массив. Компонент не перерисуется.

Правило: если селектор возвращает примитив или существующую часть state — мемоизация не нужна. Если вычисляет новый массив или объект — нужна.

@@@ state-09 | redux, async
Как делать асинхронные операции в Redux? Что такое thunk?
???
Reducer обязан быть **синхронным и чистым**: в нём нельзя делать запросы. Значит, асинхронная логика должна жить где-то ещё — в **middleware**.

**Thunk** — самый простой вариант. Это функция, которую можно передать в `dispatch` вместо объекта-экшена. Middleware видит, что пришла функция, и вызывает её, передав `dispatch` и `getState`:

```ts
const loadTodos = () => async (dispatch, getState) => {
  dispatch({ type: "todos/loading" });
  const res = await fetch("/api/todos");
  dispatch({ type: "todos/loaded", payload: await res.json() });
};

dispatch(loadTodos());
```

Внутри thunk можно делать что угодно: запросы, задержки, несколько dispatch подряд, чтение текущего состояния.

В RTK есть **`createAsyncThunk`** — он сам генерирует три экшена для жизненного цикла запроса:

```ts
export const fetchTodos = createAsyncThunk("todos/fetch", async () => {
  const res = await fetch("/api/todos");
  return (await res.json()) as Todo[];
});

// в extraReducers слайса:
builder
  .addCase(fetchTodos.pending, (state) => { state.status = "loading"; })
  .addCase(fetchTodos.fulfilled, (state, action) => {
    state.status = "idle";
    state.items = action.payload;
  })
  .addCase(fetchTodos.rejected, (state) => { state.status = "failed"; });
```

- `pending` — запрос начался;
- `fulfilled` — успех, данные в `action.payload`;
- `rejected` — ошибка.

Для обычной загрузки данных с сервера сейчас лучше RTK Query — он делает всё это и кэширует результат.

@@@ state-10 | redux, middleware
Что такое middleware в Redux?
???
Прослойка между `dispatch` и редьюсером. Экшен проходит через цепочку middleware, и каждая может его пропустить, изменить, задержать или остановить:

```ts
const logger: Middleware = (store) => (next) => (action) => {
  console.log("до", store.getState());
  const result = next(action); // передать дальше по цепочке
  console.log("после", store.getState());
  return result;
};
```

Почему три вложенные функции: `store` передаётся один раз при создании стора, `next` — ссылка на следующее звено цепочки, а `action` — каждый отправленный экшен. Если не вызвать `next(action)`, экшен не дойдёт до редьюсера.

Именно здесь живут побочные эффекты, ведь редьюсеры обязаны быть чистыми. Примеры: thunk (разрешает диспатчить функции), логгер, аналитика, `listenerMiddleware` в RTK, RTK Query.

`configureStore` уже подключает thunk и dev-проверки; свои добавляют так: `middleware: (getDefault) => getDefault().concat(logger)`.

Аналогия — конвейер проверок в аэропорту: пассажир (экшен) проходит пункты по очереди, и каждый может пропустить его дальше, что-то записать или развернуть назад.

@@@ state-11 | redux, rtk query
Что такое RTK Query?
???
Слой загрузки данных в Redux Toolkit, аналог TanStack Query. Описываешь эндпоинты — получаешь хуки с кэшем, дедупликацией, статусами загрузки и инвалидацией по тегам:

```ts
const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
  tagTypes: ["Todo"],
  endpoints: (b) => ({
    getTodos: b.query<Todo[], void>({
      query: () => "todos",
      providesTags: ["Todo"],
    }),
    addTodo: b.mutation<Todo, string>({
      query: (text) => ({ url: "todos", method: "POST", body: { text } }),
      invalidatesTags: ["Todo"], // после добавления список перезапросится
    }),
  }),
});

export const { useGetTodosQuery, useAddTodoMutation } = api;
```

Использование в компоненте:

```tsx
const { data: todos, isLoading, error } = useGetTodosQuery();
const [addTodo, { isLoading: isAdding }] = useAddTodoMutation();
```

Как работают теги: запрос `getTodos` помечает свои данные тегом `"Todo"`. Мутация `addTodo` после успеха объявляет этот тег устаревшим — и все запросы с ним автоматически перезагружаются. Не нужно вручную вызывать повторную загрузку.

- **query** — для чтения данных (GET), кэшируется;
- **mutation** — для изменения (POST, PUT, DELETE), не кэшируется.

Плюс перед TanStack Query: живёт внутри Redux, видно в Redux DevTools, если проект уже на Redux. Минус: тянет за собой Redux.

@@@ state-12 | zustand, основы
Как создать стор в Zustand?
???
Zustand — минималистичный стейт-менеджер. Стор создаётся функцией `create`, а результат — это **хук**, который можно сразу использовать в компонентах. Провайдер не нужен.

```ts
import { create } from "zustand";

type Bears = {
  bears: number;        // данные
  add: () => void;      // экшены
  reset: () => void;
};

export const useBears = create<Bears>()((set) => ({
  bears: 0,
  add: () => set((s) => ({ bears: s.bears + 1 })),
  reset: () => set({ bears: 0 }),
}));
```

Что здесь происходит:

- функция внутри `create` получает `set` и возвращает **начальное состояние** — объект, где рядом лежат и данные, и функции для их изменения;
- `set` обновляет состояние: принимает объект с новыми полями или функцию от текущего состояния.

В компоненте читаем через **селектор** — функцию, которая выбирает нужное поле:

```tsx
function BearCounter() {
  const bears = useBears((s) => s.bears);  // перерисуется только при смене bears
  const add = useBears((s) => s.add);
  return <button onClick={add}>Медведей: {bears}</button>;
}
```

Сравнение с Redux: нет экшенов-объектов, редьюсеров, `dispatch` и провайдера. Экшены — обычные функции в сторе. Поэтому кода в разы меньше.

Двойные скобки `create<T>()(…)` — особенность TypeScript: так он правильно выводит типы, когда добавляются middleware вроде `persist`.

@@@ state-13 | zustand, основы
Как работает `set` в Zustand? Нужно ли копировать всё состояние?
???
`set` делает **поверхностное слияние** верхнего уровня. Ты передаёшь только изменившиеся поля, а остальные Zustand сохранит сам:

```ts
// состояние: { bears: 0, fish: 10, add: fn }
set({ bears: 1 });
// стало:     { bears: 1, fish: 10, add: fn } — fish и add на месте
```

То есть `{ ...state }` вручную писать не нужно — это отличие от `useState` с объектом.

Но слияние только **на одном уровне**. Вложенные объекты заменяются целиком, поэтому их копируют сами:

```ts
// состояние: { user: { name: "Аня", age: 25 } }
set({ user: { name: "Боб" } });             // ✗ age пропал
set((s) => ({ user: { ...s.user, name: "Боб" } })); // ✓
```

Две формы `set`:

- `set({ bears: 0 })` — объект, когда новое значение не зависит от старого;
- `set((s) => ({ bears: s.bears + 1 }))` — функция, когда зависит. Она получает актуальное состояние.

Ещё полезное:

- `set(state, true)` — режим **замены**: состояние заменяется целиком, без слияния (осторожно — экшены тоже пропадут, если их не передать);
- `get()` — второй аргумент функции стора; читает текущее состояние внутри экшена:

```ts
create<Cart>()((set, get) => ({
  items: [],
  total: () => get().items.reduce((sum, i) => sum + i.price, 0),
}));
```

- мутировать state напрямую (`s.bears++`) нельзя — компоненты не узнают об изменении. Если хочется такого синтаксиса, подключают middleware `immer`.

@@@ state-14 | zustand, селекторы
Почему в Zustand важны селекторы? Что такое `useShallow`?
???
Компонент перерисовывается, когда меняется то, что вернул селектор. Поэтому то, **что** ты выбираешь, определяет, **как часто** компонент рендерится.

```ts
const state = useBears();                  // ✗ подписка на ВСЁ состояние
const bears = useBears((s) => s.bears);    // ✓ только на bears
```

Без селектора компонент перерисуется при изменении любого поля стора — даже того, которое он не использует.

**Проблема с объектами.** Zustand сравнивает результат селектора с прошлым через `Object.is` — по ссылке. Если селектор собирает **новый** объект, ссылка каждый раз новая:

```ts
const { bears, add } = useBears((s) => ({ bears: s.bears, add: s.add }));
// { bears, add } — новый объект при каждом вызове
```

В Zustand 5 это не просто лишние ререндеры, а **бесконечный цикл** с ошибкой «Maximum update depth exceeded».

**`useShallow`** сравнивает результат **поверхностно** — по каждому полю, а не по ссылке на объект:

```ts
import { useShallow } from "zustand/react/shallow";

const { bears, add } = useBears(
  useShallow((s) => ({ bears: s.bears, add: s.add })),
);
```

Теперь компонент перерисуется, только если изменилось `bears` или `add`.

Альтернатива без `useShallow` — несколько отдельных селекторов, каждый возвращает одно значение:

```ts
const bears = useBears((s) => s.bears);
const add = useBears((s) => s.add);
```

Это самый простой и надёжный вариант. `useShallow` нужен для массивов из `filter`/`map` и объектов из нескольких полей.

@@@ state-15 | zustand, persist
Как сохранить Zustand-стор между перезагрузками?
???
Обычный стор живёт в памяти: обновил страницу — всё сбросилось. Middleware **`persist`** автоматически сохраняет состояние в хранилище и восстанавливает его при запуске:

```ts
import { create } from "zustand";
import { persist, createJSONStorage } from "zustand/middleware";

export const useSettings = create<Settings>()(
  persist(
    (set) => ({ theme: "dark", setTheme: (theme) => set({ theme }) }),
    {
      name: "settings",                                // ключ в хранилище
      storage: createJSONStorage(() => localStorage),
      partialize: (s) => ({ theme: s.theme }),        // что сохранять
      version: 1,                                      // + migrate при смене формата
    },
  ),
);
```

Что делают опции:

- `name` — под каким ключом лежат данные (в `localStorage` будет `settings`);
- `storage` — куда сохранять: `localStorage` (по умолчанию), `sessionStorage` или своё асинхронное хранилище;
- `partialize` — сохранять только часть состояния. Функции и временные поля (открыта ли модалка) сохранять не нужно;
- `version` и `migrate` — если формат данных изменился, старые сохранения можно преобразовать.

**Гидратация.** С `localStorage` данные читаются синхронно и доступны почти сразу. С асинхронным хранилищем (IndexedDB) стор восстанавливается не сразу: первый рендер увидит начальные значения. Поэтому нужен флаг готовности, а пока его нет — показывать заглушку. Так сделано в этом приложении.

В Next.js с SSR сервер не видит `localStorage`, поэтому при гидратации возможны расхождения — тут помогает опция `skipHydration` и ручной вызов `rehydrate()` после монтирования.

@@@ state-16 | zustand
Как читать и менять Zustand-стор вне компонентов?
???
Хук, который возвращает `create`, — это ещё и объект стора с API:

```ts
useBears.getState().add();        // прочитать состояние или вызвать экшен
useBears.setState({ bears: 10 }); // записать (поверхностное слияние)

const unsubscribe = useBears.subscribe((state, prev) => {
  if (state.bears !== prev.bears) console.log(state.bears);
});
```

Удобно в утилитах, тестах, обработчиках WebSocket, интерцепторах axios (например, достать токен).

```ts
axios.interceptors.request.use((config) => {
  const token = useAuth.getState().token;
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});
```

Ловушка: `getState()` в теле компонента не подписывает его на изменения — компонент не перерисуется. В компонентах читай через хук с селектором, а `getState()` используй в обработчиках событий и вне React.

Это одно из главных отличий Zustand от Context: стор существует сам по себе, и React — лишь один из его подписчиков.

@@@ state-17 | zustand, архитектура
Как организовать большой Zustand-стор и подключить devtools?
???
Два пути: делить на **слайсы** (функции, возвращающие часть состояния) и собирать их в одном `create` — или заводить несколько независимых сторов по доменам. Второе обычно проще.

Слайс — обычная функция с тем же `(set, get)`:

```ts
const createCartSlice = (set) => ({
  items: [],
  addItem: (item) => set((s) => ({ items: [...s.items, item] })),
});
```

Devtools — middleware `devtools`, работает с расширением Redux DevTools:

```ts
const useApp = create<State>()(
  devtools(
    persist(
      (...a) => ({ ...createUserSlice(...a), ...createCartSlice(...a) }),
      { name: "app" },
    ),
  ),
);
```

`(...a)` — это `set`, `get` и API стора, которые передаются в каждый слайс. Middleware оборачивают друг друга: `devtools` снаружи видит все изменения, включая восстановление из `persist`.

Несколько сторов (`useCart`, `useAuth`, `useUi`) проще в типизации и тестировании. Один стор со слайсами удобен, когда части часто читают друг друга.

@@@ state-18 | сравнение
Redux Toolkit, Zustand или Context — что выбрать?
???
Сначала главный вопрос: **что это за данные?**

- Данные с сервера → **TanStack Query** или **RTK Query** в любом случае. Это не задача стейт-менеджера.
- Локальное состояние одного компонента → `useState`.
- Глобальное клиентское состояние → выбираем из трёх:

**Context**

- встроен в React, без библиотек;
- для данных, которые меняются **редко**: тема, язык, текущий пользователь;
- при частых изменениях — лишние ререндеры всех потребителей.

**Zustand**

- минимум кода: стор — это хук, нет провайдера, экшенов-объектов и редьюсеров;
- точечные подписки через селекторы;
- маленький размер (~1 КБ);
- отлично подходит для большинства приложений: корзина, настройки, состояние редактора, UI-флаги.

**Redux Toolkit**

- строгий и предсказуемый поток: каждое изменение — именованный экшен;
- мощные DevTools: история изменений, time travel;
- middleware, `listenerMiddleware`, RTK Query в одной экосистеме;
- устоявшиеся паттерны — новый человек в команде быстро разберётся;
- для больших команд и приложений со сложной логикой (финтех, админки, редакторы).

Короткий ответ на собеседовании: «Серверные данные — в TanStack Query. Для простого глобального стейта — Zustand. Redux Toolkit — если приложение большое, команда большая и важна строгая структура или он уже есть в проекте. Context — для редко меняющихся вещей вроде темы».

@@@ state-19 | иммутабельность
Как Redux и Zustand понимают, что состояние изменилось?
???
Сравнением **по ссылке** (`Object.is`) — это дёшево, не нужно обходить объект целиком. Поэтому изменение должно создавать новые объекты на всём пути к изменённому полю, а неизменённые части — сохранять старые ссылки:

```ts
// новый state, новый user, но settings — та же ссылка
set((s) => ({ user: { ...s.user, name } }));
```

Тогда селектор `s => s.settings` вернёт прежнюю ссылку, и подписанные на него компоненты не перерисуются.

Мутация «на месте» (`s.user.name = name`) ссылку не меняет — подписчики не узнают об изменении, и UI не обновится. Immer внутри `createSlice` позволяет писать «мутирующий» код, но под капотом создаёт новые объекты.

Почему не сравнивать по содержимому: глубокое сравнение большого состояния после каждого изменения — это обход тысяч полей. Сравнение ссылок — одна операция. Иммутабельность — это плата за быструю проверку «изменилось ли».

Наглядно: состояние — дерево. При изменении `user.name` новыми становятся только узлы на пути от корня до `name`: корень и `user`. Все остальные ветки (`settings`, `cart`) — те же объекты.

@@@ state-20 | архитектура
Что такое однонаправленный поток данных?
???
Данные движутся по кругу **в одну сторону**:

```
state → view → action → новый state → view …
```

1. **State** — текущее состояние.
2. **View** — интерфейс отображает состояние.
3. **Action** — пользователь что-то сделал, интерфейс **сообщает** об этом событии.
4. Состояние обновляется по правилам и снова отображается.

Главное правило: представление **не меняет** состояние напрямую. Оно только сообщает «пользователь нажал на кнопку». Решение, как изменить данные, принимается в одном месте.

Чем это лучше двустороннего связывания (когда интерфейс и модель меняют друг друга напрямую): в большом приложении при двусторонней связи изменение может вызвать цепочку других изменений, и непонятно, кто и почему поменял данные. При однонаправленном потоке у каждого изменения есть одна причина — конкретный экшен, — и его можно найти и отладить.

Это архитектура **Flux** (Facebook), из которой вырос Redux. В самом React тот же принцип:

- данные идут **вниз** через пропсы;
- события идут **вверх** через колбэки (`onChange`, `onClick`);
- ребёнок не может изменить пропсы — только попросить родителя через колбэк.

```tsx
<Counter value={count} onIncrement={() => setCount(count + 1)} />
```

`Counter` показывает `value` и сообщает о клике, а решение об изменении принимает родитель.

@@@ state-21 | zustand, производные данные
Нужно ли хранить в сторе вычисляемые данные (сумму корзины, отфильтрованный список)?
???
Обычно **нет**. Хранят минимальное исходное состояние, а производное вычисляют в селекторе:

```ts
const useCart = create<Cart>()((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
}));

// в компоненте
const total = useCart((s) => s.items.reduce((sum, i) => sum + i.price * i.qty, 0));
```

Иначе придётся синхронизировать `items` и `total` при каждом изменении, и рано или поздно они разъедутся. Число — примитив, поэтому такой селектор не вызывает лишних ререндеров. Если селектор возвращает новый массив, нужен `useShallow` или мемоизация.

Пример расхождения: в экшене `add` пересчитали `total`, а в `remove` забыли — и корзина показывает неверную сумму. Если сумма вычисляется из `items`, такая ошибка невозможна в принципе.

Тот же принцип в Redux: в сторе — исходные данные, производные — в `createSelector`.

@@@ state-22 | zustand, immer
Как писать «мутирующие» обновления в Zustand, как в Redux Toolkit?
???
Подключить middleware `immer` (нужен пакет `immer`):

```ts
import { create } from "zustand";
import { immer } from "zustand/middleware/immer";

const useTodos = create<State>()(
  immer((set) => ({
    todos: [],
    toggle: (id) =>
      set((s) => {
        const todo = s.todos.find((t) => t.id === id);
        if (todo) todo.done = !todo.done; // мутируем черновик
      }),
  })),
);
```

Без него для вложенных изменений приходится вручную копировать каждый уровень через spread.

С `immer` функция в `set` получает черновик и может ничего не возвращать — Immer сам соберёт новое состояние. Без `immer` функция в `set` **обязана** вернуть объект с изменениями.

Для плоского состояния (`{ count, isOpen }`) `immer` не нужен — spread короче. Он окупается на вложенных структурах: списки внутри объектов, деревья, формы.

@@@ state-23 | zustand, next, ssr
Почему глобальный Zustand-стор опасен в Next.js с SSR и как быть?
???
Модуль со стором загружается на сервере **один раз** и живёт между запросами. Если записать в него данные пользователя при рендере, следующий запрос другого пользователя увидит чужое состояние.

В браузере у каждого пользователя своя копия JS, поэтому там проблемы нет. А сервер — один процесс на всех: модуль `store.ts` загружается один раз, и `useCart` у всех запросов общий.

Решение — создавать стор **на каждый запрос** через фабрику и раздавать его через контекст:

```tsx
import { createStore, useStore } from "zustand";

const createCounterStore = (init = 0) =>
  createStore<{ count: number; inc: () => void }>()((set) => ({
    count: init,
    inc: () => set((s) => ({ count: s.count + 1 })),
  }));

const StoreContext = createContext<ReturnType<typeof createCounterStore> | null>(null);

export function CounterProvider({ children }: { children: React.ReactNode }) {
  const [store] = useState(() => createCounterStore());
  return <StoreContext.Provider value={store}>{children}</StoreContext.Provider>;
}
```

В компоненте: `useStore(store, (s) => s.count)`. Клиентские SPA без SSR этой проблемы не имеют.

`useState(() => …)` гарантирует, что стор создаётся один раз на жизнь провайдера, а не при каждом рендере. `createStore` (без `create`) возвращает просто стор, без хука, — хук получают через `useStore`.

@@@ state-24 | redux, сериализуемость
Почему в Redux нельзя класть в state и actions несериализуемые значения?
???
**Сериализуемое** значение — такое, которое можно превратить в JSON и обратно без потерь: строки, числа, булевы, `null`, массивы и обычные объекты из них.

Функции, промисы, `Map`, `Set`, экземпляры классов, DOM-узлы ломают:

- devtools и time-travel — их нельзя показать и восстановить;
- сохранение state (persist) и SSR-гидратацию;
- сравнение по ссылке и предсказуемость обновлений.

Redux Toolkit по умолчанию включает в dev-режиме `serializableCheck` middleware: он предупреждает о таких значениях. Даты обычно хранят как ISO-строки или timestamp.

```ts
state.createdAt = new Date();             // ✗ предупреждение
state.createdAt = new Date().toISOString(); // ✓ "2026-11-15T10:00:00.000Z"
```

Вместо `Map` — обычный объект `{ [id]: item }`, вместо `Set` — массив или объект с `true`. Дату обратно в `Date` превращают при отображении.

@@@ state-25 | redux, нормализация
Что такое нормализация state и `createEntityAdapter`?
???
Вместо вложенных массивов хранят сущности как **таблицу**: `{ ids: [...], entities: { [id]: item } }`. Поиск по id становится O(1), обновление одной сущности не требует обхода массива, а дубликатов в разных местах дерева нет.

Проблема без нормализации: один и тот же пользователь — автор поста и автор комментария — хранится в двух местах. Он сменил аватар, и нужно найти и обновить все копии. В нормализованном виде пользователь лежит один раз в `users.entities`, а посты хранят только `authorId`. Идея та же, что у таблиц в базе данных.

RTK даёт готовый адаптер:

```ts
const postsAdapter = createEntityAdapter<Post>();

const postsSlice = createSlice({
  name: "posts",
  initialState: postsAdapter.getInitialState(),
  reducers: {
    added: postsAdapter.addOne,
    updated: postsAdapter.updateOne,
    removed: postsAdapter.removeOne,
  },
});

export const { selectAll, selectById } = postsAdapter.getSelectors((s: RootState) => s.posts);
```

Адаптер даёт готовые редьюсеры (`addOne`, `addMany`, `setAll`, `upsertOne`, `removeOne`) и селекторы (`selectAll` — массив в порядке `ids`, `selectById` — одна сущность). Можно задать сортировку через `sortComparer`.

@@@ state-26 | tanstack query
Как устроен TanStack Query? Чем `staleTime` отличается от `gcTime`?
???
TanStack Query — библиотека для серверного состояния. Это **кэш данных по ключу**: ты описываешь, *какие* данные нужны и *как* их получить, а библиотека сама решает, когда загружать, когда брать из кэша и когда обновлять.

```tsx
const { data, isPending, error } = useQuery({
  queryKey: ["todos", { page }], // при смене ключа — новый запрос
  queryFn: () => fetchTodos(page),
  staleTime: 60_000,
});
```

У данных в кэше есть два «таймера»:

**`staleTime`** (по умолчанию **0**) — сколько данные считаются **свежими**.

- Пока свежие — повторного запроса нет, данные берутся из кэша.
- Когда устарели — они всё равно **показываются мгновенно** из кэша, но в фоне уходит запрос за новыми. Это происходит при монтировании компонента, возврате на вкладку браузера и восстановлении сети.

С нулём по умолчанию данные устаревают сразу, поэтому каждый новый компонент с этим ключом запускает фоновое обновление.

**`gcTime`** (по умолчанию **5 минут**; в v4 назывался `cacheTime`) — сколько хранить в памяти данные, на которые **никто не подписан** (все компоненты с этим ключом размонтированы). Потом кэш удаляется сборщиком мусора.

Пример: ушёл со страницы списка → через минуту вернулся. Данные ещё в кэше (`gcTime` не истёк) — список показывается мгновенно. Если они устарели (`staleTime` прошёл), в фоне подтянется свежая версия.

Бонусы: **дедупликация** (несколько компонентов с одним ключом делают один запрос), повторы при ошибке (3 раза по умолчанию), статусы `isPending`, `isFetching`, `error`.

@@@ state-27 | tanstack query, мутации
Как обновить данные после мутации в TanStack Query?
???
**Мутация** — запрос, который **изменяет** данные на сервере (POST, PUT, DELETE). После неё кэш списка устарел: в нём нет новой задачи. Есть три способа обновить его.

**1. Инвалидация** (самый частый) — пометить связанные запросы устаревшими, они сами перезапросятся:

```tsx
const queryClient = useQueryClient();

const addTodo = useMutation({
  mutationFn: (text: string) => api.post("/todos", { text }),
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ["todos"] }),
});

addTodo.mutate("Купить молоко");
```

`invalidateQueries` работает **по префиксу** ключа: задевает и `["todos"]`, и `["todos", { page: 2 }]`. Активные запросы (на экране) перезагрузятся сразу, неактивные — при следующем использовании.

**2. Записать ответ в кэш** — если сервер уже вернул обновлённые данные, лишний запрос не нужен:

```tsx
onSuccess: (newTodo) => {
  queryClient.setQueryData<Todo[]>(["todos"], (old = []) => [...old, newTodo]);
},
```

**3. Оптимистичное обновление** — изменить кэш **до** ответа сервера в `onMutate`, а в `onError` откатить. Интерфейс реагирует мгновенно — подходит для лайков и чекбоксов.

Важно: `setQueryData` требует иммутабельного обновления — возвращай новый массив, а не мутируй старый.

@@@ state-28 | атомы, jotai
Что такое атомарный стейт-менеджмент (Jotai) и чем он отличается от стора?
???
Вместо одного большого стора — множество маленьких независимых **атомов**, которые можно комбинировать:

```ts
const countAtom = atom(0);
const doubledAtom = atom((get) => get(countAtom) * 2); // производный атом

function Counter() {
  const [count, setCount] = useAtom(countAtom);
  const doubled = useAtomValue(doubledAtom);
}
```

Подписка точечная: компонент перерисуется, только если изменился его атом. Модель похожа на `useState`, но общий для всего приложения.

Сравнение: **Zustand** и **Redux** — «сверху вниз» (один стор, селекторы), **Jotai** — «снизу вверх» (атомы и зависимости между ними).

Производный атом `doubledAtom` сам знает, от чего зависит: при изменении `countAtom` он пересчитается, а при изменении других атомов — нет. Селекторы и мемоизация не нужны.

Когда удобно: много независимых кусочков состояния, которые иногда зависят друг от друга (редакторы, конструкторы, формы со связанными полями). Jotai от того же автора, что и Zustand.

@@@ state-29 | redux toolkit, store
Что `configureStore` настраивает по умолчанию?
???
По сравнению со старым `createStore` он сразу включает разумные настройки:

- **объединяет редьюсеры**: можно передать объект `{ todos, user }` вместо ручного `combineReducers`;
- **подключает middleware**: `thunk` для асинхронной логики;
- **в dev-режиме добавляет проверки**: ругается, если state мутируют вне Immer или кладут в него несериализуемые значения (`Date`, `Map`, функции);
- **включает Redux DevTools**.

```ts
export const store = configureStore({
  reducer: { todos: todosReducer, user: userReducer },
  middleware: (getDefault) => getDefault().concat(logger),
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

Важно: в RTK 2 `middleware` принимает только функцию, а свои middleware добавляют через `getDefault().concat(...)`. Если вернуть только свой массив (`() => [logger]`), стандартные — thunk и проверки — пропадут.

Объект `reducer` определяет форму состояния: `{ todos: …, user: … }` даст `state.todos` и `state.user`. Каждый слайс отвечает только за свою ветку.

@@@ state-30 | redux toolkit, async
Как обработать загрузку и ошибку `createAsyncThunk` в слайсе?
???
Thunk сам диспатчит три экшена, а слайс ловит их в `extraReducers`:

```ts
export const fetchUser = createAsyncThunk(
  "user/fetch",
  async (id: string, { rejectWithValue }) => {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) return rejectWithValue(`Ошибка ${res.status}`);
    return (await res.json()) as User;
  },
);

const userSlice = createSlice({
  name: "user",
  initialState: { data: null as User | null, status: "idle", error: null as string | null },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => { state.status = "loading"; state.error = null; })
      .addCase(fetchUser.fulfilled, (state, action) => { state.status = "succeeded"; state.data = action.payload; })
      .addCase(fetchUser.rejected, (state, action) => {
        state.status = "failed";
        state.error = (action.payload as string) ?? action.error.message ?? "Ошибка";
      });
  },
});
```

`rejectWithValue` кладёт свою ошибку в `action.payload`; обычное исключение попадает в `action.error`. Статус лучше хранить строкой (`"idle" | "loading" | …`), а не набором флагов `isLoading` + `isError`. В RTK 2 `extraReducers` принимает только функцию с `builder`.

Почему строка лучше флагов: с флагами возможны бессмысленные комбинации — `isLoading: true` и `isError: true` одновременно. Одно поле `status` физически не может быть в двух состояниях.

В компоненте: `dispatch(fetchUser("42"))`, а результат можно дождаться через `.unwrap()` — он вернёт данные или бросит ошибку.

@@@ state-31 | redux toolkit, side effects
Что такое `listenerMiddleware` и когда он нужен?
???
Способ реагировать на экшены побочными эффектами — замена redux-saga и redux-observable для большинства задач:

```ts
const listener = createListenerMiddleware();

listener.startListening({
  actionCreator: cartItemAdded,
  effect: async (action, api) => {
    api.cancelActiveListeners(); // как debounce: отменить прошлый запуск
    await api.delay(500);
    await saveCart(api.getState().cart);
  },
});

const store = configureStore({
  reducer,
  middleware: (getDefault) => getDefault().prepend(listener.middleware),
});
```

Чем отличается от thunk: thunk вызывают явно (`dispatch(fetchX())`), а слушатель срабатывает **сам**, когда произошло событие. Это удобно для реакций «когда X — сделать Y»: автосохранение, аналитика, синхронизация с `localStorage`, показ тоста после успешного запроса.

Есть `api.condition(...)` (подождать нужного состояния) и `api.fork(...)` (дочерняя задача) — этого хватает для сложных сценариев без генераторов saga.

Разбор примера: пользователь быстро добавляет 5 товаров. Каждый экшен запускает эффект, но `cancelActiveListeners` отменяет предыдущий, а `delay(500)` ждёт паузы. Корзина сохранится один раз — через полсекунды после последнего добавления.

@@@ state-32 | redux, селекторы, ловушка
Почему `useSelector((s) => ({ a: s.a, b: s.b }))` вызывает лишние ререндеры?
???
`useSelector` вызывает селектор после **каждого** экшена в сторе и сравнивает результат с прошлым через `===`. Селектор, который возвращает новый объект, всегда даёт новую ссылку — компонент перерисовывается при любом изменении в сторе, даже чужом.

Решения:

```ts
// 1. Несколько селекторов — по одному на значение
const a = useSelector((s: RootState) => s.a);
const b = useSelector((s: RootState) => s.b);

// 2. Поверхностное сравнение
import { shallowEqual } from "react-redux";
const { a, b } = useSelector((s: RootState) => ({ a: s.a, b: s.b }), shallowEqual);

// 3. Мемоизированный селектор для вычислений
const selectDone = createSelector([(s: RootState) => s.todos], (todos) => todos.filter((t) => t.done));
```

`filter`, `map` и spread внутри селектора — тот же случай. В dev-режиме React-Redux предупреждает, если селектор возвращает разные ссылки для одного и того же состояния. В Zustand аналог — `useShallow`.

`shallowEqual` сравнивает объекты **по полям**: `{ a: 1, b: 2 }` и новый `{ a: 1, b: 2 }` для него равны. Обычное `===` считает их разными, потому что это два разных объекта.

@@@ state-33 | redux toolkit, actions
Что такое `prepare` в `createSlice` и зачем он нужен?
???
Функция, которая формирует `payload` **до** того, как экшен попадёт в редьюсер. Туда выносят генерацию id, даты и преобразование аргументов:

```ts
const todosSlice = createSlice({
  name: "todos",
  initialState: [] as Todo[],
  reducers: {
    todoAdded: {
      reducer(state, action: PayloadAction<Todo>) {
        state.push(action.payload);
      },
      prepare(text: string) {
        return { payload: { id: nanoid(), text, createdAt: new Date().toISOString() } };
      },
    },
  },
});

dispatch(todoAdded("Купить молоко"));
```

Почему не генерировать id в самом редьюсере: редьюсер должен быть **чистым и детерминированным**. Тот же экшен при повторном проигрывании (time travel в DevTools, тесты) обязан давать тот же результат, а `nanoid()` и `Date.now()` каждый раз разные.

Дата хранится строкой, потому что `Date` — несериализуемое значение.

Бонус: вызывающему коду не нужно знать, как устроен `Todo`, — он передаёт только текст, а всё служебное добавляет `prepare`.

@@@ state-34 | redux, редьюсеры
Что нельзя делать в редьюсере?
???
Редьюсер — чистая функция `(state, action) => newState`. Поэтому в нём **нельзя**:

- делать запросы, писать в `localStorage`, менять URL, показывать тосты — всё это побочные эффекты (их место в thunk, listener или компоненте);
- вызывать `dispatch` — другой экшен должен быть результатом логики снаружи;
- использовать случайные значения и текущее время (`Math.random()`, `Date.now()`) — выносим в `prepare` или в аргументы экшена;
- мутировать state вне Immer (в обычном Redux) и мутировать `action.payload`;
- быть асинхронным.

Можно и нужно: вычислять новое состояние только из `state` и `action`.

Зачем такие строгости: предсказуемость (одинаковый вход → одинаковый результат), простые тесты без моков, time travel в DevTools и уверенность, что повтор экшена ничего не сломает.

Тест редьюсера — это просто вызов функции: `expect(reducer([], added("x"))).toEqual([{ text: "x" }])`. Никаких моков сети и React.

@@@ state-35 | redux toolkit, слайсы
Может ли слайс реагировать на экшены другого слайса?
???
Да, через `extraReducers`. Так один экшен меняет несколько частей состояния, и не нужно диспатчить два экшена подряд:

```ts
// authSlice
export const loggedOut = createAction("auth/loggedOut");

// cartSlice
const cartSlice = createSlice({
  name: "cart",
  initialState: [] as CartItem[],
  reducers: { /* ... */ },
  extraReducers: (builder) => {
    builder.addCase(loggedOut, () => []); // при выходе очистить корзину
  },
});
```

`reducers` создаёт **свои** экшены слайса, `extraReducers` — только слушает чужие (или экшены `createAsyncThunk`).

Это основной принцип Redux: экшен описывает **событие** («пользователь вышел»), а не команду («очистить корзину»). Какие слайсы и как на него реагируют, решают сами слайсы. Благодаря этому одно событие легко подхватить в новом месте, не меняя код отправителя.

Технически каждый экшен проходит через **все** редьюсеры стора, и каждый сам решает, реагировать ли. `extraReducers` — способ сказать «и на этот чужой экшен тоже».

@@@ state-36 | zustand, архитектура
Где хранить экшены в Zustand: внутри стора или отдельно?
???
Обычно экшены кладут в стор рядом с данными:

```ts
const useCart = create<CartState>()((set) => ({
  items: [],

}));

```

```ts
  useCart.setState((s) => ({ items: [...s.items, item] }));
```

Плюсы второго варианта: экшен вызывается откуда угодно без хука и селектора, его проще тестировать и разбивать по файлам, в сторе остаются только данные (удобно для `persist` и сброса).

Минус — нет одного места, где видно всё API стора. Оба подхода нормальные, главное — единообразие в проекте.

В компоненте второй вариант выглядит так: `<button onClick={() => addItem(item)}>` — без `useCart((s) => s.add)`.

@@@ state-37 | zustand, persist, миграции
Как обновить сохранённый Zustand-стор, если поменялась структура данных?
???
У `persist` есть номер версии и функция миграции. Если версия в хранилище меньше текущей, перед гидратацией вызовется `migrate`:

```ts
const useSettings = create<Settings>()(
  persist(
    (set) => ({ theme: "light", setTheme: (theme) => set({ theme }) }),
    {
      name: "settings",
      version: 2,
      migrate: (persisted, version) => {
        if (version < 2) {
          const old = persisted as { dark: boolean };
          return { theme: old.dark ? "dark" : "light" };
        }
        return persisted as Settings;
      },
      partialize: (s) => ({ theme: s.theme }), // сохранять только данные
    },
  ),
);
```

Без миграции у пользователей со старыми данными приложение может упасть на поле, которого раньше не было.

Сценарий: в версии 1 тема хранилась как `{ dark: true }`, в версии 2 — как `{ theme: "dark" }`. У пользователя в `localStorage` лежат старые данные. `migrate` получает их вместе со старым номером версии и превращает в новый формат.

Ещё полезное: `partialize` — не сохранять функции и временные поля; `onRehydrateStorage` — узнать, когда данные загрузились; `skipHydration` — запустить гидратацию вручную (например, после монтирования в Next.js).

@@@ state-38 | zustand, тесты
Как сбросить Zustand-стор (при выходе из аккаунта или между тестами)?
???
Вынести начальное состояние в константу и добавить экшен `reset`:

```ts
const initialState = { items: [] as Item[], coupon: null as string | null };

const useCart = create<typeof initialState & Actions>()((set) => ({
  ...initialState,
  add: (item) => set((s) => ({ items: [...s.items, item] })),
  reset: () => set(initialState),
}));
```

`set` по умолчанию **сливает** объект с текущим состоянием, поэтому экшены сохранятся.

Ловушка: `set(initialState, true)` (режим replace) заменит состояние целиком — и экшены пропадут.

Для тестов есть встроенный способ — вернуть стор к начальному состоянию, включая экшены:

```ts
beforeEach(() => {
  useCart.setState(useCart.getInitialState(), true);
});
```

Если используется `persist`, после выхода стоит ещё очистить хранилище: `useCart.persist.clearStorage()`.

Зачем сбрасывать между тестами: стор живёт на уровне модуля, и данные одного теста иначе «перетекут» в следующий — тесты начнут зависеть от порядка запуска.

@@@ state-39 | zustand, внутреннее устройство
Как Zustand устроен внутри и почему ему не нужен провайдер?
???
Ядро — маленькая функция `createStore`: состояние хранится в замыкании, подписчики — в `Set`:

```ts
const createStore = (init) => {
  let state;
  const listeners = new Set();
  const setState = (partial) => {
    const next = typeof partial === "function" ? partial(state) : partial;
    if (!Object.is(next, state)) {
      const prev = state;
      state = Object.assign({}, state, next);
      listeners.forEach((l) => l(state, prev));
    }
  };
  const getState = () => state;
  const subscribe = (l) => (listeners.add(l), () => listeners.delete(l));
  state = init(setState, getState);
  return { getState, setState, subscribe };
};
```

Хук подключает этот стор к React через `useSyncExternalStore` и перерисовывает компонент, только если изменился результат селектора.

Провайдер не нужен, потому что стор — обычный объект на уровне модуля: любой файл, который его импортирует, получает тот же экземпляр. Обратная сторона — на сервере такой стор общий для всех запросов, поэтому в SSR его создают на запрос и передают через контекст.

Обрати внимание на `Object.assign({}, state, next)` — это и есть поверхностное слияние, из-за которого `set({ bears: 1 })` не стирает остальные поля. А `Object.is` — та самая проверка по ссылке.

@@@ state-40 | react, context, useReducer
Можно ли заменить Redux связкой `useReducer` + Context? Где предел?

- нет middleware и DevTools;
- асинхронную логику придётся писать самому.

Подходит для состояния, которое меняется редко и нужно небольшой части дерева: форма-мастер, состояние виджета. Для глобального, часто меняющегося состояния лучше Zustand или Redux Toolkit.

По сути это «мини-Redux» без библиотек: тот же reducer, те же экшены. Если позже понадобится Redux, логику редьюсера можно перенести почти без изменений.

@@@ state-41 | tanstack query, ключи
Как устроены ключи запросов в TanStack Query? Что такое зависимые запросы?
???
`queryKey` — массив, который однозначно описывает данные. В него входит **всё**, от чего зависит запрос:

```ts
useQuery({
  queryKey: ["todos", { status, page }],
  queryFn: () => fetchTodos({ status, page }),
});
```

- Поменялся `page` — это новый ключ, будет новый запрос и отдельная запись в кэше.
- Порядок полей в объекте не важен — ключ хешируется детерминированно.
- Инвалидация работает по префиксу: `invalidateQueries({ queryKey: ["todos"] })` обновит все списки задач.

Частая ошибка — забыть параметр в ключе: `queryKey: ["todos"]`, а `queryFn` использует `page`. Тогда при смене страницы ключ тот же, запроса не будет, и на экране останется первая страница.

Ключи удобно собирать в одном месте (query key factory): `todoKeys.list(filters)`, `todoKeys.detail(id)`.

**Зависимый запрос** ждёт данных другого — через `enabled`:

```ts
const { data: user } = useQuery({ queryKey: ["user", email], queryFn: () => getUser(email) });
const { data: projects } = useQuery({
  queryKey: ["projects", user?.id],
  queryFn: () => getProjects(user!.id),
  enabled: !!user?.id,
});
```

Пока `enabled` равен `false`, второй запрос не выполняется.

- ссылкой можно поделиться — коллега увидит то же самое;
- работают кнопки «назад» и «вперёд»;
- состояние переживает перезагрузку;
- в Next.js сервер получает фильтры в `searchParams` и сразу рендерит нужные данные.

```tsx
const params = useSearchParams();
const router = useRouter();

const setSort = (sort: string) => {
  const next = new URLSearchParams(params);
  next.set("sort", sort);
  router.replace(`?${next}`, { scroll: false });
};
```

`replace` вместо `push` — чтобы каждое изменение сортировки не добавляло запись в историю браузера. `push` уместен, когда переход — осознанный шаг (сменили страницу каталога).

Что **не** класть в URL: секреты и личные данные, большие объекты, значения, которые меняются на каждый символ без debounce, временное UI-состояние (открыт ли дропдаун).

Для удобной работы есть библиотека `nuqs`: типизированные параметры как `useState`.

@@@ state-43 | rtk query, оптимистичные обновления
Как сделать оптимистичное обновление в RTK Query?
???
В мутации используют `onQueryStarted`: сразу меняют кэш, а при ошибке откатывают изменения:

```ts
toggleTodo: build.mutation<Todo, { id: string; done: boolean }>({
  query: ({ id, done }) => ({ url: `todos/${id}`, method: "PATCH", body: { done } }),
  async onQueryStarted({ id, done }, { dispatch, queryFulfilled }) {
    const patch = dispatch(
      api.util.updateQueryData("getTodos", undefined, (draft) => {
        const todo = draft.find((t) => t.id === id);
        if (todo) todo.done = done;
      }),
    );
    try {
      await queryFulfilled;
    } catch {
      patch.undo(); // сервер ответил ошибкой — вернуть как было
    }
  },
}),
```

- `updateQueryData(endpoint, args, recipe)` меняет закэшированный ответ через Immer — можно «мутировать» `draft`.
- `args` должны совпадать с аргументами, с которыми вызывался запрос (здесь `undefined`).
- `patch.undo()` возвращает кэш в прошлое состояние.

Когда оправдано: частые и почти всегда успешные действия — лайки, чекбоксы, перетаскивание. Для оплаты и необратимых операций лучше честно показать загрузку.

«Оптимистичное» значит, что мы заранее считаем запрос успешным. Пользователь видит отметку мгновенно, хотя сервер ответит через 300 мс, — интерфейс ощущается быстрым.

@@@ state-44 | формы, архитектура
Где хранить состояние формы: локально или в глобальном сторе?
???
По умолчанию — **локально**: в `useState`, `useReducer` или react-hook-form внутри компонента формы. Ввод пользователя нужен только этой форме до отправки, а глобальный стор добавил бы лишние ререндеры и код.

В стор или другое долговременное место состояние формы переносят, когда:

- это **многошаговый мастер**, и шаги — разные маршруты;
- нужно сохранять **черновик** между перезагрузками (стор с `persist`, `sessionStorage`);
- данные формы одновременно показываются в другом месте (живое превью);
- параметры формы — это фильтры, которыми хочется делиться (URL).

После отправки результат — это уже **серверные данные**: их место в кэше TanStack Query, RTK Query или в серверных компонентах, а не в клиентском сторе.

Общий принцип: держи состояние **как можно ближе** к месту использования и поднимай выше, только когда появилась реальная причина.

@@@ state-45 | сигналы, реактивность
Что такое сигналы и чем они отличаются от `useState`?
???
Сигнал — контейнер значения, который сам отслеживает, кто его читает. При изменении обновляются только эти места, а не весь компонент:

```ts
import { signal, computed, effect } from "@preact/signals";

const count = signal(0);
const double = computed(() => count.value * 2);

effect(() => console.log(double.value)); // перезапустится при смене count
count.value++;
```

Отличия от React-модели:

- `useState` перерисовывает **компонент целиком**, и React сравнивает результат;
- сигнал обновляет **точечно** (fine-grained) — конкретный текстовый узел или эффект, без повторного вызова компонента;
- зависимости собираются автоматически, массивов зависимостей нет.

Как собираются зависимости: когда `computed` или `effect` выполняется, каждое чтение `.value` регистрирует его как подписчика этого сигнала. Поэтому не нужно перечислять зависимости вручную — они известны по факту чтения.

Сигналы — основа Solid, Preact Signals, Angular, Qwik, похожая модель у `ref` во Vue; для JavaScript есть предложение в TC39. React идёт другим путём: вместо сигналов — React Compiler, который автоматически убирает лишние ререндеры.

@@@ state-46 | zustand, производительность
Как подписаться на частые изменения Zustand-стора без ререндеров?
???
Для значений, которые меняются десятки раз в секунду (координаты мыши, прогресс анимации, позиция скролла), ререндер на каждое изменение — слишком дорого. Можно подписаться на стор **вручную** и обновлять DOM напрямую через `ref`:

```tsx
function Cursor() {
  const dotRef = useRef<HTMLDivElement>(null);

  useEffect(
    () =>
      usePointer.subscribe((state) => {
        if (dotRef.current) {
          dotRef.current.style.transform = `translate(${state.x}px, ${state.y}px)`;
        }
      }),
    [],
  );

  return <div ref={dotRef} className="dot" />;
}
```

`subscribe` возвращает функцию отписки — её удобно вернуть из эффекта как cleanup.

В документации Zustand это называется transient updates. Компонент отрисовывается один раз, а дальше значение меняется без участия React. Этот приём стоит применять точечно: обычные данные лучше читать хуком с селектором.
