@@@ out-01 | event-loop, промисы
Что выведет код?

```js
console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve()
  .then(() => console.log("C"))
  .then(() => console.log("D"));
queueMicrotask(() => console.log("E"));
console.log("F");
```
???
`A F C E D B`

Разбираем по шагам, следя за двумя очередями.

1. **Синхронный код** выполняется сразу: печатается `A`.
2. `setTimeout` кладёт колбэк `B` в очередь **макрозадач**.
3. `Promise.resolve()` уже выполнен, поэтому первый `.then` (`C`) сразу встаёт в очередь **микрозадач**. Второй `.then` (`D`) пока **не** в очереди — он ждёт, когда выполнится `C`.
4. `queueMicrotask` кладёт `E` в очередь микрозадач. Очередь сейчас: `C`, `E`.
5. Синхронно печатается `F`. Стек пуст.
6. Выполняются **все** микрозадачи по порядку: `C` → после него в очередь встаёт `D` → `E` → `D`.
7. Только когда микрозадач не осталось, берётся макрозадача: `B`.

Ключевая мысль: цепочка `.then` не ставится в очередь целиком. Каждое следующее звено попадает туда только после выполнения предыдущего, поэтому `E` «вклинивается» между `C` и `D`.

@@@ out-02 | async, event-loop
Что выведет код?

```js
async function f() {
  console.log(1);
  await null;
  console.log(2);
}
console.log(3);
f();
console.log(4);
```
???
`3 1 4 2`

Тело async-функции до первого `await` выполняется **синхронно**, как у обычной функции, поэтому `1` печатается сразу после `3`. На `await` функция приостанавливается и возвращает промис, а продолжение (`console.log(2)`) уходит в очередь микрозадач. Она выполнится, когда опустеет стек вызовов, — то есть после `4`.

`await null` ведёт себя как `await Promise.resolve(null)`: даже если значение не промис, продолжение всё равно асинхронное.

@@@ out-03 | event-loop
Что выведет код?

```js
setTimeout(() => console.log(1));
Promise.resolve().then(() => {
  console.log(2);
  setTimeout(() => console.log(3));
  Promise.resolve().then(() => console.log(4));
});
console.log(5);
```
???
`5 2 4 1 3`

Состояние очередей по шагам:

1. Синхронный код: таймер `1` → в макрозадачи, `.then` → в микрозадачи, печатается `5`.
   - макрозадачи: `[1]`, микрозадачи: `[then]`
2. Стек пуст — выполняются микрозадачи. `then` печатает `2`, ставит таймер `3` и микрозадачу `4`.
   - макрозадачи: `[1, 3]`, микрозадачи: `[4]`
3. Очередь микрозадач выполняется **до конца**, включая добавленные по ходу: печатается `4`.
4. Микрозадач больше нет — берём первую макрозадачу: `1`.
5. После неё снова проверяются микрозадачи (пусто), затем следующая макрозадача: `3`.

Таймеры с одинаковой задержкой срабатывают в порядке постановки. `1` поставлен раньше, чем `3`, поэтому идёт первым — хотя `3` был создан внутри микрозадачи, он всё равно в общей очереди таймеров.

@@@ out-04 | промисы
Что выведет код?

```js
const p = new Promise((resolve) => {
  console.log(1);
  resolve(2);
  console.log(3);
});
p.then((v) => console.log(v));
console.log(4);
```
???
`1 3 4 2`

- Функция-исполнитель `new Promise(...)` вызывается **синхронно**, прямо в конструкторе.
- `resolve` не прерывает её, как `return`, — `3` всё равно печатается. Повторный `resolve` или `reject` после первого игнорируется.
- Колбэк `.then` всегда асинхронный (микрозадача), даже если промис уже выполнен, поэтому `2` идёт после синхронного `4`.

Из-за синхронного исполнителя исключение внутри него не вылетает наружу, а превращается в reject промиса.

@@@ out-05 | промисы, ошибки
Что выведет код?

```js
Promise.reject(new Error("boom"))
  .then(() => console.log("then"))
  .catch((e) => {
    console.log("catch", e.message);
    return "ok";
  })
  .then((v) => console.log("after", v))
  .finally(() => console.log("finally"));
```
???
```
catch boom
after ok
finally
```

Как ошибка «путешествует» по цепочке:

1. Промис отклонён с ошибкой `boom`.
2. `.then(() => …)` передан только обработчик успеха. Для отклонённого промиса он не вызывается — ошибка **проходит мимо** к следующему звену. Поэтому `then` не печатается.
3. `.catch` ловит ошибку, печатает `catch boom` и **возвращает** `"ok"`. Возврат обычного значения из `catch` означает «ошибка обработана» — дальше цепочка снова успешная со значением `"ok"`.
4. `.then` получает `"ok"` и печатает `after ok`.
5. `.finally` вызывается в любом случае — и при успехе, и при ошибке. Аргументов он не получает и значение по цепочке пропускает дальше без изменений.

Если бы в `catch` написали `throw e` вместо `return`, следующий `.then` пропустился бы, а `finally` всё равно выполнился бы.

Аналогия — `try/catch`: после блока `catch` код продолжает выполняться нормально.

@@@ out-06 | async, ловушка
Что выведет код?

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function run() {
  [3, 1, 2].forEach(async (n) => {
    await sleep(n * 10);
    console.log(n);
  });
  console.log("done");
}
run();
```
???
`done 1 2 3`

`forEach` не ждёт промисы, которые возвращает async-колбэк: он просто запускает три задачи и идёт дальше. Поэтому `done` печатается сразу, а числа — по мере срабатывания таймеров.

Подробнее: `forEach` вызывает колбэк три раза подряд. Каждый вызов async-функции доходит до `await sleep(...)` и сразу возвращает промис, который `forEach` выбрасывает — он про промисы ничего не знает. Цикл заканчивается, печатается `done`. Таймеры на 10, 20 и 30 мс срабатывают по порядку длительности, поэтому числа идут `1 2 3`, а не в порядке массива.

Чтобы дождаться всех: `await Promise.all(arr.map(async (n) => …))`. По очереди — `for...of` с `await`.

```js
for (const n of [3, 1, 2]) {
  await sleep(n * 10);
  console.log(n); // 3 1 2 — строго по порядку, всего ~60 мс
}
console.log("done");
```

Та же ловушка у `map` без `Promise.all`, `filter` и `reduce` с async-колбэками.

@@@ out-07 | this, strict
Что выведет код? (ES-модуль, то есть строгий режим)

```js
const counter = {
  count: 0,
  inc() {
    this.count++;
    return this.count;
  },
};
const inc = counter.inc;
console.log(counter.inc());
try {
  inc();
} catch (e) {
  console.log(e instanceof TypeError);
}
```
???
`1`, затем `true`

`counter.inc()` вызван как метод — `this` это `counter`. `inc()` вызван отдельно — контекст потерян, в строгом режиме `this === undefined`, и `this.count++` бросает `TypeError`.

В нестрогом скрипте `this` был бы `globalThis`: ошибки нет, функция вернула бы `NaN`.

Почему так: `const inc = counter.inc` копирует **ссылку на функцию**, но не связь с объектом. `this` определяется в момент вызова по тому, что стоит перед точкой. У `inc()` перед вызовом ничего нет.

Откуда `NaN` в нестрогом режиме: у `globalThis` нет `count`, `undefined++` даёт `NaN`.

Исправить: `const inc = counter.inc.bind(counter)` или `const inc = () => counter.inc()`. Это та же ситуация, что при передаче метода колбэком: `setTimeout(counter.inc)`, `button.addEventListener("click", counter.inc)`.

@@@ out-08 | hoisting, tdz
Что выведет код?

```js
console.log(typeof a, typeof b);
var a = 1;
let b = 2;
```
???
`ReferenceError` — ничего не напечатается.

`var a` всплывает со значением `undefined`, а `b` до своей строки находится во временной мёртвой зоне. Ловушка в том, что `typeof` от TDZ **не защищает**: он безопасен только для необъявленных переменных (`typeof neverDeclared === "undefined"`).

Почему ничего не напечатается, даже `undefined` для `a`: аргументы `console.log` вычисляются до вызова. `typeof a` даёт `"undefined"`, затем `typeof b` бросает ошибку, и `console.log` так и не вызывается.

Логика TDZ: движок **знает**, что `b` объявлена в этом блоке (имя уже зарезервировано), но инициализация ещё не произошла. Обращение к такой переменной — явная ошибка в порядке кода, поэтому JS не возвращает молча `undefined`, а падает.

Если убрать строку `let b = 2`, ответ был бы `undefined undefined` — `b` стала бы необъявленной, а для таких `typeof` безопасен.

@@@ out-09 | приведение типов
Что выведет код?

```js
console.log([] + []);
console.log([] + {});
console.log(1 + "2" - 1);
console.log("5" * "2");
console.log(null + 1, undefined + 1);
console.log([] == false);
```
???
```
                      ← пустая строка
[object Object]
11
10
1 NaN
true
```

Общее правило: оператор `+` склеивает строки, если **хотя бы один** операнд после приведения к примитиву — строка. Остальные арифметические операторы (`-`, `*`, `/`) всегда приводят к числу.

- `[] + []`: массив приводится к примитиву через `toString` → `""`. `"" + ""` = пустая строка.
- `[] + {}`: `""` + `"[object Object]"` = `"[object Object]"`.
- `1 + "2" - 1`: слева направо. `1 + "2"` — есть строка, склейка: `"12"`. Затем `"12" - 1` — минус только числовой: `12 - 1 = 11`.
- `"5" * "2"`: умножение приводит обе строки к числам: `10`.
- `null + 1`: `null` как число — `0`, итого `1`. `undefined + 1`: `undefined` как число — `NaN`.
- `[] == false`: при нестрогом сравнении с булевым обе стороны приводятся к числу. `false` → `0`, `[]` → `""` → `0`. `0 == 0` — `true`.

Забавное следствие: `[]` — truthy (`if ([])` выполнится), но `[] == false` тоже `true`. Поэтому всегда используют `===`.

@@@ out-10 | числа
Что выведет код?

```js
console.log(0.1 + 0.2 === 0.3);
console.log((0.1 + 0.2).toFixed(2));
console.log(Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON);
```
???
`false`, `"0.30"`, `true`

Числа — это двоичные float64 (IEEE 754): `0.1` и `0.2` нельзя записать точно, сумма равна `0.30000000000000004`. Дробные числа сравнивают с допуском. Деньги хранят в целых копейках или используют библиотеки вроде decimal.js.

Почему `0.1` нельзя записать точно: в двоичной системе это бесконечная дробь, как `1/3 = 0.333…` в десятичной. Компьютер хранит её округлённой, и при сложении два округления дают заметную погрешность.

- `toFixed(2)` округляет и возвращает **строку** `"0.30"`, а не число;
- `Number.EPSILON` — самая маленькая разница между 1 и следующим представимым числом (~2.2e-16). Для больших чисел допуск нужно масштабировать.

Это не баг JavaScript: так же ведут себя Python, Java и C. В интерфейсе для денег удобно `Intl.NumberFormat`, а считать — в целых копейках.

@@@ out-11 | массивы, ловушка
Что выведет код?

```js
console.log([1, 10, 2, 21].sort());
console.log(["b", "a", "C"].sort());
console.log([1, 2, 3].map(parseInt));
```
???
```
[ 1, 10, 2, 21 ]
[ 'C', 'a', 'b' ]
[ 1, NaN, NaN ]
```

- `sort()` без компаратора сравнивает **строки** по кодам UTF-16: `"10" < "2"`, а заглавные буквы идут раньше строчных. Для чисел нужно `sort((a, b) => a - b)`, для слов — `localeCompare`.
- `map` передаёт `(value, index)`, а `parseInt` понимает второй аргумент как систему счисления: `parseInt("2", 1)` и `parseInt("3", 2)` дают `NaN`.

Подробнее про `parseInt`:

- `parseInt(1, 0)` — основание `0` означает «определить автоматически», получается `1`;
- `parseInt(2, 1)` — системы с основанием 1 не существует → `NaN`;
- `parseInt(3, 2)` — в двоичной системе есть только цифры 0 и 1, `"3"` разобрать нельзя → `NaN`.

Правильно: `["1", "2", "3"].map(Number)` или `map((s) => parseInt(s, 10))`.

Про строки: код `"C"` — 67, а `"a"` — 97, поэтому заглавные впереди. Для русского текста и правильного алфавитного порядка: `arr.sort((a, b) => a.localeCompare(b, "ru"))`.

@@@ out-12 | объекты, ссылки
Что выведет код?

```js
const a = { x: 1 };
const b = a;
b.x = 2;
const c = { ...a };
c.x = 3;
console.log(a.x, b.x, c.x);
```
???
`2 2 3`

- Объекты хранятся по ссылке: `b = a` копирует ссылку, а не объект. Изменение через `b` видно в `a`.

Глубокую копию даёт `structuredClone(a)`. А `const` запрещает переприсвоить переменную, но не менять объект, на который она указывает.

@@@ out-13 | объекты
Что выведет код?

```js
const o = { b: 1, 2: "x", a: 2, 1: "y" };
console.log(Object.keys(o));
```
???
`[ '1', '2', 'b', 'a' ]`

Порядок ключей объекта определён спецификацией: сначала ключи-целые числа по возрастанию, затем строковые — в порядке добавления, затем символы. Если важен порядок вставки для любых ключей, используй `Map`.

Обрати внимание: ключи `'1'` и `'2'` — **строки**. Ключи обычного объекта всегда строки (или символы), число `1` при записи превращается в `"1"`.

Где это ломает код: словарь «id → значение» с числовыми id. Ты добавил элементы в порядке `{ 30: …, 10: …, 20: … }`, а при переборе они идут `10, 20, 30` — порядок вставки потерян. `Map` сохраняет порядок вставки для любых ключей:

```js
const m = new Map([[30, "c"], [10, "a"]]);
[...m.keys()]; // [30, 10]
```

Ключи вроде `"01"` или `"1.5"` не считаются целыми числами и идут в порядке добавления вместе со строками.

@@@ out-14 | замыкания, scope
Что выведет код?

```js
function makeGetters() {
  const fns = [];
  for (var i = 0; i < 3; i++) fns.push(() => i);
  return fns.map((f) => f());
}
console.log(makeGetters());

const x = 10;
function show() {
  console.log(x);
}
function run() {
  const x = 20;
  show();
}
run();
```
???
`[ 3, 3, 3 ]`, затем `10`

- `var` — одна переменная на всю функцию: к моменту вызова стрелок цикл закончился и `i === 3`. С `let` было бы `[0, 1, 2]` — у каждой итерации своя копия.
- Область видимости **лексическая**: `show` видит `x` там, где объявлена, а не там, где вызвана.

Подробнее про первую часть: все три стрелки замыкаются на **одну и ту же** переменную `i`, а не на её значение в момент создания. Стрелки вызываются уже после цикла, когда `i` стала 3 (на этом значении условие `i < 3` и остановило цикл).

Про вторую часть: «лексическая» значит «определённая текстом программы». Функция `show` написана на верхнем уровне, рядом с `const x = 10`, — и всегда будет искать `x` там. Неважно, откуда её вызвали. Если бы область видимости была динамической (как в старых языках), напечаталось бы `20`.

@@@ out-15 | json
Что выведет код?

```js
console.log(
  JSON.stringify({ a: undefined, b: () => 1, c: NaN, d: new Date(0), e: [undefined] }),
);
JSON.stringify({ n: 1n });
```
???
```
{"c":null,"d":"1970-01-01T00:00:00.000Z","e":[null]}
TypeError: Do not know how to serialize a BigInt
```

- свойства со значением `undefined` и функции **пропадают**;
- `NaN` и `Infinity` становятся `null`;
- `Date` превращается в ISO-строку (у неё есть `toJSON`);
- в массиве `undefined` заменяется на `null`, чтобы не сбить индексы;
- `BigInt` сериализовать нельзя — нужно своё преобразование.

Почему так: в формате JSON нет понятий `undefined`, функция, `NaN` или дата — только строки, числа, `true`/`false`, `null`, массивы и объекты. Всё остальное `JSON.stringify` либо выбрасывает, либо превращает во что-то из этого списка.

Обратное преобразование тоже теряет информацию: `JSON.parse` вернёт дату **строкой**, а не объектом `Date`.

Где это бьёт на практике: отправка формы с `undefined`-полями (они молча не доедут до сервера), сохранение в `localStorage`, передача данных из серверного компонента в клиентский. Для `BigInt` пишут `replacer`: `JSON.stringify(data, (k, v) => typeof v === "bigint" ? v.toString() : v)`.

@@@ out-16 | typescript, excess property
На какой строке TypeScript покажет ошибку?

```ts
type Animal = { name: string };
type Dog = Animal & { bark(): void };

const d: Dog = { name: "Rex", bark() {} };
const a1: Animal = d;                          // 1
const a2: Animal = { name: "Rex", bark() {} }; // 2
```
???
Только на строке **2**.

Структурная типизация разрешает лишние поля, поэтому `Dog` можно присвоить в `Animal` (строка 1). Но для **объектного литерала**, присваиваемого прямо в переменную с типом, работает excess property check: лишнее поле в литерале — скорее всего опечатка.

Почему правила разные: в строке 1 объект `d` уже существует и используется где-то ещё как `Dog`. Присвоить его в `Animal` — нормальная ситуация: «собака — это животное», лишние поля просто не будут видны через `a1`.

В строке 2 литерал создаётся прямо здесь и **только** для `a2`. Поле `bark` никто никогда не сможет прочитать через переменную типа `Animal` — значит, его написали по ошибке. Например, опечатка `colour` вместо `color` в объекте настроек.

Обойти проверку можно, сохранив литерал сначала в переменную без типа, — поэтому она ловит опечатки, но не гарантирует отсутствие лишних полей.

Какие типы выведет TypeScript?

```ts
const arr = [1, "a"];
```

- `Promise.all` ждёт всех (30 мс) и возвращает результаты **в порядке исходного массива**, а не в порядке завершения. Обычные значения вроде `"c"` считаются уже выполненными промисами.

Поэтому `race` печатается раньше, хотя вызван вторым.

Если хотя бы один промис в `Promise.all` отклонится, весь результат сразу отклонится с этой ошибкой. Чтобы получить результаты всех, даже упавших, нужен `Promise.allSettled`.

@@@ out-40 | try, finally
Что выведет код?

```js
function first() {
  try {
    return "try";
  } finally {
    console.log("finally");
  }
}

function second() {
  try {
    return 1;
  } finally {
    return 2;
  }
}

console.log(first());
console.log(second());
```
???
```
finally
try
2
```

- `finally` выполняется **всегда** — даже после `return` в `try`. Значение `"try"` уже вычислено и «отложено», затем выполняется `finally`, и только потом функция возвращает результат.
- Если в `finally` есть свой `return`, он **перекрывает** результат `try` (и даже проглатывает брошенную в `try` ошибку).

Поэтому `return` и `throw` внутри `finally` считают плохой практикой: линтер ругается правилом `no-unsafe-finally`. В `finally` оставляют только очистку — закрыть соединение, снять флаг загрузки, убрать таймер.
